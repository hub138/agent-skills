# 好设计的规矩

## 第零步：找出核心资产，再排改动顺序（任何美化任务先做这一步）

动手之前先回答三个问题：

1. **这个站点靠什么产生价值？** 访客打开站点是为了拿到什么？哪一个界面承载这个目的，它就是核心资产。
2. **核心资产现在什么状况？** 对核心资产先截图、量参数（首屏有什么、主内容从第几屏开始、字号行宽留白是多少），拿到实况再谈优化。
3. **手上的改动服务谁？** 每一个改动都要能回答"它改善的是核心资产还是周边"。周边界面为核心资产服务，不许反过来挤占它的空间和首屏。

由此得到三条排序规则：

- **空间**：核心资产占版面主体，辅助模块放后面、两侧或折叠，不许把核心资产挤出第一屏。
- **顺序**：先做核心资产，做到能拿出手，再轮到周边界面，周边不许插队。
- **审计**：程序化检查优先——拿到源码先读源码，以代码数值为准；没有源码就写脚本量指标，秒级拿到违规清单；截图只拍违规页与代表页；改完重跑同一脚本确认清零。

不同站点的核心资产不同，动手前先判断。例子（仅为例子）：知识库站点读者来读文章，核心资产是文章页；电商站点核心资产是商品详情与下单链路；工具站点核心资产是主操作界面。判断依据是访客的目的，与界面花哨程度无关，并与用户的评价互相印证。

机制细节与常见误判见 `references/asset-priority.md`。

## 冲突时的裁决顺序

1. 页面目的与核心资产：这个页面为什么存在、给谁看；整站最有价值的界面优先得到空间与打磨。
2. **用户的实际评价**：他说好看就是好看。不许用"信息量大""更现代"反驳。注意这条裁决的是审美与工作顺序（他说丑就是丑、他说先做什么就先做什么），**不裁决工程底线**：时长、`prefers-reduced-motion`、对比度、热区这类硬约束不因用户喜欢而豁免——用户要的效果照做，约束套着做；用户点名要的纯装饰动效压到最短时长并给降级分支，不拿"炫技"当理由否掉用户的点名要求，但**不得延误阅读起点**：入场动效累计让正文/标题在 300ms 后仍看不全，就换成整体淡入这类不挡阅读的替代形式。
3. 下面的通用法则；法则之间打架时：**可读性 > 一致性 > 个性**。

## 硬规则（任何界面都成立）

1. **首屏属于核心资产**：主内容上方只放阅读所需的上下文，辅助模块放主内容之后，不得把标题挤出第一屏；标题也不得顶格贴着固定顶栏下缘，框架衔接处留呼吸（细节见 `references/spacing-layout.md` 固定框架的衔接）。
2. **层级靠三个维度一起拉开**：字号、字重、颜色深浅。只动一个维度等于没层级。（frontend-design 排版章；TDesign M03 字号/行高 Token）
3. **不靠颜色单独承载信息**：红绿之外必须有图标或文字。（ui-ux-pro-max ux-guidelines `Color Only`）
4. **正文对比度 ≥ 4.5:1**，灰字压灰底是禁止项。（同库 `Color Contrast` / `Contrast Readability`）
5. **间距走阶梯**：2/4/8/12/16/24/32/48/64，区块级留白优先 16/24/32/48。（TDesign M03 `--td-size-*`）
6. **可点元素的三项要求**：hover 反馈 + `cursor: pointer` + 键盘 focus 可见；过渡 150–300ms，超 500ms 让人不耐烦。（ui-ux-pro-max `Hover States`；frontend-design 动效章）
7. **不用 emoji 当 UI 图标**：用 SVG，统一 viewBox 24，同一套图标库。（ui-ux-pro-max `No emoji icons`）
8. **色值一律走 token**，不写死 hex；深浅主题靠 token 自适应，SVG 描边用 `currentColor`。（frontend-design 禁止硬编码色值；本项目实测：写死白描边在深色下刺眼）
9. **全站元素的位置由组件决定，不由页面决定**（搜索框在所有页面都属顶栏右上角）；页面自己挂一个就是跨页不一致。

## 找素材与参考：先联网、中文优先

需要配图、图标、字体或版式参考时，**先联网检索**（判据见 `skill-craft/SKILL.md` 第零节，此处不复制）：先走中文两轮（中文关键词 + 来源限定词；再定向官方中文文档与国内厂商技术文档），无果才用英文图库。

素材类一律**先判许可再判相关性**，许可不明或禁转载即不采用。已验证可用的源与已失效的源随手写回来源清单——不写回，下次会重复踩一遍。

## 让模型评审截图：跨模型交叉，不许自说自话

程序化脚本量不出审美、语义和「读者第一眼看到什么」。这类判断让模型看截图，但必须守四条：

- **被测与裁判用不同模型**。自己改的自己评，会顺着改动找理由；同一模型既出报告又当裁判，等于自己判卷。
- **产出是问题清单，不是评语**。结论先行：先说有没有硬规则违规，再逐条列问题并给修复方向。「可以商榷」这类报告无法执行，等于没审。
- **防虚构与防漏报同等失败**。评审集里必须放干净基线页（没有预埋缺陷的图）。在这张图上捏造缺陷，与在坏图上漏报缺陷，是同一种失败。
- **偏好不豁免工程底线**。用户偏好管审美与顺序，不管硬规则。「老板喜欢 emoji」这类背景照听，评审照判违规，沟通时不顶撞，给替代方案后照做修复。

文字与图形分别执行 `references/wording.md`、`references/diagrams.md`；完整设计任务同轮检查中文素材、说明文案、深浅主题、窄屏与交互状态。独立评审要实际截图与 DOM 指标，仅有文字附件不能声称完成视觉验收。

**优先派具备视觉与工具能力的 subagent 做独立评审**，subagent 不可用才用外部模型 CLI。规则自改进执行 `scripts/quality_gate.py`（转发到同目录的确定性实现 `skill_check.py` / `review_skill.py`）：

```bash
python3 scripts/quality_gate.py snapshot --root . --out .work/baseline.json
python3 scripts/quality_gate.py review --root . --baseline .work/baseline.json --author <改写模型> --out .work/review
python3 scripts/quality_gate.py check --root . --baseline .work/baseline.json --review .work/review/review.json --author <改写模型> --out .work/gate.json
```

review 通过 `scripts/cli_runner.py` 调外部 CLI（claude、codex、codebuddy 任一，用环境变量 `CLI_REVIEW_COMMAND` 指定命令模板，如 `claude -p --model {model}`），评审链至少两个不同模型，`--author` 排除作者；凭据由 CLI 自行管理。subagent 评审按 `skill-craft/SKILL.md` 第四节的 review.json 结构落盘，两条路径都要绑定版本摘要。规则评审只审文本；视觉验收必须另给实际截图与 DOM 指标。

**裁判先挑毛病。** 没指出具体问题的 `approved: true` 视为未通过；派裁判的指令里写明"先证明产物是错的，证明不了才算通过"。换模型时一并换身份，可并行：下游使用者（拿改后规则去真用，走它没写明的路径，指出哪一步卡住、哪一句有歧义）、挑剔审计员（指定 MECE、SWOT、五问之一扫一遍，回答缺漏、互斥与边界）、反向追问（让模型就难点对自己连环提问，人来回答，答不上的那处就是没想透的地方）。每个角色只报能让产物出错的具体输入，且指得出规则里哪一句扛不住。派评审前把已验证事实一并给出——裁判没有事实就只能比措辞。同一段读第三遍仍走不通，就派 subagent 或换模型重做这一步，不在同一会话里硬磨。

## 并行改界面：写入前先过两道锁

同一批页面常被多个会话同时改。改前端文件时尤其容易撞：共享组件与全局样式被几个会话同时写，后写的会整段覆盖前一个会话的改动，且这种覆盖不会报错。

第一道独占锁：

```bash
python3 scripts/concurrent_guard.py lock <文件路径> --agent <你的会话标识>
python3 scripts/concurrent_guard.py unlock <文件路径> --agent <你的会话标识> --token <lock返回的token>
```

拿不到锁（退出码 3）换目标或等锁过期，默认 30 分钟。共享组件、全局样式、布局模板这几类文件最容易撞，动手前必先拿锁。

第二道内容校验：

```bash
FP=$(python3 scripts/concurrent_guard.py fp <文件路径>)   # 读完后立刻记
python3 scripts/concurrent_guard.py check <文件路径> --fp $FP   # 每次写回前
```

check 报「内容已被改动」（退出码 4）时，重读文件看清对方改了什么：对方改的是同一处就合并，改的是别处就保留对方的再叠加本轮。确认要丢弃对方改动才重新 lock 后写入。

两道锁各管一层：锁管「同时写」，指纹管「改完覆盖」。只认锁会在锁释放后覆盖别人成果，只认指纹会在两人同时读到同一版本时互相覆盖。

## 两条反直觉经验（本项目实测，不是抄来的）

- **引导元素要颜色和位置一起设计**：颜色对但埋没 = 没用；位置对但刺眼 = 反感。音量降到所在容器级别（导航项级，不要大卡级）。历史：大黄卡过重 → 安静小行无引导力 → 暖橙导航项可用。
- **"当前位置"与"推荐"是两套语义**，必须视觉可区分：当前位置 = 实底框（路由决定），推荐 = 暖橙项（站长指定）。实底框语义神圣，挪用一次导航定位就废。

## 三条判断纪律

- **能跑不等于对**。渲染出来没报错只说明它没崩，不说明它该这样。改完先回答"为什么非得这么改"，答不上就是照搬，不是设计。
- **自己先拿到事实再看模型输出**。截图、DOM 量测、前后对照是自己的 1 和 2；手里没有这些，模型给的 3 和 4 看不出荒谬。让模型评审之前先把量测数据附上。
- **再进一步**。改完不是结束：这次踩到的坑能不能变成一条可复用判据、能不能沉淀成脚本？觉得"够用"通常只是没想到还能更好。

## 红线

- 没定位核心资产就动手改界面，等于没做。
- 判断好坏以用户评价为准，不以"信息量大 / 酷炫 / 现代"自行排序。
- 删元素必须补位，不留空洞；太空 = 布局错，缩小容器重排。
- 改完必须截图看，不能只看代码。
- 共享组件只有一份实现（顶栏、侧栏、搜索框），页面只调用；跨页一致性要程序化量（多页一起检容器与坐标，单页截图永远"对"）。用户用类比描述交互时判据照原话写：要"翻页变标题"，验收就是下滑后顶栏仍在且显示当前页面标题。
- 站点专属偏好（默认 tab、气泡判丑、参考站清单）由各站点自行维护，与本技能冲突时以站点自己的设计语言为准。

## 改本技能之前

改规则的判据——该不该写、怎么抽象、预算与独立评审——在 `skill-craft/SKILL.md`，**本文不复制**。这里只给执行入口：先 `quality_gate.py snapshot` 存长期基线，再按 `check` → `review` → 带评审记录的 `check` 顺序验收（命令见上文）。评审优先 subagent 并绑定版本；仅静态通过时 publishable=false。改 `SKILL.md` 用 `--whole`。

## 站点环境（各站点自行维护）

改完站点代码必须重启服务，否则看到的是旧行为；实例地址、端口与重启命令由各站点的站点开发技能环境表维护，本文不复制。两条通用纪律：

- **禁止 `ps aux | grep <进程名> | xargs kill`** 的方式杀服务——同机往往跑着其他项目，会误杀。
- 凭据只通过环境变量提供，不写进文档与命令历史。
