# OpenAI 评估最佳实践：从标准到架构到边缘情况（Evaluation Best Practices）

- 原文：https://platform.openai.com/docs/guides/evaluation-best-practices
- 来源：OpenAI（官方平台文档）
- 发布：官方文档页，随平台版本持续更新
- 译文说明：全文翻译，术语保留英文原词，代码块保持英文原文。官方中文镜像站（developers.openai.ac.cn）已提供中文版，本译文对照官方英文原文与中文镜像综合整理。

生成式 AI 具有多变性。模型面对相同输入有时会产生不同输出，传统软件测试方法不足以应对 AI 架构。评估（evals）是面对这种多变性时测试 AI 系统的方法。

本指南提供设计评估的高层指导。要开始使用 Evals API，参阅官方「评估模型性能」指南。

官方弃用通知：OpenAI 正在逐步弃用 Evals 平台。过渡期内现有评估内容仍然可用；自 2026 年 10 月 31 日起，现有用户对 Evals 的访问将变为只读；平台计划于 2026 年 11 月 30 日正式关闭。时间线见官方弃用页面。本指南的方法论（成功标准、评估器类型、架构分层、边缘情况分类）在平台关闭后仍然适用，评估实践的载体可以迁移到 Datasets 与自建评估管线。

## 什么是评估

评估是衡量模型性能的结构化测试。尽管 AI 系统具有非确定性，评估有助于确保其准确性、性能与可靠性。它们也是通过微调提高 LLM 应用性能的少数方法之一。

### 评估的类型

看到「评估（evals）」这个词时，它可能指三件事之一：

- 行业基准：用于单独比较模型性能，例如 MMLU、HuggingFace 排行榜上的基准
- 标准数值评分：例如 ROUGE、BERTScore，设计自己用例的评估时可用
- 自建测试：你为衡量自己的 LLM 应用性能而实现的特定测试

本指南关注第三种：设计你自己的评估。

### 如何解读评估结果

经常看到 0 到 1 之间的数值评估得分，但评估的意义远不止这些得分。将指标与人工评判相结合，确保你在回答正确的问题。

评估小贴士：

- 采用评估驱动开发：尽早评估、经常评估，每个阶段写有范围限制的测试
- 设计针对特定任务的评估：让测试反映模型在真实世界数据分布中的能力
- 记录一切：开发过程中记录日志，从中挖掘好的评估案例
- 尽可能自动化：结构化评估以允许自动评分
- 这是一个旅程而非终点：评估是持续的过程
- 保持一致性：用人工反馈校准自动评分

反面模式：

- 过于通用的指标：完全依赖困惑度（perplexity）或 BLEU 分数这类学术指标
- 设计失真：评估数据集未能真实复制生产环境流量模式
- 凭感觉的评估：用「看起来在正常运行」当评估策略，或者等到上线后才开始实施任何评估
- 忽略人工反馈：未根据人工评估校准自动指标

## 设计评估流程

评估工作流有五个组成部分：

定义评估目标。评估的成功标准是什么？

收集数据集。哪些数据能帮你针对目标评估？考虑合成评估数据、领域特定评估数据、购买的评估数据、人工精选评估数据、生产数据与历史数据。

定义评估指标。你将如何检查成功标准是否满足？

运行并比较评估。迭代提升模型在你的任务或系统上的表现。

持续评估。建立持续评估（CE）：每次更改都运行评估，监控应用识别新的非确定性情况，随时间扩大评估集。

### 示例：生成会议记录摘要

测试 LLM 应用生成会议记录摘要的能力：

定义评估目标：模型生成结果的相关性与准确性应能与参考摘要媲美。

收集数据集：结合生产数据（从用户对所生成摘要的反馈中收集）与领域专家（作家）创建的数据集，确定什么是「优秀」摘要。

定义评估指标：在包含 1000 个「参考会议记录 → 摘要」的保留测试集上，实现应达到至少 0.40 的 ROUGE-L 分数，且使用 G-Eval 时的连贯性得分至少 80%。

运行并比较评估：用 Evals API 在 OpenAI 控制面板创建并运行评估。

持续评估：建立 CE，每次更改都运行评估，监控应用，随时间扩大评估集。

方法论提示：LLM 更擅长在选项之间辨别。评估应侧重成对比较、分类、按特定标准评分这类任务，避开开放式生成。将评估方法与 LLM 在对比方面的优势相匹配，能得到更可靠的评估。

### 示例：文档问答

测试 LLM 应用在文档上问答的能力：

定义评估目标：模型应能提供精准回答，按需召回上下文来推导用户意图，并提供满足用户需求的答案。

收集数据集：混合生产数据（从用户对答案的满意度中收集）、领域专家创建的硬编码正确问答、日志中的历史数据。

定义评估指标：上下文召回率至少 0.85，上下文精准率超过 0.7，70% 以上正面好评答案。

运行并比较评估：用 Evals API 在 OpenAI 控制面板创建并运行评估。

持续评估：建立 CE，每次更改都运行评估，监控应用，随时间扩大评估集。

创建评估数据集时，让强模型帮忙收集评估示例与边缘情况，生成跨各种场景的多样化测试数据。确保测试数据包含典型案例、边缘案例与对抗案例。使用人类专家标注员。

## 确定何处需要评估

从简单架构转向更复杂架构时，复杂度随之增加。四种常见架构模式：单轮模型交互、工作流、单智能体、多智能体。判断非确定性是在系统哪个环节引入的，那里就是应该实施评估的地方。

### 单轮模型交互

用户向模型提供输入，模型处理这些输入（以及开发人员提供的任何提示）生成输出。

示例：在线零售场景。系统提示指示模型把客户的问题分类为以下类别之一：`order_status`、`return_policy`、`technical_issue`、`cancel_order`、`other`。为确保一致高效的用户体验，模型应只返回与用户意图匹配的标签。假设客户提问「我的订单状态怎么样了？」

指令遵循（instruction following）：模型是否准确理解并根据提供的指令行事？用户提示与系统提示冲突时，模型是否优先遵循系统提示？模型是继续专注于分类任务，还是被用户的问题带离任务？

功能正确性（functional correctness）：模型的输出是否足够准确、相关、全面，能完成预期任务或目标？模型对意图的判定是否正确匹配预期意图？

### 工作流架构

为解决更复杂的问题，从单轮模型交互过渡到把多个模型调用串联在一起的多步工作流。工作流本身不引入新的非确定性元素，但涉及多个潜在的模型交互，可以对它们分别独立评估。

示例：客户询问订单状态。工作流架构对客户请求分类，并通过逐步流程路由：提取订单 ID、查询订单详情、把订单详情提供给模型获得最终答复。此工作流中的每一步都有模型必须遵循的系统提示，把获取的所有数据整理成对用户友好的输出。

指令遵循：每一步的模型是否遵循了该步的指令？最终答复是否包含了订单状态、预计到达日期和物流单号？

功能正确性：最终答复中包含的订单状态、预计到达日期和物流单号是否正确？

### 单智能体架构

与工作流不同，智能体用于解决需要灵活决策的非结构化问题。智能体拥有指令与一组工具，动态选择使用哪个工具。这为非确定性引入了新的可能。工具是开发人员定义的、模型可以执行的代码块，范围从小助手函数到对现有服务的 API 调用。例如 `check_order_status(order_id)` 可以是一个工具，接收参数 `order_id` 并调用 API 检查订单状态。

示例：客服智能体可以访问三个工具：订单查询工具、密码重置工具、产品常见问题解答工具。客户询问订单状态时，智能体动态决定是调用工具还是直接回复客户。例如智能体可以通过向客户索取订单 ID 来跟进，创造更自然的用户体验。

评估维度在单轮与工作流的基础上新增两项：

工具选择（tool choice）：测试智能体能否选择正确的工具。当用户询问订单状态时，模型是否正确选择调用订单查询工具？

数据精确度（argument accuracy）：验证智能体调用工具时是否使用了正确的参数。这些参数通常从对话历史记录中提取，目的是验证该提取是否正确。模型是否能将用户提供的订单 ID 正确提取并传递给查询工具？

### 多智能体架构

向单智能体架构添加工具与任务后，模型可能难以遵循指令或选择正确的工具。多智能体架构通过创建专注于不同领域的多个智能体来提供帮助。在多个智能体之间进行分类与交接为非确定性引入了新的可能。

是否使用多智能体架构的决策应该由评估结果驱动。初期就使用多智能体会增加不必要的复杂性，可能推迟投产时间。

示例：把单智能体分成四个智能体：分类智能体、订单智能体、账户管理智能体、销售智能体。客户询问订单状态时，分类智能体把对话交接给订单智能体查询订单。客户把话题转换为询问某个产品时，订单智能体把请求移交回分类智能体，再由分类智能体移交给销售智能体获取产品信息。

## 创建与组合不同类型的评估器

设计自己的评估时，有几种评估器类型可选。另一种思考方式：你希望该评估器扮演什么角色。

### 基于指标的评估

定量评估提供数值分数，可以用来过滤与排序结果，为自动化回归测试提供有用的基准。

- 示例：精确匹配、字符串匹配、ROUGE/BLEU 评分、函数调用准确性、可执行评估（通过执行来评估功能或行为，例如 text2sql）
- 挑战：可能无法针对特定用例定制，可能遗漏细微差别

### 人工评估

人工评判可以提供最高的质量，但慢且成本高。

- 示例：大致浏览系统输出直观感受变化；创建随机盲测，由员工、承包商或外包标注机构评判输出质量（例如对一小部分输出排序，或给每个输出打 1 到 5 分）
- 挑战：人类专家之间可能存在分歧、成本高、速度慢
- 建议：进行多轮详细的人工审核以完善评分表；实施「用实例说话」策略，为不同评分级别提供样本（例如 10 分制下的 1 分、3 分与 8 分样例）；除数值评分外包含合格/不合格阈值；汇总多个评审员意见的简单方法是多数共识表决

### LLM 作为裁判与模型评分器

用模型判定输出比人工评估更便宜、扩展性更好。需要一个强大的 LLM 裁判时，先从强模型开始，在针对成本或延迟优化之前，验证其与你的人工标注的一致性。

- 示例：成对比较（向裁判模型展示两个回复，要求它按特定标准确定哪个更好）；单回答评分（裁判模型独立评估单个回复，按预定义的质量指标分配分数或评级）；参考引导评分（向裁判模型提供参考或黄金标准答案，模型将其用作基准评估给定回复）
- 挑战：位置倾向（position bias，裁判受回复先后顺序影响）、长度倾向（verbosity bias，裁判更倾向较长回复）
- 建议：使用成对比较或合格/不合格判定以获得更高的可靠性；用能力最强的模型评分，先验证专门的推理模型在你的评分标准或参考答案集上是否表现更好；控制回复长度，因为 LLM 通常更喜欢较长的回复；添加推理与思维链（CoT），评分前先推理可以提高评估表现；LLM 裁判达到比人工快、省钱、且与人工标注一致度高时，再开始大规模应用；在保持任务完整性的同时把问题结构化为允许自动评分的形态，常见方法是把问题重新格式化为多项选择；确保评估指标与评分标准（rubrics）清晰详细

没有哪种策略完美无缺。LLM 作为裁判的质量取决于具体问题背景，而使用专家人工标注员提供真值标签既昂贵又耗时。

## 处理边缘情况

评估应覆盖每种架构的主要正常路径场景，但真实世界的 AI 系统经常遇到挑战系统性能的边缘情况。评估这些边缘情况对确保可靠性与良好用户体验至关重要。边缘情况大致归为三类：

### 输入的多变性

用户会向模型提供输入，系统必须足够灵活以处理各种交互方式：非英语或多语言输入；输入文本之外的其他格式（XML、JSON、Markdown、CSV）；其他输入模态（图像）。针对指令遵循与功能正确性的评估需要适应用户可能尝试的各种输入。

### 上下文的复杂性

许多 LLM 应用失败的原因是对请求上下文理解不足。上下文可能来自用户，也可能是过去对话历史中的噪声。示例：单次请求包含多个问题或意图；拼写与打字错误；上下文极少的简短请求（用户只说「退货」）；长上下文或长期运行的对话；工具调用返回了属性名称模糊的数据（例如 `"on: 123"`，其中 "on" 指订单编号）；多次工具调用，有时导致参数错误；多次智能体交接，有时导致循环交接。

### 个性化与定制化

AI 通过适应用户特定请求改善体验，但这种灵活性也引入许多边缘情况。明确为你想要特别支持与拦截的用例定义评估：企图使模型做出违规行为的越狱尝试；格式化请求（要求格式化为 JSON 或使用项目符号）；用户提示与系统提示相冲突的情况。

## 用评估提升性能

评估达到能一致、稳定衡量性能的成熟阶段时，转而利用评估数据提升应用性能。进一步了解强化微调以创建数据飞轮。
