# Super-agent：把多会话协调从人手上移到系统层

## 笔记卡

- 现象：单任务的质量受模型能力限制，多任务的数量受人的注意力限制；一个人通常只能同时跟进 3 到 5 个活跃会话。原文列出五个模块构成支撑四个基础特征的基本框架：双层架构兼顾连续交互与高效并发、事件驱动实现主动响应、面向人的交互同时做到连续与高效、计算状态环境分离与 Watchdog 实现跨设备持久在线与异常自愈。
- 机制：中心层的活是接话、分派、记账，是全局序点（Sequence Point，所有任务的信息先汇总到这里、由它排定谁先谁后，避免各任务各自对外说话），不碰执行，可用小而快的模型；执行层一个任务一个 Worker，上下文隔离、各带完整工具。把「要不要分派」从提示词与模型当场判断，移到系统结构里固定下来。事件处理借计算机系统的 Fast Path / Slow Path：确定性规则快筛、模型慢判；上下文当缓存管（Inline/Spill + 局部性 Locality + 链式召回 Chain of Recall）。
- 解法：Router 常驻并维护全局上下文，只分派不执行；Worker 与 Thread 多对多订阅，后续事件直通、不再绕回 Router；Trigger 先过程序层策略再由语义层模型判断；长工具调用改异步 start()/stop() 的全双工；云端无状态容器跑循环、状态入库，端侧留不保存状态的轻量 daemon，整体支持 BYOM（Bring Your Own Machine，自带机器，把日常开发机或个人电脑接入云端 Agent）；独立 Watchdog（看门狗，主系统之外另开一个会话定时检查各任务有没有进展）由定时消息驱动构成外部控制回路。
- 钩子：主动性靠两级过滤与投机执行（「静默复现并修复」，无价值则不出声）；IM 渠道单次回复不超过 100 词、异步渠道信息密集；Router 批处理把上一轮推理期间积压的 Trigger 合并进下一次 LLM 调用、在 Prefill 阶段并行计算。
- 代价与边界：中性提示的单会话方案 p95 为 29.5 分钟，Super-agent 为 15.7 分钟；代价是 cache-read token 更高（去掉直通后总读缓存 token 由 2323 万升到 3177 万，约 +37%），用更多 token 换更短更稳的尾延迟；实验基于约 300 条消息、约 20 条工作请求、每种配置 5 次的合成负载，测的是调度不是编码质量；长期记忆、Router 水平切分、A2A 通信、端侧凭据与提示注入都未解决；公开原型是验证技术路线用的研究原型，不是正式产品。
- 上游：DeepSeek Harness 团队《Super-agent 设计探索：迈向更自主的 Agent 系统》(2026-10-31)、配套原型 dsh-superagent-prototype（MIT）。

## 详情

**本篇要解决的问题**：当模型已经能独立完成单个任务，为什么人并行推进多项工作时反而成为瓶颈，系统该怎么搭才能把这份协调成本接过去。

现有主流 Agent 以单个会话为基本单位，会话之间彼此独立。A 会话里得出的结论，B 会话里的它并不知道，只有人知道所有任务的全貌。用户并行推进多项工作时，必须手动切换并自己记住每条上下文。DeepSeek 团队的观察是一个人通常只能同时跟进 3 到 5 个活跃会话。于是有一句判断：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。即使通过命令行、MCP 或外部连接器扩展本地 Agent，仍会面临单会话同步阻塞、多任务上下文混乱，以及本地设备离线后任务停止等问题。人的注意力没有减轻，反而承担了本应由基础设施处理的协调工作。

Super-agent 的答案是把会话管理与上下文同步上移到系统层，由系统承担调度与执行，人专注于目标设定与结果验收。它归纳出四项基础特征：连续（跨渠道、跨会话保持同一个 Agent 的体感）、高效（并行多个复杂任务且不必等上一任务完成）、主动（持续观察环境事件、自行推进值得处理的事项，不需要介入时保持安静）、持久（始终在线、长期运行遇异常自动恢复）。

文章借用的都是计算机系统里的老办法：快慢路径、缓存、推测执行、计算存储分离、看门狗。它明确声明这是一篇面向工程实践的架构思路探讨，把经典工程思想搬到 Agent 系统，并不提出全新理论，也不是对现有产品功能的介绍。

### 两层架构：Router 分派，Worker 执行

只用一个会话，上下文最连贯，但一步一步跑吞吐上不去，不同任务的中间过程还会混在一起；每个事件开一个新会话，吞吐有了，任务之间又断了联系。系统在底层会话组织上面临连续性与吞吐量的根本权衡，解法是把「维护全局连续性」与「高并发执行」分到两个层级。文章顺带给出一个判断：让用户手动管理 Session，很大程度上是从底层 LLM API 延续下来的设计惯性；Session 应当是系统的实现细节，而不应是用户的认知负担。这层「双层」是逻辑上的职责划分，每层实现都不必局限于单个会话。

Router 是常驻的全局路由层，承接所有入口的人类交互，所有跨任务的信息与决策在这里汇总，充当全局的序点（Sequence Point，所有任务的信息先汇总到这里、由它排定谁先谁后）、协调点与记忆，自己不直接执行具体任务，甚至可以不配备 Bash 工具。它与常见 Agent Team 的区别在于：Agent Team 分解的是单个复杂任务内部的紧耦合步骤，Team Lead 要深入理解细节、高频协调，推理负载很重；Router 只处理任务之间的高层关联与分派。Router 的活比想象的简单，小而快的模型通常就够，真正吃力的活放在 Worker，才需要最强的模型。Router 不易成为瓶颈还有一个机制原因：上一轮推理期间到达的 Trigger 会积压、在下一轮一并处理形成批处理（Batching），Router 每步是长输入短输出，把多条 Trigger 合并进一次 LLM 调用会在 Prefill 阶段并行计算，单次请求耗时增长远慢于批大小增长。规模再扩大时，Router 内部也可多层过滤或水平切分（Sharding），代价是切分越细吞吐越高、分片间记忆与上下文连续性越低——在全局记忆问题解决前这个权衡始终存在。

Worker 层由具体执行的会话组成，彼此上下文隔离、挂载完整执行工具，在独立上下文里专注单一任务；由于直接决定任务结果与代码质量，通常配置能力最强的模型。Worker 不直接与人类交互，推理与工具调用不输出到外部信道，而是向 Router 汇报状态、由 Router 统一回复，避免多个会话各自响应造成混乱。同层 Worker 之间通常不直接通信：冲突多发生在同一个 Pull Request 这类共享工作环境里，只要它们都订阅了对应 Thread 就会收到相同事件通知，从而有机会自行发现并解决冲突，少数跨任务协同才由 Router 中转。Worker 内部对 Router 透明，可以再建 Subagent，也可以本身就是一个 Agent Team。

某个 Worker 接手一个 Thread 后，直接订阅它，Thread 与 Worker 是多对多关系：一个 Worker 可订阅多个相关 Thread，一个 Thread 也可被多个 Worker 订阅。后续评论与状态变化由程序作为 Fast Path 直接送给已订阅的 Worker，Router 作为 Slow Path 仍观测全部事件以掌握全局状态、只分派尚未被订阅的新事件；新事件超出当前任务范围时，Worker 可取消订阅或交回 Router 重新分派。去掉这条订阅直通后，任务完成时间与完整版基本一致（原文未给具体值），但单次实验中 Router 需要做出的决定增加了约 30%、总读缓存 token 从 2323 万升到 3177 万（约 +37%）。所以直通的价值是减轻 Router 负担，不是让任务更快。

### 事件驱动：输入从提示词换成环境事件

Agent 的主要输入不再只是人敲的 prompt，而是环境里的半结构化事件（Trigger）：群消息、邮件、日历提醒、代码评审评论、CI 运行结果。接入真实群聊后事件流呈现「高噪音、低触发率」特征，绝大多数消息不需要 Agent 介入；对每个事件都调用大模型从头判断，延迟与算力成本都难以承受。借计算机系统的 Fast Path / Slow Path 思想：把已明确且稳定的高频判断固化成确定性代码当低成本快路径，大模型推理当灵活但高成本的慢路径。两级过滤因此是程序层策略（按来源、群组范围、用户或机器人白名单做确定性准入，例如「仅响应明确请求」「作为候选」「直接忽略」）加语义层策略（通过准入的候选才交给 LLM，按提示词策略与上下文判断是否行动；语义层同时是面向人的自然语言扩展点，可随时开关或新增策略）。

上下文当缓存管。有限的窗口有两个操作：Inline 把近期很可能用到的信息直接内联进窗口、省去额外工具调用往返，Spill 把超出预算或低频的完整内容留在窗口外、只保留引用或摘要供按需读取。注入过多会挤占窗口、稀释注意力，过少又迫使模型反复读工具增加步数，原文的说法是浪费上下文窗口就是浪费模型的智能。结合局部性（Locality）思想分三步：从最少信息开始（只给当前对象的 ID 与内容摘要）；逐步 Inline 紧密关联对象（先附关联 ID，再附时空相邻内容，如正文前 50 字、IM 前后相邻与所回复消息、评审讨论的相邻评论）；超上限则 Spill（长内容设较小长度上限，截断保留续读入口，需要全文再调工具读）。系统为 Trigger、Thread、Worker Session 等对象赋唯一 ID 并在注入时内联关联 ID，底层构成一张引用图，模型可顺着引用关系逐跳展开，文章称之为链式召回（Chain of Recall）：从当前消息的 Thread 找到相关 Worker，再找到另一个 PR 的评审 Thread。它缓解的是 Router 在长程中丢失先前信息的问题。

主动性靠投机执行。结果是否会被采用尚不确定时，先在后台提前尝试，有价值再提交，没有就放弃。内部用户群配了一条「静默复现并修复」策略：有人反馈缺陷、即使没有被 @，Agent 先在后台复现、定位原因，确认问题存在且修法简单才提交 PR 交人验收，否则全程不出声。同一机制也可用于个人助手：收到会议邀请后先核对日程、整理资料、备好回复草稿。

### 全双工、存算分离与 Watchdog

经典的 ReAct 循环里，模型发起一次同步的 run() 工具调用后，循环会阻塞直到工具返回最终结果，期间会话无法响应任何新输入。文章把耗时的命令与子任务调用改为异步的 start() 和 stop()：模型调 start() 后立即收到「已启动（Started）」返回、循环不再等待，后台工具执行完成后系统把最终结果作为一条新事件消息投递进会话，模型也可据上下文调 stop() 主动终止执行过长的后台命令。前台对话响应与后台任务执行由此解耦，新输入在当前推理步结束后即被处理。不同渠道不同说法：IM 等即时通讯信道侧重低打扰，只在需要决策或验收时发通知、只问直接问题、给简短结论，验证过的一条硬性规定是单次回复不超过 100 词；GitHub、邮件、文档等异步信道侧重结构化、高信息密度，写 PR 时按项目规范补全问题背景、改动说明与验证结果。DeepSeek Harness 已实现这个异步机制，但尚未默认开启。

计算、状态、环境三者分离。本地 Agent 通常把推进 Agent Loop 的计算、需要持久保存的会话状态、代码仓库与本地工具链等执行环境绑在同一台设备上，电脑一休眠 Agent 就停。借计算机系统的存算分离思想分两步解耦：第一步把推进 Agent Loop 的计算放进云端无状态的弹性计算容器、Session 等持久化状态存入数据库，无状态容器可水平扩展、重启或替换，连续性由持久化存储保障；第二步把云端 Agent Loop 与重状态的执行环境解耦。模型工作所需上下文很大一部分要靠工具调用从代码仓库、本地文件、依赖服务等执行环境获取，广义的上下文也包含执行环境本身。两种常见思路是把环境搬上云（云端启沙箱、拉代码、重建同步，但真实环境常含未提交的本地修改、私有凭据、内网依赖、特定硬件或工具链，同步成本高且易遗漏），或要求用户放弃本地环境迁往云端（迁移成本过高）。既然难以复制的是环境本身，文章让 Agent Loop 留在云端、重状态执行环境留在原地，仅在端侧部署一个不保存会话状态的轻量 daemon，只负责执行命令与返回结果。

这一思路与 Anthropic 提出的「脑手分离」（Decoupling the brain from the hands）一致：都让 harness 保持无状态、把会话日志放在 harness 之外、通过统一接口按需接入执行环境。区别在于场景，那篇讲托管服务与按需创建的沙箱、客户 VPC 资源，这里首先要接入的是用户日常使用、可能间歇在线的个人机器，上面有未提交修改和本地凭据。因此该设计既支持 BYOM（Bring Your Own Machine，把日常开发机或个人电脑接入云端 Agent），也支持云端托管机器或按需创建的计算环境；一台设备重新上线后，云端 Agent 会自动触发并完成需要在该设备上执行的任务。

长期运行的故障里，更常见的是进程还活着、模型却陷进没有进展的循环或脱离目标，仅靠传统的进程存活探测或监控脚本不够。系统在主系统之外配置一个独立的 Watchdog Session，用定时消息驱动它构成外部控制回路：既处理接口报错、状态恢复失败等基础设施故障，遇到外部偶发故障则持续复查直至恢复正常；也用模型判断各个 Worker 是否有实质进展、方向是否脱离整体目标，发现异常及时介入修复。由于 Watchdog 本身也是具备完整工具能力的 Agent Session，维护者可以用自然语言向它询问故障原因，也可以让它在线修正主系统行为，例如增删提示词、调整触发规则。

### 实验数据与代价

作者强调这是初步实验，使用合成负载与简化环境，结果只作参考，测的是系统调度与协作能力，并不衡量单个任务的实际执行能力。设置是：约 300 条群聊与 GitHub CI 消息，其中约 20 条是真正的工作请求，编码工作用一个只消耗时间的工具模拟，每种设计跑 5 次。本节全部数字与设置出自[微信原文 7.1、7.2 节](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)，并以该页正文为准。

| 方案 | p50 完成时间 | p95 完成时间 | cache-read token |
| --- | --- | --- | --- |
| Super-agent | 12.4 分钟 | 15.7 分钟 | 2323 万 |
| 单会话 + Subagent，中性提示 | 正文未给 p50 | 29.5 分钟 | 正文未给 |

正文只给出上表四个可直接复核的数值，外加「去掉直通后单次实验中 Router 需要做出的决定增加约 30%、总读缓存 token 从 2323 万升至 3177 万（约 +37%），完成时间与完整版基本一致」。四种方案的逐项 p50/p95 与 token 对照出现在 7.1 节配图（累计完成曲线，5 次运行均值）里，正文不逐项列出；配图中可见其他方案的数值，本页不把它们写成正文事实，避免把配图读数当成一手结论。需要逐方案数字时以[微信原文 7.1 节](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)配图为准并单独标注口径。

中性提示下，单会话方案 5 次里模型一次都没有调用 Subagent，活全在主会话里干、不断被新消息打断；换成「优先交给 subagent」的提示后，模型在 5 次里有 4 次进行了委派，完成时间有所缩短但仍慢于 Super-agent，剩下 1 次它判断工作「很小」而自己执行，拉出一条长尾。作者的解读是：单会话要靠提示词和模型当场判断来决定要不要分派，双层架构通过让 Router 不直接执行具体工作、Worker 仅接收所订阅 Thread 的消息，在系统层面缓解了这一问题。代价是用更多 token 换更短更稳的尾延迟。

Router 单独压测（Router 调用真实模型、Worker 使用 Mock 模型）：Trigger 到达速率从每分钟约 1 条升到约 40 条，平均批大小从 1.0 升到 2.8，单次请求耗时只从 2.5 秒增到 3.9 秒，摊到每个决策上的推理时间从 6.4 秒降到 1.6 秒。原因是排队的 Trigger 被合并进下一次调用、在 Prefill 阶段并行计算。按团队当时的规模，结论是不需要急着切分 Router。

### 开放问题与产品边界

作者自己列出的未解问题按原文分四块。一是双层架构的扩展（8.1）：当前「单常驻 Router Session + 订阅直通 + Worker 间不直接通信」是工程简化，规模扩大后 Router 何时水平切分、粒度如何、同层 Worker 何时引入直接通信与何种协作拓扑都无定论；系统与模型的协同设计（Co-design，针对 Router 的事件判别、批量分派、上下文召回做专项训练）也值得探索；常驻 Router 配合链式召回主要解决近期任务检索，运行周期拉长到跨月后长程记忆成为主要瓶颈。二是脱离 Session 后的人机协作（8.2）：底层执行会话不再对应界面会话后，交互可能更多发生在领域特化界面（如直接在 GitHub Issue/PR 里工作），以聊天窗口为中心在一定程度上是路径依赖；模型能力过渡期内许多任务仍需人中途参与，如何让用户在后台执行中随时介入、接管或实时协同，同样待解。三是上下文边界与 A2A（8.3）：组织决定如何配备 Super-agent 时，实际是在划分上下文共享与隔离的边界——需共享的共用一个实例、需隔离的各配一个；一旦存在多个隔离实例，跨边界协作就是 Agent 间通信（A2A，不特指某个协议），在互不共享底层上下文、各自代表不同权限边界的前提下如何安全可靠协作仍需探索。四是安全与隐私（8.4）：事件驱动让 Agent 接触更多不可信输入，第 5 节的云端 Loop 加端侧 daemon 默认建立在云与端彼此受信任的前提上；一旦云端 Agent Loop 遭遇服务端入侵或提示词注入被攻破，其连接的全部端侧设备都面临被控制风险，即使云端未被攻破，端侧凭据只要能进入模型上下文就有泄露风险。作者的想法是设计一种「用凭证但看不到凭证」的机制，让 Agent 在完全不接触凭据本身的情况下使用它。

产品边界写在明处：[微信原文结语](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)写「本文的部分设计已在 dsh-superagent-prototype 中实现……该插件只是一种为了验证技术路线而提供的原型，并非 DeepSeek 的正式产品」。再往外一层的信息来自转载与仓库：[腾讯新闻](https://news.qq.com/rain/a/20261102A09L5900)转述该原型「经过公开发布所需的改编，与内部版本及长文中的完整实现不完全相同，部分设计尚未进入公开实现」，并说公开版「目前主要围绕 GitHub 仓库工作并可接入飞书」；[AIBase](https://news.aibase.com/zh/news/32001)提到开源 MIT 协议原型。Worker 以操作者本人身份执行命令、默认不逐条审批、建议隔离环境试用这几项见 [dsh-superagent-prototype 仓库](https://github.com/deepseek-ai/dsh-superagent-prototype) 的 README、LICENSE 与 docs，微信原文未展开。文章不是对 DeepSeek Harness 现有产品功能的介绍。

## 设计检查点

把这套思路用到自己的系统前，逐项确认：

| # | 检查项 | 依据 |
|---|--------|------|
| 1 | 中心层是否只分派不执行，能否用更小的模型 | Router 的活是接话、分派、记账，推理负担轻 |
| 2 | Worker 是否上下文隔离、一个任务一个 | 隔离避免不同任务的中间过程互相污染 |
| 3 | 后续事件是否直达已订阅的 Worker | 去掉直通后单次实验中 Router 决定增加约 30%、总读缓存 token 增加约 37% |
| 4 | 事件是否先过确定性规则再过模型 | 绝大多数群聊消息不需要调用模型 |
| 5 | 长工具调用是否异步、前台能否继续接指令 | 同步 ReAct 会让整个会话在工具执行期阻塞 |
| 6 | 主动性是否有「无价值不出声」的收敛策略 | 避免 Agent 过度介入、刷屏打扰 |
| 7 | 计算、状态、环境是否分离，设备离线能否续跑 | 本地三合一绑定时设备休眠即停 |
| 8 | 是否有独立 Watchdog 检测无进展循环与脱离目标 | 长期运行的故障多是「活着但没进展」 |
| 9 | 是否只用合成负载数据做参考、不写成功率结论 | 实验测调度，不测编码质量，团队自报 |

## 测试检查点

1. 来源核对：每条机制与数字都能回指本文 sources 的一手页面；二手转述只作发现线索。
2. 数字口径核对：完成时间用 p50/p95 分开、token 用 cache-read 口径、实验次数与消息量随数字一起出现，不与单任务质量结论混用。
3. 边界核对：原型与正式产品、内部版与公开版、已实现与未默认开启（异步 ReAct）分开表述，不把架构设想写成已交付功能。
4. 结果外推核对：合成负载只说明调度趋势，搬到真实业务前先问「预期缩短的尾延迟对不对得上本团队的消息密度与任务时长」；对不上时以本团队实测为准，不把文中 p50/p95 当承诺值。

## 机制与本质

Super-agent 的本质是把「多任务要不要并行、上下文怎么接、设备断了怎么办」从人的注意力与模型的临场判断，移到系统结构里固定下来：Router 负责连续、Worker 负责并行、Trigger 把 Agent 从等指令变成看环境、云端状态加外部 Watchdog 保证一直在线。衡量它的尺度也随之从「完成了多少任务」变成「让人额外付出了多少协调成本」。它借用的全是计算机系统的经典思想，具体实现方式会随技术演进，但背后的系统设计思路有更长期的参考价值。
