# Codex 最佳实践：把编码 agent 当长期队友配置（Best practices）

- 原文：https://developers.openai.com/codex/learn/best-practices
- 来源：OpenAI（Codex 官方文档）
- 发布：官方文档页，随 Codex 版本持续更新
- 译文说明：全文翻译，术语保留英文原词，代码块与命令保持英文原文。

如果您是 Codex 或编码 agent 的新手，本指南帮助您更快获得更好的结果。它涵盖让 Codex 在 [CLI](https://developers.openai.com/codex/cli)、[IDE 插件](https://developers.openai.com/codex/ide)和 [Codex 应用](https://developers.openai.com/codex/app)中更有效的核心习惯，包括提示词撰写、规划、验证、MCP、技能和自动化。

把 Codex 视为需要不断配置和优化的团队成员，这样效果最佳。

一种有用的思考方式是：从正确的任务上下文开始，使用 `AGENTS.md` 提供持久指导，配置 Codex 匹配工作流程，通过 MCP 连接外部系统，把重复工作转化为技能，并自动化稳定的工作流。

## 良好的第一步：上下文与提示词

即使提示词不够完美，Codex 也足够强大以发挥作用。您通常可以直接交付一个难题，无需过多设置，就能获得出色的结果。获取价值并不要求清晰的[提示词](https://developers.openai.com/codex/prompting)，但清晰的提示确实能提高结果的可靠性，特别是在大型代码库或高风险任务中。

在大型或复杂的仓库中工作时，最大的改进在于给 Codex 提供正确的任务上下文与清晰的任务结构。

一个好的默认做法是在提示词中包含四点：

**目标（Goal）：**想要更改或构建什么？

**上下文（Context）：**哪些文件、文件夹、文档、示例或错误对该任务重要？可以用 @ 提及特定文件作为上下文。

**约束（Constraints）：**Codex 应遵循哪些标准、架构、安全要求或规范？

**完成条件（Done when）：**任务完成前应满足什么条件？例如测试通过、行为发生变化或错误不再重现。

这帮助 Codex 保持在范围内，减少假设，并生成更容易评审的工作成果。

根据任务难度选择推理级别，并测试最适合工作流的设置。不同用户和任务在不同设置下表现最佳：

- 低级别：适用于更快速、范围界定明确的任务
- 中级或高级：适用于更复杂的变更或调试
- 超高级：适用于长时间、自主性高、推理密集型的任务

为了更快地提供上下文，尝试在 Codex 应用中使用语音听写，口述希望 Codex 完成的操作。

## 处理困难任务时先进行规划

任务复杂、模棱两可或难以描述清楚时，让 Codex 在开始编码前先规划。

几种方案有效：

**使用 Plan mode：**对大多数用户这是最简单且最有效的选择。Plan mode 让 Codex 收集上下文、提出澄清性问题，并在实施前制定更强的计划。用 `/plan` 或 Shift+Tab 切换。

**让 Codex 采访您：**只有粗略的想法但不知道如何描述清楚时，让 Codex 先向您提问。告诉它挑战您的假设，在写代码之前把模糊的想法转化为具体内容。

**使用 PLANS.md 模板：**更高级的工作流可以配置 Codex 遵循 `PLANS.md` 或执行计划模板，处理长周期或多步骤的工作。详见[执行计划指南](https://developers.openai.com/cookbook/articles/codex_exec_plans)。

## 使用 AGENTS.md 实现指导的可复用性

一旦某种提示模式奏效，下一步就是停止手动重复它。这就是 [AGENTS.md](https://developers.openai.com/codex/guides/agents-md) 发挥作用的地方。

把 `AGENTS.md` 视为 agent 的开放格式 README。它自动加载进上下文，是记录您和团队希望 Codex 在仓库中如何工作的最佳位置。

一个好的 `AGENTS.md` 涵盖：

- 仓库布局和重要目录
- 如何运行项目
- 构建、测试和 lint 命令
- 工程规范和 PR 期望
- 约束和禁令规则
- 完成的定义以及如何验证工作

CLI 中的 `/init` 斜杠命令在当前目录快速生成 `AGENTS.md`。这是很好的起点，但应编辑生成的结果，使其符合团队实际构建、测试、评审和交付代码的方式。

可以在不同级别创建 `AGENTS.md` 文件：位于 `~/.codex` 的全局文件（个人默认设置）、仓库级共享标准文件，以及子目录中更具体的本地规则文件。当前目录附近有更具体的文件时，该指导优先。

保持实用。一个简短、准确的 `AGENTS.md` 比充满模糊规则的长文件更有用。从基础开始，只在注意到重复错误后添加新规则。

`AGENTS.md` 开始变得太大时，保持主文件简洁，为规划、代码评审或架构等内容引用特定任务的 markdown 文件。

Codex 两次犯同样错误时，要求它做回顾并更新 `AGENTS.md`。指导保持实用并基于真实的摩擦。

## 配置 Codex 保持一致性

配置是让 Codex 在不同会话和界面中表现一致的主要方式之一。可以为模型选择、推理力度、沙箱模式、审批策略、profiles 和 MCP 设置定义默认值。

一个好的起始模式：

- 个人默认设置保留在 `~/.codex/config.toml`（设置 → 配置 → 从 Codex 应用打开 config.toml）
- 仓库特定行为保留在 `.codex/config.toml`
- 命令行覆盖只在一次性场景使用（使用 CLI 时）

[config.toml](https://developers.openai.com/codex/config-basic) 是定义持久喜好的地方，例如 MCP 服务器、profiles、多 agent 设置和功能标志。可以直接编辑，或让 Codex 为您更新。

Codex 自带操作系统级沙箱功能，有两个关键开关。approval mode 决定 Codex 何时请求运行命令的权限；sandbox mode 决定 Codex 能否在目录中读取或写入，以及 agent 能访问哪些文件。

编码 agent 新手从默认权限开始。默认保持严格的审批和沙箱设置，只在确定有需要时为受信任的仓库或特定工作流放宽。

注意 CLI、IDE 和 Codex 应用共享相同的配置层。在[配置示例](https://developers.openai.com/codex/config-sample)页面了解更多。

尽早为真实环境配置 Codex。许多质量问题实际上是配置问题，例如工作目录错误、缺少写入权限、模型默认设置错误，或缺少工具和连接器。

## 通过测试和评审提高可靠性

不要止步于要求 Codex 进行更改。接受之前，要求它在需要时创建测试、运行相关检查、确认结果并评审工作。

Codex 可以为您执行这个循环，前提是它知道什么是「好的」。该指导来自提示词或 `AGENTS.md`。

这可以包括：

- 为更改编写或更新测试
- 运行正确的测试套件
- 检查 lint、格式化或类型检查
- 确认最终行为符合请求
- 评审 diff 查找错误、回归或风险模式

在 Codex 应用中切换 diff 面板直接在本地[评审更改](https://developers.openai.com/codex/app/review)。点击特定行提供反馈，这些反馈作为上下文进入下一次 Codex 操作。

斜杠命令 `/review` 提供几种评审代码的方式：

- 针对基础分支进行 PR 风格的评审
- 评审未提交的更改
- 评审 commit
- 使用自定义评审说明

团队有 `code_review.md` 文件并在 `AGENTS.md` 中引用时，Codex 在评审过程中也遵循该指导。对希望在仓库和贡献者之间保持一致评审行为的团队，这是强大的模式。

Codex 不应该仅仅生成代码。在正确的指令下，它还可以帮助测试、检查和评审代码。

使用 GitHub Cloud 时，可以设置 Codex 为 PR[运行代码评审](https://developers.openai.com/codex/integrations/github)。在 OpenAI，Codex 评审 100% 的 PR。可以启用自动评审，或让 Codex 在被 @Codex 提及时被动评审。

## 使用 MCP 获取外部上下文

Codex 需要的上下文位于仓库之外时，使用 MCP。它让 Codex 连接到您已经在用的工具和系统，不必把实时信息持续复制粘贴进提示词。

[MCP（Model Context Protocol，模型上下文协议）](https://developers.openai.com/codex/mcp)是把 Codex 连接到外部工具和系统的开放标准。

以下情况使用 MCP：

- 所需的上下文位于仓库之外
- 数据频繁变化
- 希望用工具替代粘贴的说明
- 需要跨用户或项目可重复的集成

Codex 支持带 OAuth 的 STDIO 和流式 HTTP 服务器。

在 Codex 应用中前往「设置 → MCP 服务器」查看自定义和推荐的服务器。通常 Codex 能帮您安装所需的服务器，只需询问。也可以在 CLI 中用 `codex mcp add` 命令，通过名称、URL 和其他详细信息添加自定义服务器。

仅在工具能解锁真实工作流时才添加。不要一开始就连接您使用的每一个工具。从一两个明显能消除经常性手动操作的工具开始，然后扩展。

## 把可重复工作转化为技能

工作流变得可重复后，不要再依赖冗长的提示词或重复的来回沟通。使用[技能（Skill）](https://developers.openai.com/codex/skills)把指令封装在 `SKILL.md` 文件、上下文和 Codex 应一致应用的支撑逻辑中。技能在 CLI、IDE 插件和 Codex 应用中通用。

把每个技能限定为一项工作。从 2 到 3 个具体用例开始，定义清晰的输入和输出，并编写描述说明技能的作用与使用时机。包含用户实际会说的触发短语。

不要试图预先涵盖所有边界情况。从一个代表性任务开始做好它，然后把该工作流转化为技能并持续改进。仅在能提高可靠性时才包含脚本或其他资产。

经验法则：如果您持续重复相同的提示词或纠正相同的工作流，它就应该变成一项技能。

技能特别适用于以下重复性工作：

- 日志分类
- 起草发行说明
- 按照清单进行 PR 评审
- 迁移规划
- 遥测或事件摘要
- 标准调试流程

`$skill-creator` 技能是构建技能第一个版本的最佳起点。迭代过程中保持第一个版本在本地。准备好广泛分享时，把它打包为[插件](https://developers.openai.com/codex/plugins/build)。技能最重要的部分之一是描述：说明技能的作用以及何时使用。

个人技能存储在 `$HOME/.agents/skills`，共享的团队技能可以提交到仓库内的 `.agents/skills`。这对新队员入职特别有用。

## 使用自动化处理重复性工作

工作流稳定后，可以调度 Codex 在后台运行它。在 Codex 应用中，[自动化（automations）](https://developers.openai.com/codex/app/automations)让您为重复任务选择项目、提示词、频率和执行环境。

任务变得重复后，在 Codex 应用的「自动化」选项卡创建自动化任务。可以选择它在哪个项目中运行、运行的提示词（可以调用技能）以及运行频率。还可以选择自动化在专用的 git worktree 中运行还是在本地环境中运行。了解更多关于 [git worktree](https://developers.openai.com/codex/app/worktrees) 的信息。

好的候选包括：

- 总结最近的提交
- 扫描可能的错误
- 起草发行说明
- 检查 CI 失败
- 生成每日站会摘要
- 按计划运行可重复的分析工作流

一个有用的规则是：技能定义方法，自动化定义时间表。工作流仍需要大量指导时，先把它转化为技能。变得可预测后，自动化成为倍增器。

把自动化用于反思和维护，不仅仅是执行。评审最近的会话，总结重复的摩擦点，随时间推移改进提示词、说明或工作流设置。

## 通过会话控制组织长期工作

Codex 会话不仅是聊天历史。它们是随时间积累上下文、决策和行动的工作线程，管理好它们对质量影响很大。

Codex 应用 UI 让线程管理最简单，可以固定线程并创建 worktree。使用 CLI 时，这些[斜杠命令](https://developers.openai.com/codex/cli/slash-commands)特别有用：

- `/experimental`：切换实验性功能并添加到 `config.toml`
- `/resume`：恢复已保存的对话
- `/fork`：创建新线程同时保留原始记录
- `/compact`：线程变长且想要早期上下文的摘要版本时使用。Codex 会自动为您压缩对话
- `/agent`：并行运行多个 agent 并希望在活动 agent 线程之间切换时使用
- `/theme`：选择语法高亮主题
- `/apps`：在 Codex 中直接使用 ChatGPT 应用
- `/status`：检查当前会话状态

保持每个连贯工作单元一个线程。工作仍是同一个问题的一部分时，留在同一个线程通常更好，因为它保留了推理路径。只在工作的确分叉时使用 fork。

使用 Codex 的[子 agent（subagent）](https://developers.openai.com/codex/concepts/subagents)工作流把有限的工作从主线程中卸载。主 agent 专注于核心问题，探索、测试或分类等任务留给子 agent。

## 常见错误

初次使用 Codex 应避免的常见错误：

- 用持久规则使提示词过载；持久规则应放进 `AGENTS.md` 或技能中
- 不提供运行构建和测试命令的最佳详细信息，导致 agent 无法「看到」自己的工作
- 在多步骤和复杂任务上跳过规划环节
- 在理解工作流之前给予 Codex 对计算机的完全访问权限
- 不使用 git worktree，对相同文件运行活动线程
- 重复性任务手动操作尚不稳定时，就把它转化为自动化
- 把 Codex 视为必须逐步观看的对象；应与您自己的工作并行使用
- 每个项目使用一个线程；每个任务应使用一个线程。随时间推移导致上下文臃肿，降低结果质量
