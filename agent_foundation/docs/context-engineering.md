# 面向 AI agent 的高效上下文工程（Effective context engineering for AI agents）

- 原文：[Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)
- 来源：Anthropic Applied AI 团队
- 发布：2025-09-29
- 译文说明：全文翻译，术语保留英文原词；图片为原文插图，地址为原文 CDN 直链。

提示词工程在应用 AI 领域火了几年之后，一个新词开始占据中心：上下文工程（context engineering）。用语言模型构建产品，重点正在从「为提示词找到对的措辞」，转向回答一个更宽的问题：什么样的上下文配置，最可能让模型产生我们期望的行为？

上下文指从大语言模型（LLM）采样时携带的那组 token。工程问题在于：在 LLM 固有约束下优化这组 token 的效用，稳定达成期望结果。驾驭 LLM 往往需要「以上下文的方式思考」：考虑 LLM 在任一时刻可用的整体状态，以及这个状态可能引出哪些行为。

本文探讨这门正在成形的上下文工程技艺，并给出构建可控、高效 agent 的一个更精细的思维模型。

## 上下文工程与提示词工程的区别

在 Anthropic，我们把上下文工程视为提示词工程的自然演进。提示词工程指编写与组织 LLM 指令以取得最优结果的方法（概览与实用策略见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)）。上下文工程指在 LLM 推理期间策展并维护最优 token（信息）集合的策略总和，包括提示词之外一切可能进入上下文的信息。

LLM 工程的早期，提示词是 AI 工程工作的最大板块，因为日常聊天之外的多数用例都需要为单轮分类或文本生成任务优化提示词。顾名思义，提示词工程的核心是怎么写好提示词，尤其是系统提示词。随着我们转向构建更强、需要多轮推理与更长周期的 agent，就需要管理整个上下文状态（系统指令、工具、[Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等）的策略。

在循环里运行的 agent 会不断产生可能与下一轮推理相关的数据，这些信息必须循环地精炼。上下文工程是从那不断膨胀的可能信息宇宙里，策展出进入有限上下文窗口的内容的[艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)。

## 为什么上下文工程对构建强力 agent 至关重要

尽管 LLM 速度惊人、能处理的数据量越来越大，我们观察到它和人类一样，到了某个点会失焦或困惑。大海捞针式基准研究揭示了一个概念：[context rot（上下文腐化）](https://research.trychroma.com/context-rot)——上下文窗口里的 token 数量增加，模型从上下文中准确召回信息的能力随之下降。

有的模型衰减更平缓，但这个特性在所有模型上都会出现。因此，上下文必须被当作边际收益递减的有限资源来对待。和人类[工作记忆容量有限](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)一样，LLM 解析大量上下文时也在消耗一份「注意力预算」。每个新 token 都会消耗一部分预算，这让审慎策展 LLM 可用的 token 变得更加必要。

注意力稀缺源自 LLM 的架构约束。LLM 基于 [transformer 架构](https://arxiv.org/abs/1706.03762)，每个 token 都能[关注整个上下文里的其他所有 token](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)，n 个 token 产生 n² 对两两关系。

上下文越长，模型捕捉这些两两关系的能力被摊得越薄，上下文规模与注意力集中度之间形成天然张力。此外，模型的注意力模式来自训练数据分布，其中短序列通常远多于长序列，模型对跨越整个上下文的依赖关系经验更少、专用参数更少。

[位置编码插值](https://arxiv.org/pdf/2306.15595)这类技术让模型能处理更长序列，方式是把它适配回原本训练用的较小上下文，代价是 token 位置理解有所下降。这些因素造成的是性能坡度而非悬崖：模型在长上下文上依然强力，但信息检索与长程推理的精度可能低于短上下文上的表现。

这些现实意味着，想构建强力 agent，深思熟虑的上下文工程必不可少。

## 高效上下文的解剖

LLM 受限于有限的注意力预算，好的上下文工程就是寻找可能范围内最小的高信号 token 集合，使期望结果的概率最大化。说起来容易做起来难，下面把这则指导原则应用到上下文各组件上。

系统提示词应当极为清晰，用简单直接的语言，把观点放在对 agent 来说「合适的高度」。合适的高度是两种常见失败形态之间的适中区间。一个极端是工程师在提示词里写进复杂、易碎的硬编码逻辑来诱发精确的 agent 行为，这带来脆弱性，随时间推高维护复杂度。另一个极端是只给含糊的高层指引，没有给 LLM 关于期望输出的具体信号，或者错误地假设双方共享背景知识。最优高度取平衡：具体到足以有效引导行为，又留出弹性让模型凭强启发式自主行动。

![合适高度示意图](https://www-cdn.anthropic.com/images/4zrzovbb/website/0442fe138158e84ffce92bed1624dd09f37ac46f-2292x1288.png)

建议把提示词组织成边界清晰的分区（如 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 等），用 XML 标签或 Markdown 标题划分。随着模型能力增强，提示词的具体格式大概率越来越不重要。

无论系统提示词怎么组织，你都应该追求「完整描述期望行为的最小信息集」（注意最小不等于短：仍要先给足 agent 信息，确保它遵循期望行为）。最好先用可用的最强模型测试最小提示词在你任务上的表现，再根据初始测试发现的失败形态，补充清晰的指令与示例来改进。

工具让 agent 与环境交互，在工作中拉取新的上下文。工具定义了 agent 与其信息空间、行动空间之间的边界，因此工具必须促进效率：返回 token 高效的信息，并鼓励高效的 agent 行为。

在[为 AI agent 编写工具](writing-tools-for-agents.md)一文中，我们讨论过构建 LLM 容易理解、功能重叠最小的工具。与设计良好的代码库类似，工具应当自包含、对错误稳健、用途表述极为清晰。输入参数同样要描述性强、无歧义，并顺应模型的天然长处。

我们见过的最常见失败形态是膨胀的工具集：覆盖功能过多，或让「该用哪个工具」的决策点变得含糊。如果人类工程师都说不清某场景该用哪个工具，就不能指望 AI agent 做得更好。后文会讲到，为 agent 策展一个最小可用工具集，也让长期交互中的维护与上下文修剪更可靠。

提供示例（即 few-shot prompting）是众所周知的最佳实践，我们继续强烈推荐。不过团队常把一长串边界情况塞进提示词，试图穷举 LLM 在某个任务上应遵循的每条规则，这不推荐。应该策展一组多样的、典范的示例，有效呈现 agent 的期望行为。对 LLM 来说，示例就是「值一千字的图」。

贯穿上下文各组件（系统提示词、工具、示例、消息历史等）的总指导：保持上下文信息充足而紧凑。接下来看运行时动态取回上下文。

## 上下文取回与 agent 式搜索

在[构建高效 agent](building-effective-agents.md)中，我们强调了 LLM 工作流与 agent 的区别。自那以后，我们越来越认同 agent 的一个[简洁定义](https://simonwillison.net/2025/Sep/18/agents/)：LLM 在循环中自主使用工具。

与客户并肩工作的过程里，我们看到整个领域在向这个简单范式收敛。底层模型越强，agent 的自主度就能越高：更聪明的模型让 agent 能独立穿行细微复杂的问题空间并从错误中恢复。

工程师为 agent 设计上下文的思路也在转变。今天，许多 AI 原生应用采用某种基于 embedding 的「推理前检索」，把重要上下文预先呈现给 agent。随着领域转向更 agentic 的做法，越来越多团队在这类检索系统之上叠加「即时（just-in-time）」上下文策略。

「即时」做法的 agent 不预先处理全部相关数据，而是维护轻量标识符（文件路径、存储的查询、网页链接等），在运行时用工具按这些引用动态加载数据进上下文。Anthropic 的 agentic 编码方案 [Claude Code](https://www.anthropic.com/claude-code) 就用这个方法在大型数据库上做复杂分析：模型写精准的查询、存下结果、用 head 与 tail 这类命令分析海量数据，全程不把完整数据对象装进上下文。这个做法映照人类认知：我们一般不背下整个信息库，而是引入文件系统、收件箱、书签这类外部组织与索引系统，按需取回相关信息。

除存储效率外，这些引用的元数据还提供了高效精炼行为的机制，无论是显式提供还是凭直觉利用。对在文件系统里工作的 agent 来说，`tests` 目录下有个 `test_utils.py`，与 `src/core_logic/` 下有个同名文件，暗示的用途完全不同。目录层级、命名惯例、时间戳都提供重要信号，帮人类与 agent 理解该怎样、何时使用信息。

让 agent 自主导航与取回数据还带来渐进式披露：agent 通过探索逐步发现相关上下文。每次交互产生的上下文都在指导下一个决策：文件大小暗示复杂度，命名惯例提示用途，时间戳可以充当相关性代理。agent 能一层层组装出理解，工作记忆里只保留必要内容，并用记笔记的策略获得额外持久性。这种自管理的上下文窗口让 agent 聚焦相关子集，避免被详尽但可能无关的信息淹没。

当然有权衡：运行时探索比取回预计算的数据慢。不仅如此，还需要有主见、周到的工程设计，确保 LLM 拥有在信息版图里有效导航的工具与启发式。缺乏正确引导时，agent 可能滥用工具、钻进无出路的搜索路径、或认不出关键信息，浪费上下文。

某些场景下，最高效的 agent 会用混合策略：预先取回一部分数据换速度，再自行决定是否继续自主探索。「恰当」自主度的决策边界取决于任务。Claude Code 就是采用混合模型的 agent：[CLAUDE.md](http://claude.md) 文件预先直入上下文，glob 与 grep 这些原语让它按需即时导航环境与取回文件，有效绕开索引过期与复杂语法树的问题。

内容动态性较低的领域（如法律、金融工作）可能更适合混合策略。随着模型能力提升，agentic 设计将趋向让聪明的模型聪明地行动，人工策展逐步减少。以这个领域的进展速度，「做最简单可行的事」大概仍是给基于 Claude 构建 agent 的团队的最佳建议。

### 长周期任务的上下文工程

长周期任务要求 agent 在动作序列中保持连贯、上下文与目标导向，token 总量超过 LLM 上下文窗口。对持续几十分钟到几小时的任务（大型代码库迁移、全面研究项目），agent 需要专门技术来应对上下文窗口大小的限制。

等更大的上下文窗口看似是显而易见的对策。但在可预见的未来，任何尺寸的窗口都会受制于上下文污染与信息相关性问题，至少在追求最强 agent 表现场景下如此。为了让 agent 在更长周期上有效工作，我们发展了直接针对上下文污染约束的几种技术：compaction、结构化笔记、多 agent 架构。

#### Compaction（压缩）

Compaction 的做法是：对话接近上下文窗口上限时，总结其内容，用总结重启一个新上下文窗口。它通常是上下文工程里改善长期连贯性的第一根杠杆。核心是以高保真方式蒸馏上下文窗口的内容，让 agent 以最小的性能损失继续。

以 Claude Code 为例，我们把消息历史交给模型，让它总结并压缩最关键的细节。模型保留架构决策、未解决的 bug、实现细节，丢弃冗余的工具输出与消息。agent 带着压缩后的上下文加上最近访问的五个文件继续。用户获得连续性，无需操心上下文窗口限制。

Compaction 的艺术在于保留与丢弃的选择：过度激进的压缩会丢失微妙但关键的信息，它们的重要性可能后来才显现。实现压缩系统的工程师，建议在复杂的 agent 记录上仔细调提示词。先最大化召回，确保压缩提示词捕捉记录里每一块相关信息；再迭代提高精度，消除多余内容。

多余内容里最现成的一类是清理工具调用与结果：一个工具早已在消息历史深处被调用过，agent 为什么还需要再看一遍原始结果？工具结果清理是最安全、最轻的压缩形态之一，最近已作为[功能](https://www.anthropic.com/news/context-management)发布在 Claude Developer Platform 上。

#### 结构化笔记

结构化笔记（agentic memory）指 agent 定期把笔记写到上下文窗口之外的持久记忆里，之后再把笔记拉回上下文窗口。

这个策略以最小开销提供持久记忆。像 Claude Code 建待办清单，或者你的 agent 维护一个 NOTES.md 文件，这个简单模式让 agent 能跨复杂任务追踪进度，保住否则会在几十次工具调用间丢失的关键上下文与依赖。

[Claude playing Pokémon](https://www.twitch.tv/claudeplayspokemon) 展示了记忆如何改变 agent 在非编码领域的能力。agent 在几千个游戏步里维持精确计数，追踪这样的目标：「过去 1234 步我一直在 1 号道路练级，皮卡丘朝着 10 级的目标升了 8 级。」没有任何关于记忆结构的提示，它自己绘制已探索区域的地图、记住已解锁的关键成就、维护战斗策略笔记，帮助自己学习哪种攻击对不同对手最有效。

上下文重置后，agent 读取自己的笔记，继续几小时的练级或迷宫探索。这种跨越总结步骤的连贯性，让长周期策略成为可能，单靠把一切信息保存在 LLM 上下文窗口里做不到这一点。

作为 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude Developer Platform 公测了一个[memory tool](http://anthropic.com/news/context-management)，通过基于文件的系统更方便地在上下文窗口之外存取信息。agent 可以随时间积累知识库、跨会话维护项目状态、引用先前工作，而不必把一切都放在上下文里。

#### 子 agent 架构

子 agent 架构提供了绕开上下文限制的另一条路。与其让一个 agent 维护整个项目的状态，专门化的子 agent 可以带着干净的上下文窗口处理聚焦任务。主 agent 用高层规划协调，子 agent 执行深度技术工作或用工具找相关信息。每个子 agent 可能大量探索，消耗几万 token 甚至更多，但只回传工作成果的浓缩摘要（通常 1000-2000 token）。

这实现了清晰的关注点分离：详细搜索上下文隔离在子 agent 内部，主 agent 专注综合与分析结果。这个模式在[我们如何构建多 agent 研究系统](multi-agent-research.md)一文中有讨论，它在复杂研究任务上比单 agent 系统有显著提升。

这些技术的选择取决于任务特征。例如：

- compaction 为需要大量来回的任务保持对话流；
- 笔记适合有清晰里程碑的迭代开发；
- 多 agent 架构适合并行探索有回报的复杂研究与分析。

即便模型继续进步，如何在长交互中保持连贯，仍会是构建更高效 agent 的核心课题。

## 结论

上下文工程标志着我们构建 LLM 应用的根本转变。模型越来越强，挑战不再只是打磨完美提示词，而是审慎策展每一步进入模型有限注意力预算的信息。无论你在为长周期任务实现 compaction、设计省 token 的工具，还是让 agent 即时探索环境，指导原则不变：找到使期望结果概率最大化的最小高信号 token 集合。

我们列出的技术会随模型进步持续演进。已经能看到，更聪明的模型需要更少的指令式工程，agent 能以更高自主度运行。但即便能力增长，把上下文当作珍贵、有限的资源对待，仍会是构建可靠、高效 agent 的核心。

今天就在 Claude Developer Platform 上开始上下文工程，实用技巧与最佳实践见我们的 [memory and context management](https://platform.claude.com/cookbook/tool-use-memory-cookbook) cookbook。
