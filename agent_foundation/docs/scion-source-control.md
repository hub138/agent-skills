在 Anthropic，写代码已经不再是构建系统或开展研究的瓶颈。Claude 能够自主迭代研究循环、微优化复杂程序、以我们前所未见的速度与规模从零构建新服务。眼下的瓶颈，全部是为人类规模构建的开发者基础设施：源代码控制、构建与 CI。

2026 年 5 月，Anthropic 平均每天合入约 2,500 次代码变更；到 9 月，我们每天合入超过 30,000 次。我们预计这种增速不会很快放缓：合入代码的潜在需求几乎是无限的，每移除一个瓶颈，我们产出的代码量都会立即进一步上涨。

为了支撑这种增长，我们构建了自研版本控制系统 Scion，并在五个月内将整个 monorepo 从 git 完整迁移过来。同一时期我们还构建并交付了代码评审界面（名为 Antique）、代码搜索、一套完善的源代码控制 IAM 系统、管理与合入大量已评审代码的新机制，以及更多系统。本文重点讲我们具体如何构建 Scion。它构成一个有意思的案例研究：Claude 写代码的能力，既是最初把我们带进这个处境的原因，也是我们得以快速构建一个高质量、可扩展系统来应对它的手段。

## monorepo 的成长

在讲我们构建了什么之前，应当先承认我们的工作负载有多么特殊。不出意外，Anthropic 使用 Claude 写软件的强度远超几乎所有其他公司，所以我们往往最先看到为人类规模构建的工具开始吃力的地方。源代码控制只是其中一个例子。虽然我们不认为很多机构在很近的将来会遇到这些问题，但我们怀疑其他使用 AI 编码工具的团队不会等太久就会撞上同样的压力点，这正是我们想分享构建内容与所学经验的原因。

git 是一个去中心化系统：每个 clone 都是完整、自包含的仓库，可以在完全离线的状态下计算 diff、读取历史与 blame、检出任意版本。对绝大多数仓库来说，这是正确的设计，也是 git 成为标准的一大原因。

随着 monorepo 增长，它越来越不适合这个设计空间。仅主分支的历史就接近 100 GB，压缩后的工作副本超过 25 GB。不计开发环境、agent 沙箱与研究作业，我们每天为 CI 执行约 2,500 万次代码 checkout。按朴素方式全量拉取，每天会产生超过 600 PB 的 git 流量。

git 提供了处理仓库切片的工具，比如 shallow clone、sparse checkout 与 promisor remote。在此之外，大型 monorepo 还有一批标准变通手段，比如内部 git 镜像与保存在 blob 存储里的仓库快照（seeds）。这些我们全都用过：高峰期我们运行着几百个内部 git 镜像来应付负载。这为我们争取了时间，但随着合入率上升，它们越来越难运维：seeds 在两次刷新之间离 main 顶端越来越远；让依赖历史的操作（比如 diff 与 blame）在部分 clone 上继续正常工作，需要越来越小心。

![扩展 git checkout 吞吐的典型部署形态。](https://www-cdn.anthropic.com/images/4zrzovbb/website/ff019752973f6d83d2f6ba3bf56636aced3ea82c-3840x1238.png)

*图注：扩展 git checkout 吞吐的典型部署形态。*

退一步看，我们注意到：和大多数公司一样，我们把 git 当作带唯一权威副本的集中式系统在使用，但几乎所有的客户端都是天然在线的 agent 与作业。让 git 在分布式离线工作中表现出色的那些特性，正随着仓库增长持续损害我们的扩展能力。于是我们问自己：如果从设计之初就把 agent 永远在线这个事实纳入考量，源代码控制会是什么样子？

## agent 规模源代码控制的原则

在 agent 化编码中，许多关于软件开发方式的常见假定正在演变。构建 Scion 时我们拥抱了这些变化，这让我们能够在几条核心原则上采取与 git 根本不同的路线。超大 monorepo 的源代码控制有先行者，尤其是 Google 的 [Piper](https://en.wikipedia.org/wiki/Piper_(source_control_system)) 与 Meta 的 [Sapling](https://sapling-scm.com/)[2](#脚注)，我们是带着它们积累的教训来构建 Scion 的。我们的原则是：

**客户端永远在线。** git 假定客户端离线工作并需要一份完整的仓库副本。由于我们的客户端几乎全部是 agent 与作业，我们把 Scion 的客户端与协议设计成围绕一个永远可达的服务器，客户端在需要时才拉取数据。

**客户端与服务端不对称。** 在 git 中，每个客户端都有能力成为完整的服务端。在 Scion 中，服务端回答关于文件历史与 blame 的问题、创建提交、执行 merge 与 rebase 等。客户端维护一个有界的本地对象缓存，在磁盘上布置工作副本文件，监视文件系统变化，并为用户提供与服务端协作的顺畅界面。它自身能计算的东西很少，换来的是本地所需的数据量大幅减少。

**一个全面的源代码控制服务可以驱动许多新应用。** 用 git 时，一个需要向仓库提问的 CI 作业或工具（比如谁最后改了某一行、两个提交是什么关系）必须维护一份本地仓库副本，或者指望供应商专属的 API 能给出答案。用 Scion 时，客户端使用的全部源代码控制查询同样通过 API 暴露，所以很多情况下作业根本不需要本地仓库。许多内部工具（比如我们的自动化 bisect 与 revert 流水线）若没有这种廉价的、程序化的源代码控制访问，在大规模下根本无法实现。

**一切必须可水平扩展。** 高峰期我们运行几百个 git 镜像，这严重挤压了容量，仓库一旦超出镜像的磁盘或内存上限就再也扩展不动。在 Scion 中，仓库数据是分布式的，每个组件都可独立扩展；任何地方（包括服务端）都不存在完整物化的仓库副本。没有与 packfile（git 的对象压缩包）等价的东西，所以不需要仓库维护。

**提交必须廉价、增量、无锁。** 在 git 中，你在本地提交然后 push 分享工作。在 Scion 中，每次提交、rebase 或 merge 都发生在服务端，没有东西可 push，但每个操作都必须快。创建提交并更新其下游数据结构的成本必须随变更规模伸缩，不能随仓库总规模伸缩，否则服务端跟不上。Scion 的开发生命周期不鼓励使用 refs（指向提交的指针，比如分支与标签），只保留 main ref 与发布分支，因为每台服务器都必须达成一致的全局状态是一个逼近的扩展难题。

**工作副本是可选的，且默认按需稀疏。** 我们的 monorepo 非常大，每天又为 CI 检出代码几千万次，所以能免则免。用 Scion 时，一个需要某提交与其 merge base 之间 diff 的 CI 作业可以直接向服务端请求。写入也一样：许多写入负载同样可以跳过 checkout，完全通过 API 完成。Scion 的协议以 sparse checkout 为中心（只包含客户端请求的目录），配合 virtualized checkout（按需物化文件），所以当作业确实需要磁盘上的文件时，客户端只为它实际读取的部分付出代价。

## Scion 如何运作

理解这些原则在构建 Scion 时如何汇聚成实体很有帮助。这些洞察可以应用于其他源代码控制系统，或更广泛地应用于软件开发生命周期的其他环节。

### 数据结构

在 Scion 中，工作单元是 changeset，一条预写日志（write-ahead log）里的记录。一个 changeset 存储了你对 git 提交所期望的大部分内容。差别在于：git 提交存储指向 tree 的指针，changeset 存储相对其第一父提交[1](#脚注)变化的文件清单，外加指向 blob 存储中压缩文件内容的内容寻址指针。changeset 在服务端创建，即时随处可用。

![Scion 中 changeset 的结构形态。](https://www-cdn.anthropic.com/images/4zrzovbb/website/71c83868210b4b571abb068ea4cd76de749566b1-3840x2995.png)

*图注：Scion 中 changeset 的结构形态。*

这个结构让我们能以极高吞吐接受 changeset：没有 packfile 要接收、没有锁或跨服务器协调、没有 refs 要移动。Scion 技术上支持 refs，但由于创建和获取提交都与它无关，移动一个 ref 只是对单条 Spanner 行做一次 compare-and-swap，与创建 changeset 相互独立。

changeset 只记录变化了什么，所以它自身无法快速回答诸如谁最后编辑了某一行、哪些提交影响过某个文件的问题。为了回答这些，Scion 从 changeset 构建额外的数据结构，包括文件 blame 与路径历史的专用结构，以及提交图上的跳表。我们把所有不属于 changeset 直接组成部分的东西称为 derived data（派生数据），全部通过一套通用机制计算。每类派生数据都递归定义：某个 changeset 的值由它各父提交的值计算得出。

这个机制有三重收益。第一，当某种新数据结构能让某个操作更快时，我们可以轻松添加新的派生数据类型。第二，每类数据都可以选择即时计算或延迟计算，避免物化用不上的数据。第三，客户端永远看不到这些数据结构的内部，我们可以在不改客户端的前提下优化它们。随着系统成长，我们添加新派生数据类型的次数已经很多，比如用于复制检测或按路径搜索文件的新索引。

### 扩展 Scion

一小队 Scion 服务器为客户端可能需要的任何操作提供源代码控制 API，比如获取 changeset、计算 diff、寻找 merge base、拉取 blob。所有源代码控制数据都是内容寻址的，数据一经存储就永不改变，任何服务器都可以缓存它而无需与其他服务器核对。结果是服务器可水平扩展且几乎不需要协调。它们本质上是大型缓存，还能即时计算派生数据并把结果写回 Spanner。

Scion 的众多消费者不再需要维护自己的本地仓库。获取并维护仓库曾是 CI 作业或需要向源代码控制提问的工具的一项重要维护负担，尤其是关于提交祖先关系与 blame 的问题。迁移早期，在我们还没有自己的客户端、仓库格式与协议时，Scion 只回答这些「元数据」查询。获取文件内容与物化工作副本是数据密集得多的操作，需要专门的设计。

Scion 的 scn 客户端与 git 的 fetch 协议在几个重要方面走出了不同的路线，因而天然适配一种比 git 服务器所需 CPU 少得多的可扩展架构。Scion 的协商不告诉服务端客户端已有什么，只围绕客户端想要的 tree 与 blob 进行。从根 tree 出发，客户端检查本地存储里缺哪些 tree 并递归请求，随后对 blob 重复这个过程。每个请求针对的都是永不改变的特定对象，所以任何缓存都能应答，架构与传统分层缓存高度相似。这个过程高效且可续传，因为不存在单个数 GB 的 packfile 响应。sparse 乃至 virtualized checkout 不需要特殊支持，因为客户端根本不会请求它不想要的 tree。

在集群里，客户端通过 socket 与一个 daemon 通信，scion-daemon 为整个节点存储对象。我们的大多数节点都需要访问 monorepo，同一节点上的作业复用大部分相同对象。每个 daemon 从定期刷新的快照启动，然后只与所在区域的 tree 与 blob 缓存服务器（称为 scion-cache）通信。这些缓存服务器直接从内存中以 daemon 将消费的磁盘格式流式传输对象，所以它们不需要花时间计算客户端缺失的对象或执行增量压缩。缓存缺失某个对象时，它会向权威的 scion-server 请求，后者按需从 Spanner 或云存储读取。

scion-daemon、scion-cache 与 scion-server 对这个协议应答相同的 RPC，所以客户端不需要知道缓存拓扑。理论上任何一层都可以与任何其他层通信，但我们严格强制分层以隔离故障域。我们要避免这种情况：某个区域的 scion-cache 出故障，冲击上游 scion-server 并拖垮整个系统。

![Scion 的 checkout 架构。](https://www-cdn.anthropic.com/images/4zrzovbb/website/cba1eaaa67385fd00f210badaacd147de480120b-3840x1718.png)

*图注：Scion 的 checkout 架构。*

这个系统的每一层都维持超过 99% 的缓存命中率，且不需要长驻状态，所以需要时易于扩展。按 CPU 与内存需求计，我们的 Scion 基础设施占用现在比之前的 git 镜像基础设施小 200 倍。CI 与研究作业检出代码快两个数量级（秒级而非分钟级），在整个集群释放出可观的容量；仅 CI 一项就实现了 25% 的 CPU 容量收益。客户端与缓存都不需要执行仓库维护，这简化了我们作业的生命周期管理。

## 构建 Scion 学到的

我们开始构建 Scion 的时间，与 [Claude Mythos Preview](https://www.anthropic.com/claude/mythos) 和 [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag) 在内部可用的时间差不多。这两个发布既放大了对 Scion 的需求，也实质性地加快了我们构建它的速度。

有个特别惊人的例子。今年早些时候，我们第一版 git 到 Scion 的导入流水线大体是手写的原型。我们以为它不错，直到拿到 Claude Mythos Preview 的早期内部快照。我们让它重写整个东西，在没有任何进一步指令的情况下，它产出了一个内存占用低 20 倍、速度快 4 倍的版本，同时完整保留了围绕导入顺序与数据结构的全部隐含不变量。

![2026 年 1 月到 9 月，每周合入 Scion 与 Antique 代码库的变更数量。](https://www-cdn.anthropic.com/images/4zrzovbb/website/dd91296719203f38229824bb9bc9e9a61c76ed67-3840x2160.png)

*图注：2026 年 1 月至 9 月，每周合入 Scion 与 Antique 代码库的变更数量。*

构建与运维 Scion 的经历，为 agent 规模软件的可能形态提供了一些有意思的教训。

**小团队快速开发会越来越常见。** 一支七人团队同时构建了 Scion 和 Antique（我们的代码评审工具，单讲它就能再写一篇博客），更不必说半打相关系统，并在五个月内完成完整迁移。这一切发生在每天合入代码量增长 10 倍的同时。过去，开发并部署这样一套源代码控制系统要耗费一家公司数年的迭代迁移与多得多的工程师。我们认为这种快速灵活的迁移未来会越来越常见。

**工程师的价值没有降低，但工作内容在变。** 参与这个系统的所有工程师现在都会给 Claude 的写代码能力打出高于自己的评分。但我们的工程师仍然提供了对高层跨系统组件的理解与设计层面的权衡取舍，围绕要解决的问题与要达到的规模做出有依据的选择。我们经常发现，工程师的角色是对 Claude 说「不」。agent 有时为了满足一个本就不该被允许的模式而违反核心系统约束。这在我们的迁移中特别常见：比如有多个系统试图用线性读取提交日志的暴力方式查找一个变更何时合入 main，没有去问我们的代码评审工具。Anthropic 还大量使用对抗式评审，它在许多方面非常有效，但视角也可能短浅，所以熟练的工程师需要引导 Claude 远离针对假想问题进行的过度工程。比如有一次评审对信任另一个内部服务表现得过于保守，导致 Claude 添加了过量的校验与复杂度。团队成员仍然评审这个系统的每一个 change request，但如今审视的是变更的意图，逐行阅读代码的做法已经放下。

**我们得以大幅提升优化与质量。** 凭借 Claude 以远超我们自身的速度写出海量代码的能力，Scion 是我们工作过的测试最充分、防御最完善的代码库之一。即使在紧凑的时间表下，我们还是为遇到过的每一个非平凡的基础设施与源代码控制交互构建了封闭模拟（hermetic simulation），外加 fuzzing 与精细的限流。Claude 还顺手找到了重要的优化，比如一个我们某个索引漏掉的祖先查询算法优化，这类工作要专家花数天或数周的分析与调参，然后第二天它又来一遍。

![在原生 Scion 仓库上实测到的性能改进。](https://www-cdn.anthropic.com/images/4zrzovbb/website/c706fa6efb4b9e5cd2566cb080acbfce7218042d-3840x4684.png)

*图注：在原生 Scion 仓库上实测到的性能改进。*

**我们为 monorepo 安全的新形态打下了基础。** 在巨型 monorepo 里管理安全、防护与合规，与管理规模同等重要。我们从一开始就把这些放进 Scion 的设计。它支持仓库级的丰富访问控制，还能对单个目录施加权限，在不牺牲 monorepo 收益的前提下保护最敏感的代码。此外，我们构建的代码评审工具能表达复杂的语义审批约束，让我们把仅注释这类简单变更与敏感的逻辑变更区分开，人类评审者得以聚焦于后果最重要的变更。

**一种新水平的运维卓越成为可能。** 我们的团队大量使用 Claude Tag，用它监控系统各个组件。比如我们建了一批 Slack 频道，在每个频道里让 Claude 全神贯注于单个组件的健康。我们叫这些 Claude「superfans」。有 scion-daemon superfan、scion-cache superfan、Antique merge queue superfan 等等。它们可以访问我们的遥测与日志，表现得像一个手头没有别的事可做、只会刷新图表找异常的老练工程师。我们也有覆盖全部系统的传统告警，但 superfans 能捕捉到细微与新奇的问题，让这些告警相形之下只剩一个维度。

**我们正在彻底重审既有先验。** 这个项目促使我们认真审视其他为人类规模设计的工作流。比如，一个规范的 merge queue 在 agent 规模下已经没有多大意义。当成百上千个变更可以在测试运行期间合入时，CI 到底意味着什么？我们没能有效复制业界标准的 merge queue 全局仓库锁，转而投入了合入后与部署前的自动化测试。这确实意味着并发变更可能冲突，但 Claude 修复这些冲突的速度通常比人类发现它们还快。

## 贡献给更大的生态

我们把 Scion 视为对日益强大的 AI agent 引发的扩展问题的一个局部答案。我们分享这些细节，是作为一个团队如何应对类似挑战的实例，但我们并不预期自己的方案或考量适用于所有场景。

Scion 绝非适合通用场景的 git 替代品。我们概述的这些概念，只对真正巨大的 monorepo 才成立：要么有几万名工程师，要么有成群的 agent 高产写码。而且 Anthropic 有其特殊性：我们为内部用途消耗 token 的能力远超任何其他企业现实上愿意支付的规模。我们这么做既是为了满足自身软件开发需求，也是为了测试 Claude 的能力。

实际操作上，把 Scion 以广泛有用的形态提供给其他机构很困难。它与 git 差异太大，意味着公司要迁移开发生命周期的每一个环节，而且它需要自己的代码评审、代码搜索与 CI。这些组件的内部版本高度定制，其他机构很难采用；我们也担心构建一个试图取悦所有人的公开版本实际不会有用。

不过我们预计，这类问题在未来六到十二个月会变得越来越普遍，让每家用 git 的公司独自面对类似挑战是对工程资源的浪费。据此，我们认为影响最大的做法是分享我们的思考，让其他开发者把 Scion 中最成功的部分应用到 git 上，而不必背离 git 的整体模型。git 服务端不必与 git 客户端用同一种方式工作；提供显著扩展改进的新型服务端架构是存在的。git 平台可以提供像 Scion 那样全面的服务端 RPC，甚至可以跨代码托管平台标准化，让 git 客户端学会与之对话。协商协议也不必长得和今天一样，git 里各种 sparse 与 shallow 特性也可以被组织得更好。

最后，我们要感谢 git 社区在近二十年间为几百万开发者把这个平台扩展至今。我们的贡献要窄得多：分享我们对 agent 化软件开发与这些系统交互的早期观察，以便与 GitHub、GitLab 及开源社区合作，支持开发者不断变化的需求。当软件开发生命周期与 AI 指数曲线相交时，我们都在同一条船上。
