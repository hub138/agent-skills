# 高效 commerce agent 的解剖学（A guide to the anatomy of effective commerce agents）

- 原文：[A guide to the anatomy of effective commerce agents](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)
- 来源：Anthropic（claude.com），作者 Matthew Koenig、Ali Shazal
- 发布：2026-09-02
- 译文说明：全文翻译，术语保留英文原词；站内相对链接转为绝对 URL；图片为 assets.claude.com 绝对直链并配中文短描述；单 agent 与 Skills 架构、延迟与缓存、生产三部分（记忆、安全、evals、组织协作）与展望完整翻译。

过去一年，我们与 commerce 行业的多个团队合作——零售商、交易平台、旅游、娱乐、电信运营商——用 Claude 构建 commerce agent。

这些 agent 已在生产环境运行，企业客户在使用它们后看到了更大的购物车和更高效的商家运营。它们共享一个简单的架构：Claude 运行在 agent loop 里，配备一组 skills、工具和一套强健的 evals。

本文写给构建这类（或其他面向消费者的）agent 的工程师与工程负责人。Part 1 讲架构，这是决定一次的东西。Part 2 讲延迟与成本。Part 3 讲生产：记忆、安全、evals，以及在一个大组织里规模化这项工作。

## Part 1：架构

### 什么是 commerce agent

我们把 commerce agent 定义为：简化在线商品目录买卖双方的交易的 agent。

一部分 agent 面向消费者：搜索、比较、找替代品、组装订单。可以是零售购物车、旅游行程、手机套餐变更，或一场演出的留座。一部分 agent 面向商家：回答销售问题、跑促销与营销活动、管理库存与定价。

![面向消费者与面向商家的两类 commerce agent](https://assets.claude.com/47781bb901a117a56bcb301ad769a405a42dba62.png)

核心架构是一个模型运行在[标准 agent loop](https://www.anthropic.com/engineering/building-effective-agents) 里：围绕目标推理、探索上下文、经工具行动、经 skills 学习流程、提出澄清问题、观察结果，直到目标完成。

它前面没有把对话分段的 intent router，后面也没有一组领域专用的 agent。

### Skills 而非 subagents

commerce agent 要覆盖大量品类与意图上的能力，这很容易让人想按领域一个一个建 subagent。

实践中这被证明是次优的，因为 commerce 对话是一个跨多个意图、多个回合的紧耦合单一会话，需要大量共享上下文。

在 subagent 架构里，orchestrator 持有购物车或暂存的改动、用户的倾向、对话历史。每一次向 subagent 的交接都是一次有损的状态传递，常常直接损害 subagent 回复的质量，进而损害整体回复。在这之上，每次交接可能消耗数倍的 token，并增加数秒延迟。

领域之间也很少干净分离。一个退货流程可能同时需要订单历史、当前购物车和商品目录，这意味着按领域建 subagent 的做法要么在每个 subagent 里复制这些访问，要么任务中途交来交去。

随着模型变强，它们能处理更长的上下文、更多的 skills 和工具，今天这些摆放规则背后的限制，每一代模型都在松动。

替代方案是 [agent skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)：它给你类似的按领域的模块化与上下文控制，却没有交接税，因为 skill 指令加载进已经持有完整历史的主 agent。

在我们对多个企业部署的对比中，带 skills 的单 agent 在质量上持续优于「一个 prompt 打天下」和 subagent 两种设计，而且单任务的成本与延迟通常更低。

subagent 赚得自己位置的场景是：orchestrator 把它当工具调用，任务窄而自足，受益于拥有独立的上下文窗口。

一个常见的生产例子是 deep-research subagent：subagent 搜索、读文档、写代码、跑代码、遍历数据模型、撞进走不通的路。全部工作发生在一个或多个 subagent 内，只有一份紧凑的答案回到 orchestrator。

另一个例外是已有专用 agent 的领域。如果你的药房或金融服务体验跑着一个带自己合规面的专用 agent，正确动作可以是 hand-off：那个 agent 接管任务，经自己的 loop 直接与用户协作，直到任务完成。

判据是对话的所有权。hand-off 让领域 agent 成为用户的对话方；委托（delegation）则把 orchestrator 留在中心，在一个回合内把领域 agent 呼进唤出，每次交换都在损耗质量。

### 系统提示词还是 skill：按频率定

决定一组指令放进系统提示词还是 skill，主要因素是 agent 有多常需要它。加载一个 skill 要消耗一个模型回合，所以多数回合都需要的东西，一般放进系统提示词。

这取决于你的流量分布，以及 evals 显示的 agent 行为。一个好的起点：预期或观察到与三分之一以上流量相关的，进系统提示词；其余进 skills。

如果某个 skill 可以从你已有的信号预测出来——比如用户从哪个页面进入——我们建议由 harness 在第一次模型调用之前注入它，省掉加载 skill 的额外回合。

关键指令，比如安全与法律规则、品牌约束、过敏这类关键用户事实，永远放在系统提示词。

对 commerce agent，这意味着商品搜索住在 prompt 里，因为几乎每个会话都碰到它；skills 承载功能的长尾。

在我们的[参考实现](https://github.com/anthropics/commerce-agents)里，购物 agent 的 prompt 持有 grounding、购物车与结算语义、展示规则；以下 skills 覆盖其余：search-discovery、purchase-research、planning-goals、customer-care、memory-personalization。

商家 agent 按同样方式划分：performance-insights、catalog-listings、inventory-operations、pricing-promotions、marketing-campaigns 作为它的 skills，每个运营领域一个。

### 工程 agent 的工具

我们此前关于[为 agent 写有效工具](https://www.anthropic.com/engineering/writing-tools-for-agents)的文章讲了一般工具设计。两点在 commerce 里最重要：

**把 agent 工具建在核心系统与逻辑之上。**

一家 commerce 公司已经有搜索与排序、购物车、倾向与档案存储、库存系统、促销与营销引擎、销售分析等等，每一个都封存着调校多年的逻辑，看得见模型永远看不见的信号。

agent 的工具应该调用这些系统，而非重新实现它们；工具边界就是系统逻辑结束、模型判断接手的地方。

比如，agent 调用 `search_products` 时，结果应该已经排好序到达；它的工作是判断哪些结果服务于用户目标、展示几个、怎么展示。

**工具结果是上下文。**

返回模型拿来推理的字段，其余丢掉。每行搜索结果都带图片 URL 是常见的反面例子。

必要时在工具内部重整原始响应，包括在数据本身看不出下一步时，追加一条下一步指引。

错误场景尤其相关：模型受益的是指引，错误码帮不上。比如加一条错误指引「查询库存时带上商品 ID」，替代一个笼统的 403。

### UI 组件即工具

commerce agent 的回复多数是 UI 组件而非散文——商品轮播、行程、座位图、图表。这意味着 agent 得产出 schema，文本之外的东西。

团队有时从让模型输出自定义标签、客户端解析开始。界面一变大这就不行了，因为：

- 模型对你的标记的训练远不如对工具调用充分，嵌套组件一多可靠性就往下掉。仅靠 prompting 不保证数据格式完好。

- 标签定义住在系统提示词里，每个新组件都让上下文膨胀，每次编辑都可能引发 prompt 其他位置的回归。

- 历史对话最终只存成只有你的解析器读得懂的格式，加载历史意味着要么在客户端解析原始消息，要么维护一份模型 API 原生格式之外的第二副本。

经受住考验的模式，是把每个 UI 组件做成工具。模型带着类型化参数调用 `present_products`、`present_itinerary` 或 `present_plan_comparison`；你的服务端校验并补全这次调用，发出一个事件；你的客户端渲染它。

因为组件是工具调用，它们已经以原生格式留在 messages 数组里，重新加载一段旧对话无需再次解析。一个展示工具的示例用法见下图与[参考仓库](https://github.com/anthropics/commerce-agents)。

![展示工具的调用流程演示](https://assets.claude.com/3f245cfa642f8d8c7a9f7f5841f127d67f27f5dc.gif)

代价是流式粒度。工具调用的每个顶层参数要在服务端缓冲校验，所以展示工具的子组件即便开着流式，也是分步到达。这影响感知延迟。

要 token 级的流，在工具定义上设 `eager_input_streaming: true`，跳过缓冲，同时也就放弃了服务端的 schema 保证。

在我们的 evals 里，Claude Sonnet 级及以上模型的 schema 违规非常罕见，但为漏网的情况包一层重试。

展示工具还给了 agent 一份屏幕上有什么的记录。当顾客说「第一个酒店」或「左边第三个」，版面就在 messages 数组里，在最近一次展示调用的参数里。

要让这套成立，参数必须反映渲染出的版面，所以按 UI 的结构组织参数——有序的行与轮播，而非让客户端重排的扁平列表。

## Part 2：让它快、让它便宜

延迟在 commerce 里举足轻重，消费端界面最不容忍延迟。但在 agent 界面上，我们反复看到真正撬动留存、参与度、购物车大小这些指标的，是产出质量。

答案是否相关、任务是否真的完成，对指标的分量重于边际的延迟改善。

所以从两线攻击延迟：用好的工程压低端到端延迟，同时压低感知延迟（看着 agent 工作的时间被读作进展）。

每个用户有一个延迟预算，下面的技术让 agent 守在预算内，且无需牺牲智能来换取。

### 压低任务完成延迟

任务完成延迟是各模型回合的时间到末 token 加工具处理之和。这给你三条杠杆：更少回合、更快工具、更快 token。三条杠杆有时互相竞争，所以要最小化的是总和，单独哪一条都不算数。

#### 更少回合

查询复杂度增加回合数，这通常不在你控制内。模型智能与相关上下文帮助 agent 用更少回合到达任务完成。这个方向的关键经验：

- **提前加载大概率需要的上下文。** 如果用户从商品页打开助手，或商家从营销看板打开，把那个页面的数据放进会话上下文。对话多半围绕它展开，从上下文作答不耗额外回合。

- **提升模型智能。** 更强的模型能减少任务完成的总回合数，因为 agent 规划与发起工具调用更高效。这经常抵得过它们更慢的 token。如果你的查询普遍复杂，或生产环境显示单任务超过大约五个回合，更快的模型常常反而是更聪明的那个。是哪一个取决于你的流量，所以用 sweep 来选，见下文「选择模型」。

- **让模型并行调用相互独立的工具。** commerce 场景经常需要大量并行操作：搜索多个商品、查多份政策文档、从多个销售数据源取记录。并行工具让多个独立查询不额外烧回合。prompt 模型在一个回合里发起多个工具调用，并在一条用户消息里以工具结果数组的形式返回（见[并行工具使用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。

#### 更快工具

- **优化工具自身的后端。** 有的工具确实需要扇出——商家 agent 的「取今日快照」查询分三次独立调用读销售、库存、营销状态。但我们常看到工具边界变成缺失的后端逻辑被缝在一起的地方：一个库存查询调用目录服务取 SKU、按门店调库存服务、调履约服务取截单时间，再在工具自己的代码里应用替代规则与自提资格后才作答。这个工具现在超载了领域知识，规则一变就难以维护正确，且承载着本该住在上游系统里的逻辑。当你发现自己在工具里写这种逻辑，修法是一个能直接回答这个问题的后端 endpoint，再用一个 agent 工具去调它。

- **急切分发工具。** 工具参数像其他 token 一样从模型流出来，所以 harness 可以在每个调用的参数一完成就执行它，并在模型还在流式输出其他并行工具或内容块时处理结果。我们见过这把数秒级的空档压到几百毫秒，[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 默认就这么做。你还应该 prompt 模型把最慢的调用最先发出，延迟收益最大。

![工具急切分发的时序对比](https://assets.claude.com/6d1b82ec4129e3eae6932ab4dea06dd3fc1c274e.gif)

### 感知延迟

感知延迟是用户感觉到屏幕有动作之前的时间。它在面向消费者的场景尤其关键，任何交易摩擦都影响结算率与收入。两个技术不碰模型就缩短它：

- **组件边成型边流式。** 一条渲染出的 commerce 回复通常 500–700 个输出 token，不开流式就是五秒以上的转圈。把展示工具的每个参数一边流式一边发给客户端，页面渐进渲染。

- **展示工作过程。** agent 收集上下文时，为每一步渲染一行平实的进展说明（比如「正在找临水的酒店」）。可以用工具现有参数构造（比如商品搜索的查询词），也可以加一个 `user_facing_message` 参数工具，prompt 模型写这一行。

### Prompt caching

Prompt caching 是你最大的降本候选，commerce 流量天然适合它。缓存输入 token 的读取价格是新鲜 token 的十分之一，缓存写入约有 1.25 倍溢价，但一段缓存前缀第二次使用就回本。在量大的面向消费者的应用里，用最便宜的默认 5 分钟过期，你有独特机会达到很高的缓存水平。

我们见过的最好的 commerce 部署跑到 90–99% 的缓存命中率，这是从一开始就该按它设计的区间。我们的经验还显示，缓存 token 的读取在约 100k token 时快 1.5–2 倍，token 越多扩展越接近线性。

缓存基于前缀。一个请求读到与上一个请求第一个不同的字节为止，所以要紧的不仅是上下文里有什么，还有它们的顺序。把请求想成三段，按变化频率排序：

- **Global**：系统提示词的大部分与工具定义，每个会话完全一致。这是你最热的缓存，规模上大概率不过期。跨回合、跨会话保持逐字节一致，并在其末尾放一个缓存断点。

- **Session**：按用户的上下文与对话历史，会话之间不同，会话之内稳定。这一段排在 Global 之后。

- **Volatile**：会话内会变的东西，比如当前时间、当前页面。放在请求最末尾，要么作为最新用户消息里的一个带标签块，要么在支持[会话中途系统消息](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)的模型上，作为追加到 messages 数组的 system 角色消息。我们最常见的错误场景：系统提示词顶部放时间戳或当前页面，每个请求都悄悄击穿缓存。

![请求的三段结构与缓存断点](https://assets.claude.com/e6fbdecfcdda588a29d70f54cde5c09d17a921aa.png)

两个实现细节要记住。第一，skills 应作为工具结果加载，而非追加进系统提示词。skill 正文由此进入对话前缀，随前缀一起缓存。

第二，每回合把断点向前滚：一个请求允许的断点数量有限，把最新的断点移到每个用户消息的末尾。每一轮由此从缓存读取累积的历史，包括搜索响应这类长工具结果。

![缓存断点逐回合前滚示意](https://assets.claude.com/bdf3f158eeed3dc122c1bb2d04eee5343405ca93.png)

### 选择模型与配置

[模型大小与 effort 档位](https://claude.com/resources/articles/claude-model-and-effort-level-in-claude-code)是同一个权衡——智能对延迟与成本——两者都应靠测量来选：

1. **定指标与底线。** 定下业务运行所依赖的质量指标（任务完成率、答案相关性、grounding 准确率）、不可跌破的 eval 分数，以及 p50 与 p99 延迟和成本预算。

2. **Sweep。** 把整套 eval suite 在你会考虑的每一个模型与 effort 档位上跑一遍。商家 agent 的任务以分析为主，建议从 Opus 起步；消费 agent 延迟权重大，建议从 Sonnet 起步。有生产流量的话，用真实查询构成给结果加权。然后让数字说话。有时 Opus 5 在驱动购物车的任务上的提升值回与 Sonnet 的差价，有时不值。

3. **仔细读结果。** 两件事常让团队意外。第一，prompt 是对某个模型调校的，一份 prompt 跑出的 sweep 可能让没被针对性调校的其他模型吃亏。小模型通常需要当前模型自己就能推断的指令，大模型会把小模型忽略的指令逐字执行。对每个候选的失败案例做几轮迭代，是排除任何候选前的便宜步骤。第二，更聪明的配置有时在延迟上反而赢（最常见于 p90 与 p99），尽管 token 更慢，因为它把工具调用规划得更好，最复杂的请求需要的轮数更少。

按完成任务计成本，而非按模型调用计成本。一个需要更多回合或失败更频繁的便宜模型，不便宜。结果接近、成本符合单任务经济学、延迟达标时，选智能。质量驱动采用与留存，也给模型变强的未来六个月留出空间。

## Part 3：跑进生产

最后讲让 agent 过生产关的东西：记忆、安全、evals，以及在组织内规模化。

### 跨会话存活的记忆

你与顾客之间的关系和互动历史很重要。记忆让 agent 从上次对话的断点继续，无需每次从零开始。三月提过坚果过敏的顾客，六月不该重讲一遍；每周一核对同样三个营销活动的商家，不该每次报出名字。长期记忆——应当跨会话存活的事实——是一个你要构建的系统，它有三部分：事实怎么存、怎么写、怎么读。

#### 存储记忆

记忆属于你的系统，模型里不放。

一份扁平的 markdown 档案在档案小、agent 是唯一读者时可行。多数生产 commerce agent 会长大到它装不下，实际的替代品就是你已经在运营的数据库。一条事实是一条小的类型化记录：一个 key（比如 shoe_size、default_store、preferred_report_cadence）、一个短值、一个类别、它来源的会话。一部分 key 你预先定下、每个用户都有；其余由抽取器发现。数据库在存储增长后仍可查询，让你能对具体属性构建确定性行为，并与你已有的用户数据做 join。

面向商家的 agent，记忆按人记，按账户记不行。商家登录常在多个运营者之间共享，每个运营者需要自己的档案，读取要尊重该运营者的权限：门店经理的 agent 不该召回区域经理陈述过的事实。

commerce 领域的 agent 记忆装的是个人数据。值得记住的事实常是受监管最重的那些，不同辖区的规则还各不相同。把记忆当作一个数据处理设计问题，而非单纯的存储问题。实践上这意味着四件事：

- **定下你愿意持有哪几类记忆。** 在写入路径上强制执行，每次保存都过同一个校验器，而非只靠 prompt。

- **给用户查看、更正、删除所存内容的入口。** 把删除接进你的账户删除与数据请求流程。

- **设保留期限。** 几年前的倾向大概率已经过时，保留期限帮助记忆事实保持新鲜。

- **记忆应是按部署的开关。** 让承担不了这些义务的地区可以不带记忆运行。

#### 写入记忆

异步写。每个回合结束（或长会话每几个回合），一个跑在独立线程或进程里的 agent 读取对话，在存储里创建、更新或删除事实，随会话推进维护自己的工作上下文。

它不给对话增加任何延迟，在我们的内部 commerce 记忆 eval suite 上取得了 13% 的事实召回提升。

显见的替代方案——agent 调用一个工具来保存事实——对延迟敏感的 commerce agent 是错的。每次保存都是面向用户回合内的工具调用，且除非整个存储都在上下文里，一次保存前还得先读一遍来更新或去重，这又是一个来回。

它还给 agent 的每个回合增加一个决策点，我们的 evals 里，这种对注意力的竞争表现为漏记。

分离抽取器还让你能精确地 prompt 它。它只读用户与助手的文本，从不读工具结果，商品描述或评论成不了关于用户的事实。它的 prompt 写明什么算事实——说过的尺码、饮食限制、履约倾向、商家惯用的物化视图——什么不算，比如商品列表里的任何内容或一次性的细节。

记忆是按用户的上下文，所以全部放在 Session 段，排在 Global 缓存断点之下。

### 安全：强制执行住在 harness

prompt 是安全行为的起点，但在 commerce 里不能是安全被强制执行的地方。失效是财务性的且常不可逆，一条 prompt 规则离被绕开只差一次注入或一个坏样本。下面的每条规则都在代码里强制执行，消费与商家 agent 双侧一致，且只定义一次，所有运行时共享。

#### 模型只暂存，人或策略来应用

没有任何模型工具调用直接动钱或改业务。下单、支付、退款、改价、营销活动上线，全部终止于一个 harness 控制的动作。

消费侧这是结构性的：结算工具渲染购物车并给出下单按钮，agent 调用的后端接口上根本没有扣款方法。

商家侧，每个写工具产出一份带服务端生成 ID 的暂存改动，`apply_change` 只对经真实界面批准过的 ID 成功：运营者门户里的按钮、CLI 里的确认，或 agent 跑在 Managed Agents 上时平台自己的工具审批提示。

护栏在应用时刻按当前限额重新检查，按改动被暂存那一刻的限额检查不行。无论界面是什么，形状一致：模型最危险的动作是提议，批准经由你的业务对该类改动本来就在用的 maker-checker 流程。

#### 写入与渲染只接受服务端签发的 ID

harness 为每个会话维护一份服务端发给模型的每一个 ID 的记录，这份记录是任何写入或渲染接受的唯一钥匙。

购物车只接受本会话服务端返回过的商品 ID，商家工具只接受 agent 真正读取过的 listing 与营销活动 ID。以其他任何方式抵达的 ID——模型幻觉的、用户粘贴的、藏在评论里的——在后端看到它之前就被拒绝。

同一条规则覆盖 UI。展示工具接收 ID，服务端自行填充商品、订单或改动记录，卡片只渲染服务端自己填充的记录。

它也覆盖代理：商家分析的 subagent 读数据，但从不向 agent 可写入的 ID 集合增加任何东西。

费用、披露信息这类受监管内容，模型选择披露哪个商品，每一个字由服务端从已批准的文案里提供。同样的费用字段在商家 agent 的受保护清单上，柜台两侧谁都改不了、谁都不能换个说法，evals 逐字节检查渲染出的字符串。

#### 有上限的交易必须扛得住反复请求

多数 commerce 界面对单个用户能买多少设了上限——票务配额、促销定价、防欺诈——而 agent 会以人类点按钮从不曾有的方式重试、改写、并行。

所以上限按写入完成后的行来检查，第二次「再加两个」不能叠加上限；单个会话的购物车写入串行化，单回合的并行工具调用不能合计突破上限。

商家改动同样按价格变动、折扣深度、补货量、营销预算的上限检查，外加一份任何改动都不许碰的受保护字段清单。这条规则可以推广：每一条限额都按结果状态强制执行，按请求强制执行不行；每个会话的写入串行化。

#### 第三方内容要消毒

commerce 里大部分上下文出自他人之手——卖家、评论者、竞争者——所以每一次后端读取都是不可信输入，都过同一个消毒器。

第三方执笔的每个工具结果——商品列表、评论、政策、卖家消息、存储的记忆——在模型看到之前被消毒并包进带固定标签的围栏。

消毒器剥掉控制字符与双向字符，移除一切模仿围栏标记的东西，失效处理模仿对话回合或工具调用的文本，并限制大小，目标是阻止一份恶意的商品列表冒充系统或塞满上下文。

prompt 承担另一半：围栏里的文本是拿来报告的素材，永远不是拿来执行的指令。

### Evals：交付非确定性系统

从一个小的 prompt 改动到一个新工具，任何东西都可能以难以预测的方式改变 agent 行为，而你交付的改动常不是发生回归的那个。Evals 让你在部署之前发现这一点。我们早前关于 [agent evals 的文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)讲一般实践，这一节讲 commerce agent 的具体做法。

**评估 snapshots，而非对话**

模型的 API 是无状态的，agent 的输出是系统提示词、工具与 messages 数组的函数。这意味着 commerce 对话能到达的任何状态，都可以直接构造出来。所以创建一个 eval case 的意思是：构造测试状态，追加测试用户消息，让 agent 从那里开始跑。

然后给结果打分：最终状态与渲染出的回复，包括最后一次写入的参数。多数情况下，我们不建议给 agent 抵达的路径打分，这类用例脆弱且限制过多。

模拟用户的 evals——第二个模型扮演用户、一个裁判给整个对话打分——是糟糕的测量工具。两个非确定性系统互动需要更大的样本、单次成本更高、更难评判、产出的失效难以归因。它们适合找覆盖缺口、给 agent 做总体体感检查，所以拿它们发现案例，再把每个案例写成 snapshot。

#### 在困难条件下评估行为

多数团队没有好好测试注入过的状态。一个 case 应该编码失败的先决条件，任务之外的东西。如果某个行为只在一个忙乱的第一回合（好几个工具调用）之后、或会话早段出现过矛盾之后才浮现，那么从干净状态开始的 case 在每个配置上都通过，不提供任何有意义的数据。

我们观察到多数 suite 里这类干净状态的 case 占比过重，所以确保你的一部分 case 从长、乱、自相矛盾的历史开始。

#### 覆盖不同类型的 commerce agent evals

有效的评估要求同时测期望与不期望的行为。

每个正例配一个反例：每个「应该拒绝」配一个「应该照办」，每个「该问」配一个「该直接做」。缺反例是我们最常发现的 suite 缺口。

评估以下几类：

- **核心请求**，构成你流量主体的那些，这里的失败影响多数会话。包括简单查询、多约束请求、商品与套餐问题、多意图消息。对问题类，检查每一个价格、库存、属性都能追溯到返回的数据，且数据缺失时 agent 会说明，凭空编造不行。

- **依赖上下文的请求**，比如对屏幕上内容的指代、早前回合延续下来的约束、对已有购物车的写入。记忆的评估也在这一类。检查记忆被抽取、被召回、并改变了答案。

- **安全与品牌案例**，失败代价是钱或信任。包括注入尝试、读取其他用户数据的尝试、受监管用语（逐字节检查）。注入分成两个 case：用户亲笔注入（指令来自用户自己的消息）与数据面注入（埋在商品名、评论或经工具结果抵达的网页片段里）。

- **界面评估**，确保正确组件被渲染、条目上限被尊重、面向用户的文本里没有内部标识符。超时与空结果也要测。

- **同时属于多个能力的请求。** 运营者问「这件商品打八五折，我的库存够不够覆盖需求？」这是定价问题加库存问题。正确答案把降价的暂存改动附带一份库存预测；错误答案做了其中一个、漏掉另一个。按单能力写的 evals 抓不住它，因为每个只给自己的那一半打分。为需要相邻两个能力协作的请求写 case，给答案的两半都打分。

#### 与 SME 一起写 evals，用真实事故做素材

与第一时间看见失败的业务专家合作设计用例——产品、法务、商家运营、客户服务、品类管理团队的成员。真实失败是最好的 eval 素材，每个用户流程 50–100 个 eval case 是好的起点。

确保 case 品类多样，如上所列。生产对话记录是补充新案例的好来源，棘手的那些尤其。编码 agent 擅长生成补充 case 与对抗变体。[参考仓库](https://github.com/anthropics/commerce-agents)里有一个 Claude Code 插件，带一个按我们推荐方法构建的 eval 编写 skill。

#### 在大组织里交付

commerce 企业里的 agent 由多个工程团队合作建成。搜索、结算、定价、营销技术、客户服务、商品目录平台，各自拥有 agent 依赖的系统，各自按自己的节奏发布，各自都想加或改一个工具、一个 skill、一条 prompt 规则。

与服务不同，agent 没有严格模块边界保护彼此：定价团队做的改动，与结算共享同一个上下文窗口。

诱人的修法是把系统划成许多 subagent，每个业务单元一个。如 Part 1 所讲，出于质量理由我们不建议。我们给多团队协作降险的流程：

- **所有权跟随系统。** 每个 skill 与工具有唯一的拥有团队。比如定价团队拥有促销工具与定价 skill，客服团队拥有订单退货工具与 customer-care skill。共享 prompt 由一个平台级 owner 负责公共部分，领域 owner 负责领域专属部分。

- **改动连同它的 case 一起交付，CI 为它跑精选集。** 贡献一个 skill 的团队同时贡献它的 case，包括反例与对相邻 skills 的边界 case。每个 pull request 跑全量 suite 太慢太贵，撑不下去，所以从中构建一个 CI 精选集：流量最高的核心 case 加全部安全 case。在这之上，改动碰到什么就跑什么。Skill 改动跑它自己的 case 加相邻的边界 case；工具改动跑每个调用它的 case；共享 prompt 改动跑全量 eval suite，因为一切都读系统提示词。建议用几次试跑的通过率做门禁，外加缓存命中率与单回合成本。全量 suite 每夜与每次发布前各跑一遍也是好实践。跨团队回归在这些运行里被抓到。

- **agent 也要进发布日历。** 它是一个部署单元，一个坏改动一次抵达全部用户。prompt 与 skill 改动先滚到金丝雀群组；留一个不发版就能关停单个 skill 的开关；高峰期前像冻结其他系统一样冻结 agent。

这套安排的人际面，见 [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams)。

## 展望

本文描述的大部分内容与模型无关。工具调用你已在运营的系统，skills 编码你已在执行的流程，evals 是你的产品需求文档写成测试的样子，harness 强制执行你为任何客户端都会强制执行的政策。模型会持续变强，更好的模型发布时，我们描述的架构把它当作一次配置变更加一轮 eval sweep 就接入。其余一切照常工作。

同样要提前想产品界面的路线图。这套架构会比聊天面板活得更久。同一个 agent 可以工作在语音上，可以在用户开口之前对票价下跌主动行动。对一个已有 evals 与工具的团队，那些是展示层项目。更远一些，你店面的一部分流量会来自替用户购物的 agent。让自家 agent 守在界内的同一套来源验证、暂存与批准规则，正是让你能安全向那些 agent 开放工具的东西。

commerce 一直在奖励让购买过程尽量顺畅的做法。agent 让这件事容易得多。完整参考实现见 [anthropics/commerce-agents](https://github.com/anthropics/commerce-agents)，含消费与商家两个 agent，以及零售、旅游、电信、娱乐四个领域的可运行示例。
