# 我们如何构建多 agent 研究系统（How we built our multi-agent research system）

- 原文：[How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)
- 来源：Anthropic Engineering，作者 Jeremy Hadfield、Barry Zhang、Kenneth Lien、Florian Scholz、Jeremy Fox、Daniel Ford
- 发布：2025-06-13
- 译文说明：全文翻译，术语保留英文原词；图片为原文插图，地址为原文 CDN 直链。

Claude 现在具备 [Research 能力](https://www.anthropic.com/news/research)，可以搜索网页、Google Workspace 与任意集成，完成复杂任务。

这套多 agent 系统从原型走到生产的历程，教给我们关于系统架构、工具设计与提示词工程的关键一课。多 agent 系统由多个 agent（在循环中自主使用工具的 LLM）协作组成。我们的 Research 功能包含一个根据用户查询规划研究过程的主 agent，它用工具创建并行的子 agent 同时搜索信息。多 agent 带来了 agent 协调、评估与可靠性上的新挑战。

本文逐项给出对我们有效的原则，希望对你构建自己的多 agent 系统有用。

## 多 agent 系统的收益

研究工作面对的是开放性问题，所需的步骤极难提前预测。你无法为复杂主题的探索预先写好固定路径，这个过程本质上是动态的、路径依赖的。人类做研究时，会根据发现不断更新方法，追踪调查中涌现的线索。

这种不可预测性让 AI agent 特别适合研究任务。研究要求随调查展开而转向、探索侧向关联的灵活性。模型必须自主运行很多轮，根据中间发现决定追哪个方向。线性的一次性流水线处理不了这类任务。

搜索的本质是压缩：从浩瀚语料中蒸馏洞见。子 agent 通过各自独立的上下文窗口并行工作来促成压缩，同时探索问题的不同侧面，再把最重要的 token 浓缩后交给主研究 agent。每个子 agent 还提供关注点分离：独立的工具、提示词与探索轨迹。这降低路径依赖，支持彻底、独立的调查。

智力一旦跨过某个门槛，多 agent 系统就成为扩展性能的重要方式。例如，过去十万年里单个人类的智力在增长，而人类社会在信息时代的能力是指数级增长，靠的是集体智力与协调能力。即使是通用智能的 agent，单打独斗也有上限；一群 agent 能完成的事多得多。

我们的内部评估显示，多 agent 研究系统特别擅长宽度优先的查询，即同时追寻多个独立方向的任务。在内部研究评估上，以 Claude Opus 4 为主 agent、Claude Sonnet 4 为子 agent 的多 agent 系统，成绩比单 agent Claude Opus 4 高出 90.2%。例如，被要求找出标普 500 信息技术板块全部公司的董事会成员时，多 agent 系统把任务分解给子 agent 找到了正确答案，单 agent 系统则用缓慢的串行搜索失败了。

多 agent 系统有效的主要原因，是它帮任务花到足够的 token。我们的分析显示，三个因子共解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评估（测试浏览型 agent 定位难找信息的能力）95% 的成绩差异，其中 token 用量单独解释了 80%，另两个因子是工具调用次数与模型选择。这个发现验证了我们的架构：把工作分布到各有独立上下文窗口的多个 agent，为并行推理增添容量。最新的 Claude 模型是 token 使用效率的大型放大器：升级到 Claude Sonnet 4 带来的性能提升，超过把 Claude Sonnet 3.7 的 token 预算翻倍。对超出单 agent 上限的任务，多 agent 架构有效扩展了 token 使用量。

代价是这些架构烧 token 很快。我们的数据显示，agent 的 token 用量约为普通聊天的 4 倍，多 agent 系统约为聊天的 15 倍。要经济上可行，多 agent 系统适合的任务必须价值足够高，付得起性能提升的开销。此外，要求所有 agent 共享同一上下文、或 agent 之间依赖繁重的领域，目前不适合多 agent。例如，多数编码任务的真并行度低于研究任务，LLM agent 实时协调与委派其他 agent 的能力还不够好。我们的经验：多 agent 擅长的是高价值、重并行、信息量超出单个上下文窗口、需要与大量复杂工具交互的任务。

## Research 的架构概览

我们的 Research 系统采用编排者-工作者模式的多 agent 架构：主 agent 协调全程，把任务委派给并行运行的专门化子 agent。

![架构图](https://www-cdn.anthropic.com/images/4zrzovbb/website/1198befc0b33726c45692ac40f764022f4de1bf2-4584x2579.png)

用户提交查询后，主 agent 分析它、制定策略、派出子 agent 同时探索不同侧面。如上图所示，子 agent 充当智能过滤器，迭代使用搜索工具收集信息（这里是 2025 年的 AI agent 公司），然后把公司清单返回给主 agent，由它汇编最终答案。

传统 RAG（Retrieval Augmented Generation）用静态检索：取出与输入查询最相似的一批文本块，用它们生成回答。我们的架构用的是多步搜索：动态找到相关信息，适应新的发现，分析结果以组织高质量回答。

## 研究 agent 的提示词工程与评估

多 agent 系统与单 agent 系统有关键差异，协调复杂度增长尤其快。早期 agent 犯过这类错：为简单查询开出 50 个子 agent、无休止地搜网页上不存在的来源、用过量更新互相干扰。每个 agent 都由提示词驾驭，提示词工程是我们改进这些行为的主要杠杆。以下是我们学到的重要原则：

1. 像 agent 一样思考。迭代提示词必须理解提示词的效果。为此我们用 [Console](https://console.anthropic.com/) 搭了模拟环境，用系统里一模一样的提示词与工具，逐步观察 agent 工作。这立刻暴露出失败形态：结果已经够用还继续搜、搜索词过于冗长、选错工具。有效的提示词工程依赖对 agent 建立准确的心智模型，这让影响最大的改动一目了然。

2. 教会编排者怎么委派。我们的系统里，主 agent 把查询分解为子任务并描述给子 agent。每个子 agent 需要：目标、输出格式、该用什么工具与来源的指引、清晰的任务边界。缺少详细的任务描述时，agent 会重复劳动、留缺口、或找不到必要信息。我们最初允许主 agent 给「研究一下半导体短缺」这种简短指令，结果子 agent 常把任务理解错，或与其他 agent 做一模一样的搜索。例如，一个子 agent 在查 2021 年汽车芯片危机，另外两个却在重复调查 2025 年的供应链，分工失效。

3. 按查询复杂度分配投入。agent 不擅长判断不同任务该花多少力气，我们把分配规则写进提示词。简单事实查询只需 1 个 agent 3-10 次工具调用；直接对比类需要 2-4 个子 agent、各 10-15 次调用；复杂研究可能用 10 个以上职责划分清晰的子 agent。这些显式规则帮主 agent 高效分配资源，防止在简单查询上过度投入，那是我们早期版本的常见失败形态。

4. 工具设计与选择至关重要。agent 与工具的界面和人机界面同等关键。用对工具是效率问题，多数时候甚至是必要条件。例如，一个 agent 到网页上搜只存在于 Slack 里的上下文，从一开始就注定失败。接入 [MCP server](https://modelcontextprotocol.io/introduction) 后模型能访问外部工具，这个问题被放大：agent 会遇到没见过的工具，描述质量参差不齐。我们给 agent 明确的启发式：先查看全部可用工具，把工具用途对准用户意图，外部广泛探索用网页搜索，专门工具优先于通用工具。糟糕的工具描述会把 agent 引上完全错误的路，每个工具都需要独立用途与清晰描述。

5. 让 agent 改进自己。我们发现 Claude 4 系列模型可以是出色的提示词工程师。给它一段提示词与一个失败形态，它能诊断 agent 为什么失败并提出改进。我们甚至造了一个工具测试 agent：给它一个有缺陷的 MCP 工具，它尝试使用这个工具，然后改写工具描述来避免失败。通过几十次试用，这个 agent 找出了关键细节与 bug。这套改进工具合手度的流程，让后续 agent 使用新描述后任务完成时间下降 40%，因为它们避开了多数错误。

6. 先宽后窄。搜索策略应该像专家研究：先摸清版图，再钻进细节。agent 常默认用又长又具体、返回结果寥寥的查询。我们用提示词纠正这个倾向：先用短而宽的查询，评估有什么，再逐步收窄焦点。

7. 引导思考过程。[extended thinking 模式](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking)让 Claude 输出可见思考过程的额外 token，可以当作可控的草稿纸。主 agent 用思考来规划方法：评估哪些工具适合任务、判断查询复杂度与子 agent 数量、定义每个子 agent 的角色。我们的测试显示 extended thinking 改善了指令遵循、推理与效率。子 agent 也先规划，再在工具结果之后用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 评估质量、找缺口、精炼下一轮查询。这让子 agent 更能适应各种任务。

8. 并行工具调用改变速度与性能。复杂研究任务天然要探索很多来源。早期 agent 串行执行搜索，慢得难受。为提速我们引入两类并行：其一，主 agent 并行拉起 3-5 个子 agent，替代串行；其二，子 agent 并行使用 3 个以上工具。这些改动把复杂查询的研究时间最多压缩了 90%，让 Research 在几分钟而非几小时内完成更多工作，覆盖的信息也多于其他系统。

我们的提示词策略重在灌输好的启发式，避免僵硬规则。我们研究熟练的人类如何做研究，把这些策略写进提示词：把难题分解成小任务、仔细评估来源质量、根据新信息调整搜索方法、判断何时求深（详细调查一个主题）何时求广（并行探索多个主题）。我们还主动设置显式护栏，防止 agent 失控带来意外副作用。最后，把重心放在带可观测性与测试用例的快速迭代环上。

## agent 的有效评估

好的评估是构建可靠 AI 应用的基石，agent 也不例外。但评估多 agent 系统有独特挑战。传统评估常假设 AI 每次走同样的步骤：给定输入 X，系统应沿路径 Y 产出 Z。多 agent 系统不这样工作。即使起点相同，agent 也可能走完全不同但同样有效的路径到终点。一个 agent 搜三个来源，另一个搜十个，或用不同工具找到同一答案。既然我们并不总知道正确步骤是什么，通常无法只检查 agent 是否遵循了预先规定的「正确」步骤。需要的是灵活的评估方法：判断 agent 是否取得了正确结果，同时过程合理。

立即用小样本开始评估。agent 开发早期，改动的效果巨大，因为低垂的果实俯拾皆是。一次提示词调整可能把成功率从 30% 提到 80%。效果量这么大，几个测试用例就能看清改动的影响。我们从约 20 条代表真实使用模式的查询起步。测试这些查询常让我们清楚看到改动的效果。常听说 AI 开发团队因为「只有几百条用例的大型评估才有用」而推迟建评估，其实最好立刻用几条样本开始小规模测试，别等更全面的评估建成再说。

LLM 当裁判的评估方式做得好就能扩展。研究输出难以程序化评估：它们是自由文本，很少有唯一正确答案。LLM 天然适合给输出打分。我们用 LLM 裁判按评分标准逐项评估输出：事实准确性（论断是否与来源一致）、引用准确性（引用的来源是否支撑论断）、完整性（是否覆盖了要求的全部方面）、来源质量（是否用一手来源而非低质量二手来源）、工具效率（是否用对工具且次数合理）。我们试过多裁判分别评估各个维度，但发现单次 LLM 调用、单个提示词、输出 0.0-1.0 的分数加过/不过判定，与人类判断最一致。当评估用例确实有明确答案时，这个方法尤其有效，可以让 LLM 裁判直接检查答案是否正确（例如是否准确列出了研发预算前三的制药公司）。用 LLM 当裁判，我们能规模化评估数百条输出。

人类评估能抓住自动化漏掉的。人测试 agent 会发现评估漏掉的边界情况：奇怪查询上的幻觉回答、系统故障、细微的来源选择失误。我们的例子里，人类测试员注意到早期 agent 一贯选择做了 SEO 优化的内容农场，而放弃权威但排名较低的来源（学术 PDF、个人博客）。在提示词里加入来源质量启发式后这个问题得到缓解。即便在自动化评估的世界里，手动测试仍然关键。

多 agent 系统有涌现行为，它们未经专门编程就出现。例如，主 agent 的小改动会不可预测地改变子 agent 的行为。成功需要理解交互模式，只懂单个 agent 的行为不够。因此，给这类 agent 的最好提示词不只是严格的指令，更是协作框架：定义分工、解题方法与投入预算。做对这件事靠的是细致的提示词与工具设计、可靠的启发式、可观测性与紧密的反馈环。我们系统的示例提示词见 [Cookbook 里的开源提示词](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 生产可靠性与工程挑战

传统软件里，一个 bug 可能弄坏一个功能、拖慢性能或造成故障。agentic 系统里，小改动会级联成大行为变化，这给「为复杂 agent 写在长时进程中维护状态的代码」带来非凡难度。

agent 有状态，错误会复利。agent 能长时间运行，跨许多次工具调用维护状态。这意味着需要持久化执行代码，并在过程中处理错误。没有有效缓解，小的系统故障对 agent 可能是灾难性的。出错时不能只是从头重启：重启昂贵，也让用户恼火。我们建的是能从出错点恢复的系统。我们还借助模型智力优雅处理问题：例如，告知 agent 某个工具正在失败、让它自行适应，效果好得出奇。我们把 Claude agent 的适应性与确定性保障（重试逻辑、定期检查点）结合。

调试需要新方法。agent 做动态决策，即使提示词完全相同，两次运行也是非确定性的。这让调试更难。例如用户报告 agent「找不到显而易见的信息」，我们却看不出为什么。是搜索词糟糕？来源选择差？还是碰上工具故障？加上全量生产追踪后，我们能诊断 agent 为什么失败、系统性地修复问题。除标准可观测性外，我们还监控 agent 的决策模式与交互结构，全程不监控单个对话的内容，以保护用户隐私。这种高层可观测性帮我们定位根因、发现意外行为、修复常见故障。

部署需要谨慎协调。agent 系统是提示词、工具与执行逻辑织成的有状态网络，几乎持续运行。这意味着每次部署更新时，agent 可能处在流程中的任何位置。要防止善意的代码改动弄坏正在运行的 agent。无法同时把所有 agent 更新到新版本，我们用 [rainbow deployment](https://brandon.dimcheff.com/2018/02/rainbow-deploys-with-kubernetes/) 避免打断运行中的 agent：让新旧版本同时运行，流量逐步从旧移到新。

同步执行制造瓶颈。目前主 agent 同步执行子 agent，等每一批子 agent 完成才继续。这简化了协调，但造成 agent 间信息流的瓶颈。例如主 agent 无法在半途调整子 agent，子 agent 之间无法协调，整个系统可能卡在等一个子 agent 搜完。异步执行能带来更多并行：agent 同时工作，需要时再创建新子 agent。但异步给结果协调、状态一致性、跨子 agent 的错误传播都添了难题。随着模型能处理更长更复杂的研究任务，我们预期性能收益会抵过复杂度。

## 结论

构建 AI agent 时，最后一公里常成为旅程的大头。在开发者机器上跑得动的代码库，要变成可靠的生产系统需要大量工程。agentic 系统里错误会复利，对传统软件只是小问题的毛病，可能让 agent 整个脱轨。一步失败会让 agent 走上完全不同的轨迹，结果不可预测。出于本文讲的这些原因，原型与生产之间的鸿沟常比预期更宽。

尽管有这些挑战，多 agent 系统在开放性研究任务上已证明了自己的价值。用户说 Claude 帮他们找到了没想过的商业机会、理清了复杂的医疗选择、解决了棘手的技术 bug、靠发现他们独自找不到的研究关联省下最多几天的工作。靠谨慎的工程、全面的测试、细致入微的提示词与工具设计、稳健的运维实践，以及对当前 agent 能力有深刻理解的研究、产品、工程团队的紧密协作，多 agent 研究系统能在生产规模上可靠运行。我们已经在看到这些系统改变人们解决复杂问题的方式。

## 附录

以下是多 agent 系统的一些补充技巧。

多轮改动状态型 agent 的终态评估。评估在多轮对话里改动持久状态的 agent 有独特挑战。与只读的研究任务不同，每个动作都会改变后续步骤的环境，形成传统评估方法难以处理的依赖。我们的成功经验是聚焦终态评估，替代逐步分析：评估 agent 是否达到了正确的最终状态，而非它是否走了特定过程。这个方式承认 agent 可能找到通往同一目标的其他路径，同时仍然确保交付预期结果。复杂工作流可以把评估切成离散检查点，只验证特定状态变化应该发生的位置，避免试图验证每一个中间步骤。

长周期对话管理。生产 agent 常进行几百轮的对话，需要谨慎的上下文管理策略。对话拉长后，标准上下文窗口不敷使用，需要智能压缩与记忆机制。我们实现的模式：agent 在进入新任务前总结已完成的工作阶段，把关键信息存进外部记忆。接近上下文上限时，agent 可以开出带干净上下文的新子 agent，靠谨慎的交接保持连续性。此外，它们还能从记忆里取回研究计划等已存上下文，而不是撞到上下文上限就丢掉先前工作。这种分布式做法防止上下文溢出，同时在长交互里保住对话连贯性。

子 agent 产物写文件系统，减少传话游戏。某些类型的子 agent 产物可以直接绕过主协调者，同时改善保真度与性能。与其要求子 agent 把一切都通过主 agent 转述，可以建产物系统：专门 agent 创建独立持久化的产物。子 agent 调用工具把工作存进外部系统，然后只把轻量引用回传给协调者。这防止多阶段处理中的信息丢失，也减少把大产物在对话历史里复制来去的 token 开销。这个模式对结构化产物（代码、报告、数据可视化）尤其好用：子 agent 的专门提示词产出的结果，好于经通用协调者过滤一遍的结果。
