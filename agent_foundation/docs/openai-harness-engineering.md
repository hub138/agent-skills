# Harness 工程：在 agent 优先的世界用好 Codex（Harness engineering: leveraging Codex in an agent-first world）

- 原文：[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)
- 来源：OpenAI 工程博客
- 发布：2026-02-11
- 译文说明：全文翻译，术语保留英文原词，代码块逐行保留英文；openai.com 对脚本直连返回 403，正文经全文镜像站逐段核对。

过去五个月，我们的团队一直在做一个实验：构建并发布一个软件产品的内部 beta 版本，全程 0 行手写代码。

这个产品有内部日常用户，也有外部 alpha 测试者。它照常发布、部署、出故障、被修复。不同的地方在于：每一行代码——应用逻辑、测试、CI 配置、文档、可观测性、内部工具——全部由 Codex 写成。我们估计，整个构建只花了手工编写所需时间的约十分之一。

人类掌舵，agent 执行。

我们有意选择这个约束，为的是把「能把工程速度提升几个数量级」的必要东西都逼出来。我们要在几周内交付的，最终是一百万行代码的量级。要做到这一点，就必须弄清楚：当一个软件工程团队的主要工作从写代码，变成设计环境、明确意图、构建让 Codex agent 可靠干活的反馈回路时，什么会改变。

这篇文章讲的是我们用一个 agent 团队从零构建全新产品学到的东西：什么坏掉了、什么在复利增长、怎么把人类时间与注意力这项唯一真正稀缺的资源用到极致。

## 我们从一个空的 git 仓库开始

对空仓库的第一次 commit 在 2025 年 8 月末。

最初的脚手架——仓库结构、CI 配置、格式化规则、包管理器与应用框架——由 Codex CLI 用 GPT-5 生成，靠一小组现成模板引导。连指挥 agent 在这个仓库里怎么干活的 AGENTS.md 文件，最初也是 Codex 自己写的。

系统里没有既存的手写代码做锚点。从第一天起，这个仓库的形态就是 agent 塑造的。

五个月后，仓库的应用逻辑、基础设施、工具、文档与内部开发工具加起来约一百万行。这段时间里开出并合并了约 1,500 个 pull request，驱动 Codex 的只有三名工程师，折合人均每天 3.5 个 PR；团队后来扩到七人，吞吐量居然还在上升。重要的是，这些产出并非为了产出本身：产品在内部已有数百名用户使用，其中包括每天使用的内部重度用户。

整个开发过程中，人类从未直接贡献过任何代码。这成为团队的一条核心哲学：不写手写代码。

## 重新定义工程师的角色

没有人类动手写代码，反而引出了一种新的工程工作：围绕系统、脚手架与杠杆做工作。

早期进度比我们预期的慢，原因不在 Codex 的能力，而在于环境的规格不足。agent 缺少工具、抽象与内部结构，无法朝着高层目标推进。我们工程团队的主要工作，变成了让 agent 能做有用的事。

实际做法是按深度优先推进：把大目标分解成更小的构件（设计、编码、评审、测试等），提示 agent 构建这些构件，再用它们解锁更复杂的任务。某个环节失败时，修复方式几乎从来不是「再努力一点」。因为推进的唯一途径就是让 Codex 把活干出来，人类工程师每次都会走进任务里问：「缺的是什么能力？怎么把它做成 agent 可读又可强制执行的形式？」

人类与系统的交互几乎全部通过提示词完成：工程师描述任务、运行 agent、让它开 pull request。要把一个 PR 推到完成，我们指示 Codex 在本地先评审自己的改动，再在本地与云端申请额外的指定 agent 评审，回应人类或 agent 给出的反馈，循环迭代到所有 agent 评审方满意（这实际上是一个 [Ralph Wiggum Loop](https://ghuntley.com/loop/)）。Codex 直接使用我们的标准开发工具（gh、本地脚本、仓库内嵌的 skills）收集上下文，无需人类往 CLI 里复制粘贴。

人类可以评审 pull request，但没有硬性要求。随着时间推移，我们已把几乎全部评审工作推给了 agent 对 agent 的评审。

## 提升应用的可读性

代码吞吐量上来之后，瓶颈变成了人工 QA 的产能。既然固定约束是人类的时间与注意力，我们就持续给 agent 增加能力，方式是把应用 UI、日志、应用指标本身直接做成 Codex 可读的东西。

例如，我们把应用做成可以按 git worktree 启动，Codex 能为每次改动启动并驱动一个独立实例。我们再把 Chrome DevTools Protocol 接入 agent 运行环境，为 DOM 快照、截图与页面导航建了技能。这让 Codex 能直接复现 bug、验证修复、推理 UI 行为。

可观测性工具也照此办理。日志、指标与调用链通过一套本地观测设施暴露给 Codex，这套设施对每个 worktree 独立存在、用完即销毁。Codex 在应用的一个完全隔离版本上工作，包括该应用自己的日志与指标，任务完成后随之销毁。agent 可以用 LogQL 查日志、用 PromQL 查指标。有了这些上下文，「确保服务启动在 800ms 内完成」「这四条关键用户旅程里任何一个 span 不超过两秒」这类提示词就变得可以执行。

我们经常看到单次 Codex 运行在同一个任务上连续工作六小时以上（常常是在人类睡觉的时候）。

## 我们把仓库知识做成记录系统

上下文管理是让 agent 在大型复杂任务上有效的最大挑战之一。我们最早学到的教训很简单：给 Codex 一张地图，远胜一本一千页的操作手册。

我们试过「一个大 [AGENTS.md](https://agents.md/)」的路线。它以可以预见的方式失败了：

- **上下文是稀缺资源。** 一份巨型指令文件会挤占任务、代码与相关文档的空间，agent 要么漏掉关键约束，要么开始为错误的约束做优化。
- **过多的指导等于没有指导。** 当一切都「重要」时，就没有任何东西重要。agent 最终在局部做模式匹配，失去带着意图的导航。
- **它会迅速腐化。** 一本巨型手册会变成过时规则的坟场。agent 分辨不出哪些规则仍然成立，人类停止维护，这份文件悄悄变成一个诱人的麻烦。
- **它难以验证。** 单一大文件做不了机械化的检查（覆盖率、新鲜度、归属、交叉链接），漂移不可避免。

所以我们不把 `AGENTS.md` 当百科全书，把它当目录页。

仓库的知识库放在结构化的 `docs/` 目录里，作为记录系统（system of record）。一份短的 `AGENTS.md`（大约 100 行）注入上下文，主要充当地图，指向其他地方更深的事实来源。

```
 1  AGENTS.md
 2  ARCHITECTURE.md
 3  docs/
 4  ├── design-docs/
 5  │   ├── index.md
 6  │   ├── core-beliefs.md
 7  │   └── ...
 8  ├── exec-plans/
 9  │   ├── active/
10  │   ├── completed/
11  │   └── tech-debt-tracker.md
12  ├── generated/
13  │   └── db-schema.md
14  ├── product-specs/
15  │   ├── index.md
16  │   ├── new-user-onboarding.md
17  │   └── ...
18  ├── references/
19  │   ├── design-system-reference-llms.txt
20  │   ├── nixpacks-llms.txt
21  │   ├── uv-llms.txt
22  │   └── ...

24  ├── FRONTEND.md

26  ├── PRODUCT_SENSE.md
27  ├── QUALITY_SCORE.md
28  ├── RELIABILITY.md
29  └── SECURITY.md
```

仓库内知识库的目录布局。

设计文档有编目与索引，包含验证状态，以及一组定义 agent 优先运行原则的核心信念（core beliefs）。[架构文档](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)提供业务域与包分层的顶层地图。一份质量文档为每个产品域与架构层打分，跟踪缺口随时间的变化。

计划（plan）被当作一等工件。小改动用临时轻量计划，复杂工作写进[执行计划（execution plans）](https://cookbook.openai.com/articles/codex_exec_plans)，带进度日志与决策日志，一并提交进仓库。进行中的计划、已完成的计划与已知技术债全部版本化、放在一处，agent 因此可以在不依赖外部上下文的情况下运行。

这就实现了渐进式披露（progressive disclosure）：agent 从一个小而稳定的入口起步，被教会下一步去哪里找信息，免得一开始就被淹没。

我们用机制强制执行这一切。专用的 linter 与 CI 任务验证知识库是否最新、交叉链接是否有效、结构是否正确。一个定期运行的「文档园丁（doc-gardening）」agent 扫描那些不再反映真实代码行为的过时文档，开出修复性 pull request。

## agent 可读性是目标

随着代码库演进，Codex 的设计决策框架也需要跟着演进。

因为这个仓库完全由 agent 生成，它首先为 Codex 的可读性优化。就像团队会为新入职工程师改进代码的可导航性一样，我们人类工程师的目标，是让 agent 能直接从仓库本身推理出完整的业务领域。

从 agent 的视角看，任何它在运行时无法有效访问的东西都不存在。住在 Google Docs、聊天记录或人脑里的知识，系统访问不到。仓库本地、受版本控制的工件（代码、markdown、schema、可执行计划）才是它能看到的全部。

我们学到：需要把越来越多的上下文推进仓库里。那次让团队就架构模式达成一致的 Slack 讨论？只要 agent 发现不了它，它就是不可读的，就像三个月后入职的新人不知道它一样。

给 Codex 更多上下文，意味着组织并暴露对的信息让 agent 能在上面推理，避免用零散指令把它淹没。就像你会给新队友介绍产品原则、工程规范与团队文化（包括 emoji 使用习惯），把这些信息也给 agent，产出与团队的期望就更一致。

这个视角让很多取舍变得清晰。我们更青睐能被完全内化、能在仓库内推理的依赖与抽象。常被形容为「无聊」的技术，对 agent 来说通常更容易建模：可组合性好、API 稳定、在训练集里出现得多。某些情况下，让 agent 重新实现一小块功能，比绕开公共库不透明的上游行为更便宜。例如，我们没有引入通用的 `p-limit` 类包，而是实现了自己的 map-with-concurrency 辅助函数：它与我们的 OpenTelemetry 埋点紧密集成，有 100% 测试覆盖率，行为与我们运行时的预期完全一致。

把系统的更多部分变成 agent 可以直接检查、验证与修改的形态，会提升杠杆——受益的不仅有 Codex，还有在这个代码库上工作的其他 agent（例如 [Aardvark](https://openai.com/index/introducing-aardvark/)）。

## 用机制守住架构与品味

光靠文档，守不住一个完全由 agent 生成的代码库的一致性。我们的做法是强制不变量，避免对实现方式做微观管理，agent 因此能快速交付，同时不伤根基。例如，我们要求 Codex [在边界处解析数据形状](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)，但不规定具体怎么做（模型似乎喜欢 Zod，但我们没有指定这个库）。

agent 在[边界严格、结构可预期](https://bits.logic.inc/p/ai-is-forcing-us-to-write-good-code)的环境里最有效，所以我们把应用建在一个刚性的架构模型上。每个业务域划分为一组固定分层，依赖方向严格验证，只允许有限的一组边。这些约束由自定义 linter（当然是 Codex 生成的）与结构性测试机械化强制执行。

下图展示这条规则：在每个业务域（例如 App Settings）内部，代码只能沿固定分层「向前」依赖（Types → Config → Repo → Service → Runtime → UI）。横切关注点（auth、connectors、telemetry、feature flags）通过单一显式接口 Providers 进入。其余一律禁止，并由机制强制执行。

这类架构通常要等到团队有几百名工程师时才会建立。在编码 agent 的世界里，它是早期的前提条件：正是这些约束，让速度可以不伴随腐化与架构漂移。

实践中，我们用自定义 linter 与结构性测试执行这些规则，外加一小组「品味不变量」。例如用自定义 lint 静态强制结构化日志、schema 与类型的命名规范、文件大小上限、平台特定的可靠性要求。因为 lint 是自定义的，我们把修复指引写进报错信息，注入 agent 的上下文。

在人类优先的工作流里，这些规则可能显得迂腐或束缚。换成 agent，它们变成放大器：一旦编码，立刻处处生效。

同时，我们对「约束在哪里重要、在哪里不重要」保持明确。这类似领导一个大型工程平台组织：边界由中心统一强制，边界之内允许自主。你深切在乎边界、正确性与可复现性；在这些边界之内，你允许团队——或 agent——在解决方案的表达方式上拥有充分自由。

产出的代码未必总符合人类的风格喜好，这没问题。只要输出正确、可维护、对未来 agent 运行可读，就达到了标准。

人类品味持续回流进系统。评审意见、重构 pull request、面向用户的 bug，被沉淀为文档更新，或直接编码进工具。当文档不够用时，我们就把规则提升为代码。

## 吞吐量改变合并哲学

Codex 吞吐量上升后，许多常规工程规范开始起反作用。

仓库运行时几乎不设阻塞式合并闸门。pull request 生命周期很短。测试偶发失败通常用后续重跑处理，避免无限期阻塞进度。在一个 agent 吞吐量远超人类注意力的系统里，修正很便宜，等待很昂贵。

在低吞吐量环境里，这样做是不负责任的。在这里，它往往是正确的取舍。

## 「agent 生成」到底指什么

当我们说这个代码库由 Codex agent 生成，指的是代码库里的一切。

agent 产出的包括：

- 产品代码与测试
- CI 配置与发布工具
- 内部开发工具
- 文档与设计历史
- 评测 harness
- 评审意见与回应
- 管理仓库自身的脚本
- 生产仪表盘定义文件

人类始终在环里，只是工作在比过去更高的抽象层级。我们排定工作优先级、把用户反馈翻译成验收标准、验证结果。当 agent 陷入挣扎，我们把它当作信号：找出缺什么——工具、护栏、文档——再回流进仓库，而且始终由 Codex 自己来写修复。

agent 直接使用我们的标准开发工具。它们拉取评审反馈、内联回应、推送更新，常常自己 squash 并合并自己的 pull request。

## 自主性逐级提升

随着开发循环的更多环节——测试、验证、评审、反馈处理、恢复——被直接编码进系统，这个仓库最近跨过了一个有意义的门槛：Codex 可以端到端驱动一个新特性。

给一条提示词，agent 现在可以：

- 验证代码库当前状态
- 复现一个上报的 bug
- 录制视频演示故障
- 实现修复
- 驱动应用验证修复
- 录制第二段视频演示问题已解决
- 开出 pull request
- 回应 agent 与人类的反馈
- 检测并修复构建失败
- 只在需要判断时才升级给人
- 合并改动

这一行为严重依赖本仓库特定的结构与工具投入，不能想当然地认为它可以直接推广——至少现在还不能。

## 熵与垃圾回收

完全的 agent 自治也带来新问题。Codex 会复制仓库里已有的模式，包括不均匀或欠优的模式。时间一长，这必然导致漂移。

一开始，人类手动处理。我们团队过去每个星期五花 20% 的时间清理「AI 垃圾」。不出所料，这个做法扩不起来。

我们改为把「黄金原则（golden principles）」直接编码进仓库，并建了定期清理流程。这些原则是一组有主见、可机械执行的规则，让代码库对未来 agent 运行保持可读与一致。例如：(1) 优先用共享工具包，避免手写零散辅助函数，让不变量集中；(2) 不「YOLO 式」探测数据——我们要么在边界验证，要么依赖有类型的 SDK，agent 就无法在猜测出的数据形状上继续搭建。按固定节奏，一组后台 Codex 任务扫描与黄金原则不一致的地方、更新质量评分、开出针对性的重构 pull request。这些 PR 大多一分钟内可评审完并自动合并。

这就像垃圾回收。技术债像一笔高息贷款：持续小额偿还，几乎总是好过让它利滚利、再痛苦地一次性清算。人类品味被捕获一次，随后在每一行代码上持续强制执行。这让我们能按天为单位抓住并解决坏模式，避免它们在代码库里扩散几天或几周。

## 我们仍在探索的问题

到 OpenAI 内部发布与采纳为止，这套策略运转良好。为真实用户构建真实产品，帮助我们把投入锚定在现实上，引向长期可维护性。

我们还不知道：在一个完全由 agent 生成的系统里，架构一致性如何跨年度演进；人类判断在哪里杠杆最大、怎么编码才能复利；随着模型持续变强，这套系统会如何演变。

有一点已经清晰：构建软件仍然需要纪律，只是纪律更多体现在脚手架上，而非代码本身。维持代码库一致性的工具、抽象与反馈回路，正变得越来越重要。

我们当前最困难的挑战，集中在设计环境、反馈回路与控制系统上，帮助 agent 达成我们的目标：规模化地构建并维护复杂、可靠的软件。

随着 Codex 这类 agent 承担软件生命周期的更多环节，这些问题只会更重要。希望这些早期教训能帮助你判断该把精力投在哪里，[放手去构建](https://openai.com/codex/)。
