# 通用 Agent 能力指南

> 配套代码：本包 `src/agent_foundation/`，每个模块可独立使用；文中「→ 模块」指向参考实现。前提：Python ≥ 3.10，零运行时依赖（纯标准库），仓库内 `pip install -e .` 即装即用。
> 素材来源：五个真实 agent 工程（知识检索站、迭代调优内核、经验中台、上游修复流水线、多智能体验证集群）在同一批问题上反复付出的代价。每个机制背后至少有一次真实故障。按症状反查用第 19 章的反模式表（「看到什么改什么」），按能力查用第 18 章速查表。

## 怎么读这份指南

每章回答三个问题：这个坑长什么样、有哪几种做法、哪种更值得抄。章节按 agent 的一次完整生命周期排列——跑起来、听懂输出、断线续跑、判断失败、管住资源、组织并发、对外通信、形成记忆、检索资料、设计工具、管好上下文、留下证据、干净收尾、放行发布、知道自己做得好不好。带着具体项目来的，先看下一节「按你的原型对号入座」；可以跳读，第 18 章有速查表，第 19 章是反模式清单；从零开始先读第 0 章，想直接抄代码去第 21 章，打算开源自己的 agent 基建先看第 22 章。

一条总纲先放在这里：**agent 工程的可靠性来自「假设一切会断」的设计立场。** 模型会超时、进程会卡住、磁盘会写满、消息会重复、输出会变形、人会在一半时改配置。下面每章的机制，都是对其中一种「断」的正面回答。

另一条放在同样靠前的位置：**先确认你需要的是 agent。** 路径可预测的固定流程，用工作流（代码里预先编排的步骤链）更省更稳；只有步数与路径无法预知、需要模型现场决策时才值得上 agent 循环，并接受误差累积的代价——展开见第 20 章「向公开榜样学习」。

## 按你的原型对号入座：你要做的是哪一种

能力按生命周期分章，但你的项目是具体的。四种最常见的原型，各给一条取用路线；第 21 章的骨架对四种原型通用，三闸是所有 agent 的底座。

**原型 A：批量跑任务。** 把一个清单交给模型或 CLI 逐项处理（批量复现、批量改写、批量审查）。先装第 0 章三件套，再加任务账本与并发（`campaign`、`convoy`）。必读第 3 章（断线续跑，批量的命根子）、第 6 章（并发）、第 5 章（磁盘——批量任务最常见的意外是产物写满盘）。最先咬你的坑：半截写入清空账本、兜底值吞掉失败。速查表看第 1、3、6、7、9 行。

**原型 B：自主循环。** 观察-行动循环，自己决定下一步（迭代调优、持续优化、自修复）。三件套之外必须加预算三闸（`budget`，循环最容易失控的是轮数与花费）与指标口径（`metrics`、`iteration_loop`）。必读第 4 章（失败分类）、第 5 章（预算）、第 16 章（自主循环的停止判定）、第 20 章（工作流与 agent 的分界——这类项目动手前最该想清楚的一页）。最先咬你的坑：循环无界、一次失败写全局经验。速查表看第 4、5、6、14、15、25、26 行。

**原型 C：对外服务。** 接消息、回消息（通知机器人、建议服务、webhook 消费者）。先装幂等接收与可靠投递（`idempotency`、`advisory`、`webhook`、`atomic_json`）。必读第 7 章（对外通信，整章都是你的）、第 12 章（证据）。最先咬你的坑：HTTP 200 当成功、重复投递没去重。速查表看第 10、11、12、21 行。

**原型 D：带知识库。** 回答问题前先检索（知识站、问答助手）。先装检索与记忆（`context`、`file_memory`、`memory`）。必读第 8 章（记忆）、第 9 章（检索）、第 11 章（管好上下文）。最先咬你的坑：整篇文档塞进上下文、引文无法验证。速查表看第 13 到 18 行。

混合形态取并集：批量+检索 = A 加 D；对外服务+自主循环 = C 加 B。拿不准时从第 0 章的三件套起步，跑出第一版再回来按坑找章。

## 0. 开箱：新 agent 先装的三样

如果你今天要从一个空目录开始写一个会跑长任务的 agent，先装这三样，其余后补：
1. **原子检查点 + 有界退避**（`recovery`）——第一次断线就把整批任务打回起点，是新手最快交的学费。
2. **空闲+总超时双闸的进程监督**（`cli_session`）——一个挂起的子进程就能吃掉整晚无人值守时间。
3. **轮数+墙钟+花费三闸**（`budget`）——模型循环一旦失控，没有任何外部信号会提醒你停。实现形态是一个单资源支出闸原语 `SpendGovernor`：每个闸一个实例、单位自己定义（轮、秒、token 均可），任一实例抛 `BudgetExhausted` 即停。

装完这三样，agent 已经比多数第一版可靠。之后按需加装：要并发加第 6 章，要对外发消息加第 7 章，要积累经验加第 8 章，要检索资料加第 9 章，要设计工具加第 10 章，要管上下文加第 11 章，批量任务先上第 6 章的文件账本。

## 1. 让 agent 真的跑起来：进程监督

**坑长什么样。** agent 的执行体通常是一个子进程（CLI 工具、脚本、模型服务）。它有三种非正常形态：卡住（还有输出但不再推进）、挂起（无输出且不退出，在等一个永远不会来的输入）、残留（父进程已经退出，它还在后台占资源）。只用一个总超时对付这三种，要么误杀长任务，要么眼看着挂起任务占满整段时间。

**有哪几种做法。**

| 做法 | 描述 | 代价 |
|---|---|---|
| 单一总超时 | 超过 N 秒强杀 | 长任务被误杀；挂起进程照样占满 N 秒 |
| 空闲判活 | 监视输出流，超过 M 秒无新输出判定为挂起 | 需要能读到 stdout/stderr；纯计算无输出的阶段误报 |
| 外置看门狗 | 另一个进程定时检查 | 谁来监督看门狗；复杂度翻倍 |

**推荐：空闲超时 + 总超时双闸，配合进程组回收。** 空闲超时回答「它还活着吗」（生理判断），总超时回答「这件事该不该跑这么久」（业务判断），两个值分开设置：空闲超时短（分钟级），总超时长（小时级，按任务类型定）。能读到输出流的前提下再加心跳打点，把「活着但没输出」的阶段显式声明出来。

**两个容易踩的坑。**
1. 超时后只杀直接子进程，孙进程变孤儿。以进程组为单位发信号（POSIX 用进程组，Windows 用作业对象）。
2. 超时值固定写在代码里。空闲超时和总超时都应该是构造参数，任务类型不同取值不同。

**长驻服务的存活判定看证据，不看进程。** 长驻进程可以活着而什么都不干：监控服务、看门狗、轮询进程崩掉了主循环却留在内存里，「进程存在」与「服务在工作」是两件事。健康检查要看最近一次产出的证据——最近一次写入的心跳文件、最近一次成功处理的条目时间，证据新鲜才算活着；只查进程存在性的健康检查，对「僵着不退」永远是绿的。真实学费：看护服务进程存活数月，实际已数周没有产出任何一次检查记录，靠的人直到事故才发现。

→ 模块：`cli_session`（双超时、心跳、进程组回收）；`probe`（开工前探测 CLI 是否存在、能否启动，避免把「没安装」误判成任务失败）；事件流留痕见第 12 章的 `events` 与 `transcript`。

## 2. 听懂 agent 在说什么：输出解析

**坑长什么样。** agent 的输出面向人，混杂闲聊、代码块、进度播报；你需要的结构化结果埋在里面。只按约定格式解析的程序，在 agent 换了一种措辞的那天集体失效。

**有哪几种做法。**

| 做法 | 描述 | 代价 |
|---|---|---|
| 只信约定格式 | 按协议逐行解析 JSON | 格式一漂移全部失效 |
| 提示词加压 + 失败重试 | 反复要求模型重出 | 烧 token，不保证收敛 |
| 分级降级解析 | 逐级放宽输入形态，全部失败时保留原文 | 实现略复杂 |

**推荐：三级降级，失败必须携带原文。** 第一级读标准输出里的流式 JSON 行（最可靠的协议形态）；全部行都不是 JSON 时，第二级从普通文本里找回嵌入代码块的 JSON 对象；仍取不到才判失败，失败结果里带上已观察到的原始文本。没有原文的失败无法诊断——你只能知道「解析失败」，无法知道 agent 当时想说什么。

**一条引申。** 「让 agent 输出结构化」没有银弹，协议约定与降级恢复必须同时存在：前者把成功率提上去，后者兜住剩下的尾巴。

→ 模块：`protocol`（三级恢复）、`content`（从裸文本恢复 JSON）

## 3. 断了怎么接：检查点与重试

**坑长什么样。** 长任务必然中断：网络抖动、机器重启、额度耗尽、人工终止。没有检查点的任务从头重跑；有检查点但写得不原子的任务，在崩溃瞬间留下半截状态文件，比没有检查点更糟——恢复逻辑读到一半的 JSON，做出错误的续跑。某真实工程的任务账本就曾被一次半截写入整个清空。

**存什么，有哪几种做法。**

| 做法 | 描述 | 代价 |
|---|---|---|
| 存业务状态 | 检查点里放领域对象的序列化 | 业务 schema 一演化，旧检查点全部读不回 |
| 存不透明续跑指针 | 包只保存调用方给的字符串，不解释内容 | 调用方要自己定义「从哪里继续」 |
| 全量工作区快照 | 目录级复制 | 占空间，但恢复最快 |

**推荐：不透明续跑指针做骨架，重活辅以快照。** 不透明的设计让存储层与业务解耦：旧检查点读不回时按「无检查点」处理、干净重跑，绝不崩溃。检查点写入必须原子——临时文件写全、fsync、原子重命名，三步缺一不可；关键账本再配一层「备份先行、损坏回退不静默清库」。

**配置分两类，密钥只走环境变量。** 普通配置（地址、开关、阈值）可以进文件，密钥与令牌只从进程环境变量读取，绝不写入配置文件、更不写入日志——文件会被打包分发、提交、截图，环境变量只活在进程里。既有工程的真实学费：一旦密钥进过配置文件，历史版本、备份、终端历史里就全是，回收成本远高于一开始就分离。权限分级同理：管理凭据与普通用户凭据分开签发，管理凭据永不下发到普通用户侧，明文只在签发响应里出现一次。

**易变现状不进配置，配置只装决定。** 「这台机器能不能跑构建」有两类事实：环境选了什么编译器、跑本地还是跑云（这是决定，写配置）；工具链在哪个路径、某个库此刻装没装（这是现状，开工时探测）。把现状写进配置，机器一变就失真，且没人知道它错了——配置里「编译器在 /opt/gcc-9」这句从写下那一刻就开始腐烂。真实工程的做法是把执行能力说明分成四个来源分清先后：项目与用户的声明、仓库静态发现、类型化的运行时探测、运维人工覆盖，探测结果不回写配置。判据：写下之后会不会自己变？会变的探测，不变才进配置。

**悬挂的运行态要有对账终结。** 进程重启之后，上一轮标记为「运行中」的条目没人再推进，状态字段永久悬挂——账本上永远有一批「在做」，实际无人做。给运行态字段配一个对账步骤：启动或巡检时把超时的运行中条目显式标记为中断，判定依据是状态更新时间早于进程重启时刻。状态字段只该有两种归宿：被流程推进，或被对账终结；悬挂本身不算一种状态。

**追加型账本只进不出，要配归档与瘦身。** 每次执行都记一笔的命令流水、事件流水，写入频率远高于业务数据：管线每秒写几条，几个月就长成几个 GB——主库膨胀拖慢的不只是这张表，是所有查询。成熟做法是按时间归档：早于保留期的记录整表搬到归档库（保留可审计），主库删除已搬记录并回收空间（VACUUM），归档与瘦身一次搬动完成。配套纪律：这类破坏性的批操作必须默认只预览（列出会搬多少条、释放多少空间），带显式执行开关才真正动手；没有预览的清理脚本，误删只差一次手滑。

**转人工的等待也是一种中断。** 审批与升级把任务的下一步交给人，而人什么时候回应没有承诺：下午转出去的审批，次日上午才有答复是常态。这类中断与进程崩溃同构，但多出两件事：等待无界（不能给人工响应设超时熔断），恢复时需要的不只是续跑指针，还有「人到底决定了什么」。检查点覆盖四样：未决目标、进行中的子任务、环境状态（哪些工具调用过、结果是什么）、给审批人的结构化简报。人批准的若是修改后的方案，agent 按原方案续跑就是静默丢弃人的决定——恢复逻辑必须先显式吸收人的结论，再从检查点继续。

**重试策略，有哪几种做法。**

| 做法 | 描述 | 适用 |
|---|---|---|
| 固定间隔 | 每次等同样久 | 简单；突发故障时反复撞同一堵墙 |
| 指数退避 + 抖动 | 间隔逐次翻倍，上下限封顶，加随机量 | 通用默认 |
| 按重置时刻冷却 | 对方自报恢复时间时按它等 | 额度类失败最准 |

**推荐：指数退避做兜底，能拿到重置时刻就用重置时刻加安全余量。** 固定猜测在两个方向都错：额度八小时后恢复时，傻等让任务反复撞墙；额度五分钟后恢复时，长时间冷却白烧了已经恢复的配额。多数限流报文自带重置时刻，解析它比自己猜准。

**一条边界。** 哪些异常可重试，由调用方判定；重试机制只管「怎么等」，不管「该不该」。把语义判定塞进重试层，会让它对每个新任务类型都失准。

**判定的起点分类。** 调用方不必从零想：传输层错误与超时可重试；HTTP 5xx、408、429 可重试（5xx 是对方临时病了，408 是请求超时，429 是限流）；其余 4xx 立即失败——每个 4xx 都是确定性拒绝，同一份请求重发 N 遍只会得到同样的拒绝。这组起点来自边缘 agent 的真实实践，多数场景直接够用，特殊语义再按第 4 章的失败分类叠加。

→ 模块：`recovery`（原子检查点、有界退避、调用方注入可重试判定）、`atomic_json`（崩溃安全存储）、`provider_failure`（自报重置时刻解析）

## 4. 判断谁错了：失败分类与冷却

**坑长什么样。** 一切错误都重试是灾难：限流时重试等于加剧撞墙，凭据失效时重试等于白烧时间。一切错误都熔断同样是灾难：一次网络抖动停掉整个批次。

**有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 全部可重试 | 不分类，失败就重试 | 限流与鉴权失败被放大 |
| 全部熔断 | 不分类，失败即停 | 瞬时抖动误杀整个批次 |
| 窄口径分类 + 差异化处置 | 只识别高置信的失败类型，各给各的处置 | 判定表需要维护 |

**推荐：窄口径三分类。** 限流（冷却并换通道）、凭据失效（冷却换通道，换凭据才恢复）、暂时不可用（短冷却，同会话重试）。判定的第一条纪律是窄：宁可漏判，不可误伤。把产品输出里正常出现的词（timeout、connection 这类）当成提供方故障特征，会把成功结果误判成失败——错杀一个好结果，比漏判一个可重试的失败更贵。

**处置表。**

| 类型 | 冷却 | 同会话重试 | 换通道 |
|---|---|---|---|
| 限流 | 自报重置时刻 + 安全余量；无重置信息时用保守固定值 | 否 | 是 |
| 凭据失效 | 固定冷却（换凭据才恢复） | 否 | 是 |
| 暂时不可用 | 秒级短冷却 | 是 | 不必 |

→ 模块：`provider_failure`（三类判定、冷却推算）

**运维失败与产品失败分开放。** 失败还要再分一层：产品层面的失败（这个方案没修好这个缺陷）可能藏着经验——什么路走不通、为什么；运行层面的失败（鉴权过期、凭据缺失、配置错误）只是环境没准备好，不承载任何关于产品的教训。混进同一个经验库的后果是检索层被运维噪音污染：查「这类缺陷怎么修」，捞回来五条「token 过期了」。真实工程的做法是把运维失败类别收成一个封闭清单（鉴权失效、凭据缺失、配置缺项），命中的条目永远进不了经验素材；运维失败的处置是修环境重跑，不是总结经验。

## 5. 管住资源：磁盘、预算与缓存

**坑长什么样。** agent 工程最著名的翻车现场是磁盘：几十个并行工作区、几轮迭代的中间产物、无人认领的临时目录，直到某天 ENOSPC 让所有在跑任务一起报废。某真实工程 923G 用量里约 700G 找不到归属，靠的还是人工进会话里手动追查。

**磁盘治理，有哪几种做法。**

| 做法 | 描述 | 盲区 |
|---|---|---|
| 清理式 | 定期删除已知模式的目录 | 新模式的目录无人认领；回答不了「盘被谁吃了」 |
| 记账式 | 周期产出目录体积账单，逐次对比，暴涨目录自动浮出 | 事后追查，盘满那一刻已经晚了 |
| 准入式 | 启动前推演预算：可用空间、每 worker 预留、保留下限，容量不足就地拒绝 | 需要清楚自己的容量模型 |

**推荐：三层叠加，各司其职。** 准入式做门卫——构建开始前拦截，拒绝在半路撞 ENOSPC；记账式做侦探——回答「盘被谁吃了」，暴涨目录自己浮出来；清理式做保洁——只处理已知模式的目录。只装清理式的工程是被动挨打：清理规则永远追不上新目录的产生速度。

**就地读，不整份展开。** 两个高频场景的真实学费：一是查大仓库的历史与代码，不建磁盘工作副本——磁盘检出慢、被中断后索引还容易损坏，直接读 git 对象库（rev-list 算祖先、按提交号 grep、show 单个文件）拿同样的结果，快且可靠；附带的坑是老仓库常见非 UTF-8 编码，按「UTF-8（带 BOM 兼容）→ GB18030 → 宽松替换」的顺序探测解码，别让一个 GBK 文件打断整批读取。二是消费大压缩包（用户日志包动辄上百兆），不解压到临时目录再读——只列目录清单，按需把单个文件解到标准输出逐行处理，读完即走，临时目录永远不膨胀。共同的本质：数据留在原地，取用粒度从「整份」降到「需要的那个文件、那段内容」。

准入式的三个关键细节（都来自真实修正）：
1. 已提交 worker 的既有占用按其配额上限一次性抵扣——断点续跑与重试不重复扣并发额度。
2. 工作区与根分区可能在不同挂载点，各自独立计账。
3. 容量不足时给出完整推演（请求多少、配置上限、可用多少、为什么拒绝），让调用方能决策。

**支出预算，有哪几种做法。**

| 做法 | 描述 | 适用 |
|---|---|---|
| 只限轮数 | 最多迭代 N 轮 | 每轮成本稳定时够用 |
| 轮数 + 墙钟 | 加时间闸 | 防单轮超长 |
| 轮数 + 墙钟 + 花费 | 三闸任一耗尽即停 | 长任务标准答案 |

**推荐：三闸全装。** 花费闸在调用外部模型的任务里最重要——轮数没超、时间没超、账单已经爆了的情况真实存在。注意闸是原语不是成品：`SpendGovernor` 管一种资源，轮数、墙钟、花费各起一个实例；墙钟闸在循环每轮开头 `spend(elapsed)`，花费闸在每次模型调用后按用量记账。

**缓存的方向性坑。** 一次性工作区（每个任务一个新目录）会让编译缓存完全失效：缓存路径跟着工作区走，任务一换缓存全冷。给稳定路径的缓存槽加独占租约——路径固定暴露给所有任务，用租约保证同一时刻只有一个任务占用，关闭时撤销。

→ 模块：`disk_budget`（准入推演）、`artifacts`（工件布局与超预算清理）、`budget`（三闸）、`cache_lease`（缓存租约）

## 6. 组织并发：车队、资源池与预算准入

**坑长什么样。** 并发一上量，两类事故准时出现：不同任务抢同一份资源（同一仓库的两个工作区互相污染），不同通道的额度被单个通道的突发流量耗尽。

**并发组织，有哪几种做法。**

| 做法 | 描述 | 适用 |
|---|---|---|
| 全串行 | 一次一个任务 | 安全但慢；任务间无资源共享时纯浪费 |
| 全并行 | 无差别并发 | 资源冲突与额度放大 |
| 按资源分道 | 同一资源串行、跨资源并行 | 多数 agent 工程的最优解 |

**推荐：按资源分道的混合车队。** 把「资源」抽象成 lane（仓库、工作区、文件锁，任意调用方定义），同一 lane 串行排队，跨 lane 并行；派发前查重，同一任务不重复进队；队列空了自动撤销登记，不占内存。lane 是这个抽象的核心：它把「什么算冲突」的判断完全留给调用方。

**进程内的车道管不到跨进程的并发：多个独立 agent 写同一批文件要有双闸。** 车道、队列都是单进程里的结构；多个 agent 进程（或多个会话）同时改同一仓库的文件时，先到先得靠文件系统的原子创建锁，外加一层内容指纹校验——锁只保证「同一时刻只有一个人在写」，保证不了「你手里的底稿还是不是最新的」：读文件、加锁、写回之间隔了十分钟，期间别人改过，直接覆盖就是静默丢改动。三条真实学费值得抄：锁要有 TTL（持有者中断后锁文件残留，所有人被堵在门外，过期后可显式抢占）；写前校验指纹失败时的处置是「重读全文、把外部改动并进本轮」，原样重试会再次覆盖；有 frontmatter 的文件指纹只算正文——工具自己写状态标记会改元数据区，全文指纹会让持有者自己写完标记就撞上自己。

**共享资源池，有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 无限制 | 各任务自便 | 瞬时限流放大成账号额度耗尽 |
| 简单信号量 | 全局一个上限 | 单通道故障拖累全部通道 |
| 分通道配额 + 熔断 | 每通道独立上限，故障熔断该通道 | 需要区分「忙」与「熔断」 |

**推荐：分通道上限 + 跨通道全局限额 + 熔断区分忙碌。** 四个不显然的细节：
1. 并发上限不可被配置突破——瞬时限流放大成账号额度耗尽是真实事故。
2. 同一资源出现在多个通道时，空闲数不叠加（同一账号在两个通道里是同一份额度）。
3. 熔断与忙碌分开：忙碌是「等一会就有」，熔断是「换通道」。混在一起会让健康通道陪葬。
4. 凭据只存引用名，不存值——池子管调度，不管秘密。

**模型可用性是实测事实，不是配置默认值。** 「哪些模型能用、多快、会不会失败」这类事实会随时变（服务端上下架、限流政策调整），把它们写进调用逻辑，改动时就得在调用代码里翻；单独一张事实表只回答「有哪些模型」，调用逻辑只回答「怎么调」，实测结果更新事实表即可，两边的改动互不牵连。

**限流口径全站一套。** 每个调用方自己管限速，结果就是「这个脚本 4 rpm、那个脚本 20 rpm」的各自为政，同一账号的额度被反复误伤。限流、并发、失败换模型全部收进调度层——它应该是整个系统里唯一「会等」的地方，任何调用方拿到的都是同一套限流口径。

**批量任务的账本，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 内存列表 | 进程终止状态即丢 | 断线后不知道哪些做过了 |
| 数据库 | 完整事务 | 重装备；单机任务过重 |
| 文件账本 + 原子写 | 登记/领取/完成/失败重试/跳过，每笔原子写入 | 单机批量任务的标准答案 |

**推荐：文件账本。** 批量任务的每个环节都要留痕：登记（幂等，同一任务重复登记只算一次）、领取（带状态防双领）、完成、失败（区分可重试与永久失败）、跳过（记录原因）。崩溃后重启，账本就是断点。账本同时是唯一事实源：开工第一个动作读账本，收工最后一个动作更新账本；驱动提示词只写不变量（范围、判据、纪律、格式），进度与状态不进提示词，与账本冲突时以账本为准——进度写两处（提示词里一半、账本里一半）必然失同步。

**把别的 agent 当工具调用。** 驱动其他 AI CLI 完成子任务时，每个 CLI 的失败长相都不一样：限流读起来像普通报错，鉴权过期看起来像崩溃，有的吐 JSON 有的吐散文。封一套封闭的失败类型（未安装/鉴权/限流/超时/解析/传输），每类给固定处置；多个 CLI 轮转时有一条真实学费：**捶打刚被熔断的资源池，把 20 秒的故障拖成了 2 小时的挂起**——轮转必须给刚失败的成员一段冷却期，冷却期内直接跳过；同族跳过只对限流与鉴权这类共享预算的失败生效，没安装、解析失败与家族无关，同族的健康成员照常要试。

**每个 CLI 收敛成一个调用层，输出清理只写一遍。** 直连 CLI 的调用点一多（某真实工程 5 处各自 subprocess、各自清输出、各自判超时），同一个坑要在 5 处各踩一遍：输出里混着进度噪音与会话 ID 尾巴，一处清理了另一处忘了，下游解析器收到两种长相的输入。清噪音、拼参数、判超时这类「把回复拿回来」的脏活收进一层，限速、重试、选模型留在上层——每层只管一件事，坑只需要修一处。

**候选谱系。** 迭代类 agent 每轮产出多个候选，后一轮往往基于前一轮某个候选变异而来——记录派生关系（谁是谁的孩子、哪条分支最终被接纳），才能回答「最好的方案是怎么长出来的」。这里的三次真实学费值得抄：新增派生字段只建了列、写入路径没同步，字段永远为空，树退化成一串链（加字段必须连着写读两侧一起改）；父引用取自上一轮整体状态而非具体候选，来源不稳时全部节点挂在根下，偶发正确不是设计保证（孤儿引用归根保展示，同时计数，孤儿突增就是父引用来源断了的报警）；每轮只产一个候选，树只有深度没有分支（想看树就得真给每轮多个方向）。

→ 模块：`convoy`（分道车队）、`resource_pool`（资源池）、`campaign`（批量账本）、`adapters`（其他 agent 的适配层：封闭失败分类、池轮转、冷却熔断）、`genealogy`（候选谱系：孤儿归根计数、环即报错、代数现场推导）

## 7. 对外通信：幂等接收、可靠投递与建议回执

**坑长什么样。** agent 与外界的每次通信都默认不可靠：发送方会重试导致同一消息到达两次；接收方返回 HTTP 200 但业务层失败，消息被静默丢弃数日而日志里全是「发送成功」；建议发出后没人知道有没有被采纳。

**幂等接收，有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 不处理 | 重复就重复 | 对账时数字对不上 |
| 数据库唯一键 | 指纹唯一 | 只挡完全相同的重复 |
| 幂等键 + 内容指纹双通道 | 键挡逻辑重复，指纹兜并发 | 需要约定键的构造 |

**推荐：双通道查重 + 指纹唯一兜底 + 版本替换。** 幂等键挡住「调用方明确知道是同一次」的重复；内容指纹兜住并发写入撞车（同一指纹两个请求同时到达，后到者返回先到者的记录）；生命周期版本更高的提交替换过期状态（对同一任务的重发，新版本生效）。接收方不解释负载内容，只保证「同一份只生效一次」。

**可靠投递，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 发出即成功 | 只看 HTTP 状态码 | 200 带业务错误码时静默丢消息 |
| 只看业务码 | 忽略传输层 | 网络断时误判成功 |
| 传输层 + 业务层双验 | 两者都过才算成功 | 需要为每个目标定义业务成功判定 |

**推荐：双验 + 字节分块 + 整消息去重。** 四条血泪规则：
1. HTTP 200 不是成功——某真实工程的 webhook 长期返回 200 带错误码，超长消息静默丢弃数天。
2. 大小限制按 UTF-8 字节算，按字符算会把 4096 字符的中文（12KB）原样发出去然后失败。
3. 分块投递失败即停——接收方收到 4 块中的 1、2、4 块，比什么都收不到更糟（半截消息）。
4. 去重以整条逻辑消息为单位，且只在发送成功后记录——失败的发送允许重试，查询去重状态必须无副作用（查询即记录会把真正要发的消息误判为重复）。

**建议回执，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 发完不管 | 无回执 | 无法评估建议质量，坏建议反复发 |
| 发送即采纳 | 无确认环节 | 重复投递变成重复执行 |
| 先存后确认 | 消费方持久化后发确认，结果回执只记一次 | 需要约定确认协议 |

**推荐：先存后确认。** 生产方发布带时效的建议；消费方先本地持久化、再发消费确认（确认幂等，重复确认无害）；同一建议的结果（采纳/忽略）只记一次，重复上报按冲突拒绝；过期建议自动隐藏不删（留着对账）。这与幂等接收互补：那边保证发送方重复投递不产生双份，这边保证消费侧不丢、不重、有回执。

**进度通知的节奏。** 长循环对外的另一面是别把人淹了：每轮都报，真正的失败淹没在例行进展里；全程静默，出事时人一无所知。失败是行动信号，延迟等于损失，失败轮永远立即报；例行进展是状态信号，按轮次聚合（每几轮一条，起点建议 3），节奏设为零表示只报失败不报进展。

**通知失败不阻塞任务。** 通知是旁路：发送失败记日志、按投递策略重试，绝不改变主任务的状态与判定——一条没发出去的进度消息把跑了一夜的批次标记成失败，是最冤枉的假故障。主流程对通知的唯一依赖是「尽力发出」，不是「必须送达」。

**旁路镜像失败同样不回滚主账。** 主账之外同步写一份副本给另一个系统（派发记录镜像到验证中心）时，副本不可达只记日志，已成立的主账状态不回滚——副本是投影，投影失败撤销事实源，等于让最不可靠的一端否决最可靠的一端。下次同步自然补齐；真需要补偿的，由副本方的对账来提。

**同一份报告，多种密度，共享一份投影。** 工作台右侧详情与完整报告是两种密度的读者界面，内部排版不必相同，但字段口径必须共享同一份投影（字段名、语义、单位在两端一致），否则同一事实在两处长出两套说法。关联一律用唯一键（完整 commit 号、带命名空间的 ID），标题、短 commit、列表行号都不构成身份；过期内容显式标示「待刷新」，不伪装成实时数据。

→ 模块：`idempotency`（幂等接收）、`webhook`（可靠投递）、`advisory`（投递-确认-回执）、`notify_cadence`（进度通知节奏判定）

## 8. 形成记忆：短期窗口与长期沉淀

**坑长什么样。** 把全部历史塞进上下文，费用与噪音同步爆炸；什么都不记，同一个坑摔倒两次。中间态更糟：记了一堆但检索时捞不出相关的。

**会话记忆，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 全量带上 | 无截断 | 费用爆炸，噪音淹没重点 |
| 只留最近 N 条 | 按条数截断 | 超长单条消息挤掉全部历史 |
| 双预算窗口 | 条数与字符数双上限，取最新的完整消息 | 需要处理单条超长消息 |

**推荐：双预算窗口。** 条数与字符数各设上限，从最新往回取完整消息；唯一的例外是孤立的第一条超长消息——截它尾部保留最新内容，因为它不在任何「保留完整」的集合里。

**长期记忆的排序，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 只按相关度 | 检索器说了算 | 老旧但重要的记忆被新但平庸的淹没 |
| 只按时间 | 新的先来 | 关键事实被灌水冲掉 |
| 相关度 + 重要度 + 时间衰减加权 | 三个信号合成分 | 权重需要按任务调 |

**推荐：三信号加权（0.75/0.15/0.10 是可用的起点），过期条目先过滤。** 时间衰减用半衰期（每过 N 天分数减半），不用线性扣减——线性衰减会让记忆在固定日期集体「过零」，半衰期让老旧记忆平滑淡出但永不为零。

**经验沉淀的准入门槛，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 一次失败就入册 | 高敏 | 孤证污染库，检索时错误经验挤掉正确经验 |
| 全部攒着不提炼 | 无门槛 | 库永远空着，经验白交学费 |
| 重复失败达门槛才提炼 | 同一现象出现 N 次才值得总结 | 需要按范围分层设门槛 |

**推荐：重复门槛 + 范围分层。** 范围越宽（本任务 → 本仓库 → 本场景 → 全局），要求的支持案例越多：孤证最多只能入本任务范围，全局经验至少三个案例支撑。检索时按来源可信度与历史采纳记录加分排序，同分时可迁移层级更宽者在前（这条是修出来的：纯加分排序曾让「窄范围孤证」压过「宽范围多案例」）。

**一卡一文件，索引先行。** 长期记忆选一个文件还是一个大库，决定后面每一次增删改的难度。站点记忆库的形态值得抄：一条记忆一个 Markdown 文件（frontmatter 带名称、描述、类型），另备一份索引文件逐行列出标题、一行简介与文件链接——回答问题先读索引（几十行定位条目），需要细节才打开具体卡片。单文件大库的代价是结构性的：改一条要整体重写，AI 或外部工具无法逐条增删，也无法只读一部分做核对；一卡一文件之后，每条记忆可独立读、独立改、独立外审，索引坏了按文件重建即可，两者互为备份。判据：这套记忆会不会被程序逐条增删？会，就按文件粒度存放。

**经验的分型：三类分开放。** 经验不是一锅粥：值得重复的成功模式（策略）、要避开的失败模式（含回滚原因）、带可执行动作的反思建议（洞察），三类分开存放与检索——混放时「什么时候该做什么」会被「什么不该做」淹没，检索器只能在错误的语言里找答案。

**外部内容进记忆前先过准入，写入时就做隔离。** 记忆与上下文污染的攻击形态：恶意或误导信息一旦进入对话历史、长期记忆或检索库，会在后续全部会话里持续影响决策——一次投毒长期生效，与提示词注入的即时性正好相反。防线在写入侧：外部内容（用户上传的材料、抓取的网页、工具返回的结果）进记忆库前先过准入判定，与第 8 章经验沉淀的「重复失败达门槛」同一位置；记忆按来源隔离（租户隔离、来源分级），跨来源不共享信任；记忆里发现敏感值（密钥、令牌）就地抹除后才入库，与第 14 章「敏感值在产出侧统一抹除」同一原则在写入侧的形态。审计面：记忆条目可追溯到来源会话与写入时刻，污染发生时能定位并清除。

**外部记忆服务是可降级的。** 长期记忆放在自建服务（向量库、记忆服务）上时，服务的每次异常都捕获、记日志、绝不向上传播：记忆读写失败按无记忆降级运行，主流程绝不能依赖「记忆服务必须在线」才能完成任务。记忆增强是增益，不是命脉——命脉是任务本身。

**原始素材与提炼结论分层存放。** 经验管线里两种写法混着：用户或执行方上传的原始材料（原文、日志、笔记）是 L0，蒸馏出的通用结论是 L1；检索只服务 L1（量小、质高），追溯与重蒸馏才回读 L0（量大、保真）。分层之后三件事各归各位：上传即蒸（进 L0 的同时立刻产 L1，不等批量任务）；蒸馏输出挂在识别出的场景下（检索先锁大类再按语义细排，正好接第 9 章的两级检索）；蒸馏质量不稳时允许重新蒸馏——L0 原文还在，结论随时可以重算，这正是第 14 章「结构化字段是投影」在经验层的形态。

**测试态与生产态隔离：测试数据不进生产存储。** 验证队列闭环时，测试记录写进程内存、跑完即消失，生产记录写数据库、重启不丢——测试态永远不碰生产存储。混用一个存储的两条学费：测试数据在生产队列里被真实流程消费，任务状态被测试污染；清理脚本按「测试数据有特征」删除，删错一条生产记录代价远高于从头隔离。判据是「谁消费这条数据」：真实流程消费的进生产存储，只被测试消费的进易失态。

→ 模块：`memory`（窗口、排序）、`experience`（经验准入与分层检索）、`file_memory`（文件型记忆库）

## 9. 检索资料：切块、融合与预算组装

**坑长什么样。** 检索质量的一半问题出在切块：按固定窗口硬性均分，一句话被拦腰切断，命中的块残缺不全；另一半出在融合：两个检索源各自打分，量纲不同没法直接比，硬比等于随机排序。

**切块，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 固定窗口 | 每 N 字符一块 | 段被拦腰切断，语义残缺 |
| 只按段切 | 整段成块 | 超长段塞爆预算 |
| 按段优先、超长段内再开窗 | 结构完整性与预算兼容 | 实现稍多 |

**推荐：按段优先，超长段内部再用带重叠的固定窗口。** 段是天然的语义边界；重叠窗口让被窗口边切断的内容在相邻块里有第二次被命中的机会。每块带稳定 ID（文档 ID + 序号 + 内容摘要哈希），引用时可溯源。

**多路融合，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 分数直接相加 | 假设量纲一致 | 量纲不同时等于随机 |
| 归一化后相加 | 每路先 min-max | 对离群分数敏感 |
| 倒数排名融合（RRF） | 按名次倒数累加，不碰原始分数 | 名次信息之外的分数细节被丢弃 |

**推荐：RRF。** 它的聪明之处在于只要求每路给出「排序」，不要求分数可比——这正是多路检索（关键词、向量、远程服务）的现实约束。融合后按规范化文本指纹去重，保留名次最高版本。

**语料大时先锁大类，再按语义细排。** 语料规模上去之后，直接对全库做细粒度语义匹配既慢又容易把邻近大类的高相似条目捞进来。成熟形态是两级：先用粗类目（标签、场景、知识域）把候选缩到一个小集合，再在集合内按细节语义取最接近的若干条；写路径同理——新条目先识别归属场景再挂载，删除权限也跟着归属走。检索的第一级解决「在哪个范围找」，第二级解决「在范围内找哪个」。

**类目词表是受控的：模型提候选，确认后才进正式表。** 分类的词表一旦各处随手加词，几个月后就是几十个同义词并存的膨胀现场，检索与统计全部失准。成熟形态是两阶段：模型产出的新类目先进候选区，累计命中达到阈值或经人工确认后才回填正式词表；规则匹配的顺序本身也是优先级——具体场景的规则排前面，泛化兜底的规则排最后，顺序写错，全部条目都归进兜底类。

**组装进上下文，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 全塞 | 无预算 | 爆上下文 |
| 截断前 N 条 | 无字符预算 | 单块超长时爆 |
| 预算打包 | 字符预算 + 条数预算双闸，逐条计量 | 需要处理预算耗尽 |

**推荐：双预算打包，每条带编号引用标记，引文与被引块绑定成包。** 引用编号让模型输出「[2] 说的是文档 X 的块 Y」可验证——配套的引用逐字校验（引文必须在被引块中逐字出现）防模型编造引文。

**AI 只消费中间产物，不直接碰上游。** 需要从 git、数据库这类上游系统取材料喂给 AI 扫描时，脚本先把「聚类、过滤、去重」做掉，产出一份自包含的中间产物（manifest：每簇带哈希与成员清单），AI 只读 manifest 不直接执行 git 命令。直接碰上游的代价：每次会话重复执行昂贵查询、提示词与真实仓库状态对不上时错误无从发现、上游系统命令的输出形态一变整个提示词作废。中间产物把「材料是什么」变成可检查的字节，审查结论与材料错位当场可见。

**跨进程也走产物边界：平台不开对方的目录、不拉起对方的进程。** 两个独立服务协作（扫描引擎与验证平台）时，接收方不读对方的内部工作区、不直接 spawn 对方的命令行，只消费对方按约定写入交接目录的协议产物（handoff 文件），各自的内部结构怎么改都不越界。越界读取省下的一次适配，换来的是两边内部实现从此互相牵制——对方挪一个目录，这边就静默失效。

→ 模块：`context`（切块、RRF、预算组装、引用包）、`evidence`（引用逐字校验）

## 10. 设计工具：接口、返回与错误文案

**坑长什么样。** 工具是 agent 的手脚，接口设计得差，模型用它就全靠猜：参数填错、结果读不懂、报错只有一句「失败」。Anthropic 给过一组对照数字：把功能相近的几个端点工具合并成一个带参数的工具、参数改用语义化命名之后，示例调用的准确率从 72% 提高到 90%。这层损耗在接口层修最便宜，提示词层补不回来。

**工具粒度，有哪几种做法。**

| 做法 | 描述 | 代价 |
|---|---|---|
| 一个工具包办多职 | 参数开关切换行为 | 描述写不清，模型常选错开关 |
| 端点平铺 | 每个后端操作一个工具 | 工具数量暴涨，选择本身变难题 |
| 合并同族 + 一工具一职 | 相似端点合成带参数的单工具，职责边界清晰 | 需要一次接口设计投入 |

**推荐：合并同族端点，工具职责单一。** 查询任务、查询任务详情、查询子任务三个端点合成一个带过滤参数的查询工具；命名空间前缀（`asana_search` 这类）帮模型区分同名操作。读写分离同样要紧：查询类与变更类不放进同一个工具，模型误调查询工具没有损失，误调变更工具会改坏数据。

**返回值是给模型读的，有哪几种做法。**

| 做法 | 描述 | 代价 |
|---|---|---|
| 原样返回 | 后端给什么吐什么 | UUID 与内部代号逼模型猜 |
| 高信号返回 | 语义化字段名，去掉无关字段 | 组装层要写一次映射 |
| 巨型结果整份返回 | 不设上限 | 单次结果吃满窗口 |
| 截断加续取 | 默认上限（参考值 25,000 token），超出显式提示 | 需要处理续取 |

**推荐：高信号返回 + 默认截断。** 语义化 ID 替代 UUID，减少模型幻觉引用；返回格式给档位开关（concise/detailed 一类），简档约省三分之二的 token；大结果默认截断并明示「结果不完整、如何续取」。空结果返回「无匹配」加一句原因说明，绝不报错——空结果与访问失败是两件事，混在一起模型会误判数据源坏了。

**错误信息即提示工程。** 模型读错误文本来决定下一步：错误信息写清约束是什么、违反了哪条、怎么恢复（「日期需早于今天，收到的是 2027-01-01，请改用历史日期」），模型下一轮就能自纠；只写「参数错误」的错误，模型只能反复瞎猜。MCP 规范里 isError 标志的含义同源：工具执行失败（参数、约束、内部错误）作为正常结果返回，给模型自纠的机会；协议级失败才需要调用方介入。

**描述即提示工程。** 工具描述除了写用途，还要写什么时候不该用这个工具——两个功能相近的工具并存时，不适用场景的说明让模型选对入口；参数描述写清语义与单位，模型填参的质量直接依赖这段文字。

**破坏性操作加确认层。** 两步提交（第一步预览将要发生的改动，第二步显式确认才执行）防误触；写操作带幂等键，防网络重试导致的双写。与第 7 章的投递纪律同一个原则，在接口层再出现一次：不可逆动作必须给模型一次看清楚再动手的机会。

**工具数量有上限。** 每个服务器暴露的工具数建议少于十五个：工具太多时模型选错工具的概率上升，Anthropic 观察到模型会漏看列表中间的工具。功能多时收进命名空间与分组，别让模型在几十个平铺工具里挑。

**跨调用状态用显式句柄。** MCP 2026-07-28 版规范把协议核心改为无会话：初始化握手与会话头被废除，任意请求可交给任意服务器实例处理，横向扩容无需共享存储。应用层仍需要跨调用状态（购物篮、分析会话一类）时，规范给出的做法是服务器铸造显式句柄：创建工具的返回值里带一个句柄，后续工具把它当普通参数传回。官方结论值得记：模型看得见句柄、能在工具之间传递句柄，这优于藏在传输层里的会话状态。句柄设计四条：每次调用都验证授权——句柄是名字，携带它的调用者未必获得授权，无鉴权的服务器要用高熵标识符加有界生命周期；用不透明标识符，编码了内部结构的句柄招人猜测；保留策略写进创建工具的描述（「篮子闲置 24 小时后过期」这类），模型创建状态时看得见过期规则；对过期或未知句柄的调用返回工具执行错误并说明情况，模型可以创建新句柄恢复。句柄消费的工具应做成幂等：流断之后客户端必须重发请求，重发是客户端义务，非幂等的消费工具会把一次操作执行两次。

→ 模块：`adapters`（CLI 适配层：清噪音、拼参数、判超时收进一层只写一遍）、`idempotency`（幂等键）、`webhook`（双验与分块）、`protocol`（结构化输出的降级恢复）

## 11. 管好上下文：窗口、压缩与外部记忆

**坑长什么样。** 上下文窗口变大之后，很多工程把「塞得下」当成「用得好」。实测数据全部指向反面：ChromaDB 对 12 个模型的测试里，11 个在 32K token 之后性能降到 50% 以下；Microsoft 的长对话测试从 90% 起步，最终停在 51%；干扰的代价更夸张——单个与任务无关的元素就能显著拉低性能，且窗口里开头与结尾的内容表现好于中间。约束遵循同样随轮次衰减：一项测试里模型第 5 轮还能遵守 73% 的约束，到第 16 轮只剩 33%。塞满窗口的代价是性能先于容量见顶。

**摆放纪律：规则在两端、证据贴问题、中部放参考资料。** 注意力对窗口里每个位置的分量并不均匀，U 形曲线是跨架构稳定的事实：开头与结尾最强、中部最弱，中部摆的规则被遵守的概率天然低于摆在两端。三条摆放规则：必须被遵守的规则与当前问题放在两端，系统提示词开头放不可协商的约束，步内指令紧贴生成点重申；证据按相关度排序时最相关的材料放最后、离问题最近；要截断历史时从中间截、两端保留。中部专门留给模型主动查阅的参考资料（schema、示例、背景知识一类）——主动查阅走的是检索路径，位置劣势不构成伤害；passive 靠注意力记住的规则，禁止摆在中部。失败形态值得认：一个「一直好使」的功能突然失灵，排查方向往往不是措辞，是它前面新塞了几段检索材料或工具输出，把这条指令推进了中部弱区。评估配套：造几条关键事实特意摆在窗口中部的用例，与同样内容摆在两端对比准确率，位置敏感性是可以量测的回归，删除猜测。

**管理技术，有哪几种做法。**

| 做法 | 做什么 | 代价 |
|---|---|---|
| 按需检索 | 轻量指针常驻窗口，要用时才取全文 | 需要一个可用的检索器 |
| 工具结果清理 | 已消费的大块工具输出及时清出窗口 | 实现最轻，收益立现 |
| 压缩 | 摘要替换原文，必要时重启窗口 | 摘要丢细节，要守纪律 |
| 结构化笔记 | 重要结论写入外部文件，跨会话取用 | 要设计笔记的形态 |

**推荐：四技术分层组合。** 按需检索做第一层：窗口里只放指针，材料留在原地，要用才取。工具结果清理做第二层：消费完的大输出退场，这是最轻量的窗口回收。压缩做第三层：窗口占用到 60-70% 区间触发摘要化，JetBrains 的实测里单 observation masking 一项就省约 52% 成本，SWE-bench 解题率同时提高 2.6%。结构化笔记做第四层：会话里有价值的结论写进文件，窗口随时可以重新开始。

**压缩的三条纪律。**
1. 记压缩账：每次压缩记一条「何时压的、压掉了什么」，否则事后无法回答「为什么模型不知道 X」——答案多半是 X 在某次压缩里被摘要掉了。
2. 摘要必保留决策与放弃理由：「为什么放弃方案 A」这类信息丢了，模型会重新尝试已知走不通的路。
3. 系统提示词等头部内容保持字节不变：前缀缓存按开头字节命中，头部一动整段缓存全部失效，省下的成本立刻回来。

**数字给一组参照。** Anthropic 的实测：context editing 让 agent 表现提高 29%，配合 memory tool 提高到 39%，百轮搜索任务的 token 消耗下降 84%。方向比绝对值重要——清理与外部记忆的组合，收益大到值得专门做工程。

**结构化笔记的形态。** 生产实践收敛出的三层形态值得抄：一份索引文件逐行列出全部笔记（先读索引定位，几十行扫完）；一事实一文件的正文（独立读、独立改、独立审）；会话记录单独归档，过程性材料不与结论混放。记忆按性质再分三类：语义记忆（事实与知识）、情景记忆（哪次会话发生了什么）、程序记忆（怎么做事情的方法论）——程序记忆最难沉淀也最值钱，一项研究把程序记忆做扎实后，任务完成率从 30% 提高到 100%。

**子任务开独立窗口。** 深挖类子任务（通读一个大文件、追一条线索）派给独立的上下文窗口去跑：主窗口只收一段 1000-2000 token 的摘要回传，完整过程不回流。这同时是编排问题，展开见第 20 章。

**长任务的压缩是状态转换，不是截断。** 上下文压缩发生在长任务中途时，压掉的窗口里装的是工作状态本身，按长度截断会把状态拦腰切断。压缩结果必须保留六样东西：目标与不可协商的约束、已做的决定与理由、已完成的动作及其标识符、未解的问题与下一步、产物与证据的引用、当前的权限与预算。这份清单丢了任何一项，模型从压缩点继续走的就是一条不知道自己从哪来的路。压缩前的完整上下文存为版本化检查点，事后要能回答「压缩点之前模型到底知道什么」——这与压缩账是同一件事的两种视角。

**工具输出必须有界，截断必须显式。** 大结果返回的默认上限（参考值 25,000 token）之外，还要有分页与服务端过滤两个配套：能按条件过滤就别把全集拉回来让模型自己翻。截断发生时必须在返回里显式说明「结果不完整、如何续取」，静默截断的代价最贵：模型基于不完整证据做出自信的决策，且没有任何人知道证据缺了一角。稳定 ID 加简短预览替代整份内容，需要时按 ID 取详情。

**外部内容进上下文就是攻击面。** agent 读的网页、MCP 服务返回的数据、第三方工具的输出，全部是不可控来源的内容直接进入上下文——审过的连接器不等于审过的数据：GitHub 连接器通过全部恶意软件检查，照样把投毒的 README 原文送进模型上下文。三个可用防线：网络层限制能到达的端点（出站允许列表，agent 通过凭据代理访问模型 API 而非直连）；抓取内容先摘要再进窗口（摘要器本身就是一道过滤，原始网页不直接入上下文）；高敏会话给工具返回的内容划隔离窗口，处理完即清。这与「按需检索」同一层：窗口里放的是指针与摘要，原文留在够不到的地方。

**边界声明。** 本章讲机制不讲实现：按需检索的检索器、语义匹配的 embedding 调用、向量库，全部由调用方提供或另行选型，本包不包含这些。包内给到的是四层零件：窗口管理（双预算窗口）、检索组装（切块、融合、预算打包、引用包）、笔记形态（一卡一文件）、分层沉淀（原始素材与提炼结论分放）。

→ 模块：`memory`（双预算窗口）、`context`（切块、RRF、预算组装、引用包）、`file_memory`（一卡一文件、索引重建）、`experience`（L0/L1 分层：原始素材与提炼结论分放）

## 12. 留下证据：快照、回执与血缘

**坑长什么样。** agent 改了文件、跑过构建、产出报告，事后没人能证明「哪次执行、动过什么、产出了什么」。并发写入互相覆盖后，恢复操作回到错误版本；报告里的引用查无出处。

**可回滚性，有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 编辑前备份文件 | 简单直接 | 目录被后续写入覆盖就全丢 |
| 目录级快照 + 哈希校验 | 恢复前先逐文件核验 | 占空间 |
| Git 提交 | 版本完整 | 恢复被禁止或不可行时用不上 |

**推荐：字节级快照 + 恢复前校验。** 每个文件记录 SHA-256；恢复时逐文件先验后写，部分失败绝不报成功（半恢复状态比不恢复更糟）。这条的直接起因是并发写入方的恢复冲突：没有校验的恢复把目录恢复到错误版本还宣称成功。

**执行证明，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 日志文件 | 可编辑可丢失 | 无法证明「那次执行真的发生」 |
| 摘要绑定 | 源树、入口、输出三者字节摘要互相绑定 | 归档时若重定位目录，摘要会失配 |

**推荐：三绑定 + 重定位不换摘要。** 一份执行回执绑定「当时的源码树是什么、入口是什么、输出是什么」三个字节摘要；归档时目录可以搬走，摘要按原始字节重算必须一致。这回答的是「你凭什么说这次验证有效」——答案必须是字节级的，时间戳和日志不够。

**回执不是裁决。** 外部产出的回执可能描述一次规范的复现，也可能只是个有用候选，但回执本身永远不构成结论：采纳前必须校验输入冻结、把案例在框架内重放一遍，重放过了才允许把结论写入正式事实。跳过重放直接采信外部回执，等于把判定权交给一个没经过验证的来源。

**外源上下文的隔离纪律。** 从外部工具抓取的上下文（缺陷跟踪记录、第三方报表）有助于理解现状，但这类记录不是代码证据，且原文可能含敏感内容：读取它们走独立通道，输出永不写入命令留痕与工作区数据库，与自有证据链物理隔离。混进证据链的后果不只是泄密，还会让下游把「某人说」当成「代码里如此」。

**事实溯源，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 不可追溯 | 数据出现即出现 | 引用链条断，下游无法核查 |
| 全程埋边 | 每步都记 | 记录爆炸 |
| 收件箱去重 + 按需埋边 | 入口去重，事件成边，双向可查 | 需要设计边模型 |

**推荐：持久收件箱去重 + 五元组边索引（主体、关系、客体、时间、来源），正向反向都可查。** 溯源的意义在审计时刻才显现，但设计必须在数据产生时刻完成——事后补埋边永远补不全。

**边的可信度要标注。** 血缘边不是天生可信：机器事件生成的边（某任务产出了某候选）可信，推断出来的边（某记忆可能影响了某决策）必须经独立审查才能升级。边带三态——已核实、待核实、已驳回——下游统计与展示只默认信已核实边，待核实边可见不采信，驳回边留档不删除。混着用，血缘图迟早变成「看起来很全但不知道哪条是真的」的装饰品。

**补全类信息走旁路字段，不覆写参与流程判定的字段。** 复现成功但缺少引入信息时，后台补查进程把结果写进独立的旁路字段，绝不覆写原有的选择字段——那个字段参与选包等流程判定，两种来源两种时序的写入混进同一字段，流程行为就随写入时序漂移。判断依据：问一句「哪个字段参与流程决策」，参与的字段只由主流程写，补全的信息一律另立字段。

**事件流与运行留痕。** 事后复盘「那次到底发生了什么」，靠的是运行时留的事件流：事件类型收成封闭集合（开始、输出、诊断、心跳、检查点、恢复、错误、结束），追加只写、一事件一行；写入磁盘前先脱敏——密钥、令牌、鉴权头是运行输出里最常见的意外泄密源，正则按模式替换后再写盘；读取端容忍半截行（进程中断在写一半时留下坏行，跳过坏行继续读，不因一行废掉整个 transcript）。注意边界：通知（要不要发给人看）是第 7 章的节奏问题，留痕（事后能不能查到）是本章的完整性问题，两件事独立决定。

**每一步都能拉出一条 trace。** 行业约定已经收敛：每次 agent 运行一个 trace（稳定运行 ID、起止时刻、终态三档——成功、部分完成、失败），每次工具调用一个 span（工具名、输入、输出、延迟、成败），每次模型调用记模型名、token 数与成本，用户与会话标识挂在根 trace 上——缺了会话标识，出问题时无法回答「多少用户受了这次回归影响」。两个高频坑值得先记：工具调用要记语义成败，HTTP 200 但返回空或错误内容照样算失败，这类静默坏掉的工具会持续弄坏 agent；成本记在 span 属性上，不从月底账单倒推。采样纪律：失败 trace 全量保留，新提示词版本上线头几次全量，健康运行抽代表性样本，成本显著高于滚动均值的 run 单独全采——均匀随机采样会藏掉最需要排查的长尾失败。trace 读法五步：从最后一个正常步往后看；读下一步的完整输入（坏上下文、坏工具输出、记忆缺失在这里暴露）；查工具结果的内容，不只查调用是否发出；找同一工具同一参数连调多次（卡住的信号）；比对每步 token 数（突增常来自工具倾倒大块数据）。最该记的一件事是模型每步看到的完整消息数组：绝大多数 agent bug 是上下文 bug，没有这个数组就无从查起。克制同样重要：embedding 原始向量、流式逐 token 事件、框架内部回调洪流不值得记；三十秒能读完的 trace，胜过三十分钟才能解析的万能记录。

**重跑与重放是两件事。** 重跑：再执行一遍，模型是随机系统，会得到不同结果，还有副作用；重放（replay）：把工具输出缓存、当时的文件快照、模型版本、提示词与参数版本四样备齐，在历史状态的精确复原上继续调试，无副作用。调试「第 7 步为什么选了工具 A」这类问题，重放回第 6 步、改一个条件、看分叉怎么走，是重跑给不了的能力。工程上要备齐两样：检查点写盘时连工具输出一起存；模型与提示词的版本号随 trace 记录，三个月后还能对上「当时跑的是哪一版」。

→ 模块：`snapshot`（校验快照）、`execution_receipt`（执行回执）、`lineage`（血缘）、`events`（封闭类型事件流）、`transcript`（JSONL 留痕、密钥脱敏、坏行容忍）

## 13. 干净收尾：一次性工作区的生命周期

**坑长什么样。** 每个任务一个工作区，任务结束后目录留下来：正常路径有人清理，失败路径（崩溃、被杀、断电）没人管；更隐蔽的是工作区还被进程占着（挂在 cwd、打开着文件），删了目录进程继续在已删除的路径上读写，产生幽灵错误。

**有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 事后定期清理 | 按年龄删除 | 正在跑的任务被误删 |
| 无清理 | 磁盘爆炸 | 上一章的 ENOSPC |
| 终态门槛 + 引用检测 + 加锁 | 先确认任务终态，再扫活进程引用，全程加锁 | 实现较重 |

**推荐：三道门槛一次做全。**
1. **终态门槛**：任务未到终态（成功/失败/取消）拒绝清理——失败任务的现场是排查素材。
2. **/proc 引用扫描**：清理前扫全部活进程的工作目录、argv、可执行文件路径、打开的文件描述符，四路任一命中即跳过——回答「还有没有人在用这个目录」。
3. **证据保全回调先于删除**：任务账本里该留的记录先拷走再删目录；加文件锁串行化，避免两个清理者同时动手；杀进程树时等待真正退出再继续。

**为什么值得专门一章。** 工作区生命周期是 agent 工程里「平时没人看见、出事就是大事」的典型：出问题时通常是半夜的批量任务，目录被误删导致断点续跑全部失败，磁盘被幽灵目录吃满导致次日报废。

→ 模块：`workspace_lifecycle`（三道门槛）；上游修复工程里按仓库清理工作树的做法，是终态门槛与 /proc 扫描的通用化前身

## 14. 放行之前：风险闸门与运行态一致性

**坑长什么样。** 两类「最后一米」事故：带司内痕迹的包发布到公开渠道，靠人的记性把守，总有一次忘掉；代码改了、构建了，但运行中的进程还在跑旧版本，验证全绿而用户看到的还是旧行为。

**发布闸门，有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 靠自觉 | 人记着检查 | 迟早漏 |
| 发布前人工清单 | 有检查动作 | 仍是人工执行 |
| 机器强制闸门 | 扫描进 CI，命中即红 | 需要维护禁词与规则 |

**推荐：字面量规则 + 禁词扫描的强制闸门，且闸门自身必须被证明会红。** 三层检查：禁词扫描（项目名、内部域名、凭据形态）、编译产物入库检查（`__pycache__` 可能嵌入本机绝对路径）、源码绝对路径扫描。最关键的一条经验：**闸门必须配「植入必红」检出测试**——往样本里故意塞违规内容，验证闸门真的会拦。没被证明会红的闸门，可能从某次重构起就永远绿灯，而所有人都以为它在工作。

**动作放行按后果分级，不按习惯。** agent 的每个动作按后果分四档：观察类（读文档、搜索、起草）免闸，只记录、事后抽样；可逆变更（改分支内文件、建工单）在线监督即可，配速率与范围上限；重大变更（合入主分支、对外发信、批量读敏感数据）逐动作审批，审批界面展示确切参数；不可逆与特权操作（删生产数据、转账、改 agent 自身权限）升级认证加独立审批人，先给 dry-run 预览。审批有三条绑定纪律：必须来自认证过的人、必须匹配一个待定请求及其确切参数、一次性使用——未绑定或可重放的审批等于可伪造。闸门的位置放在 agent 够不到的层（执行侧或下游系统）：写在 agent 提示词里的「请先询问用户」，对提示词注入没有任何抵抗力。审批疲劳有实测数字：用户对权限弹窗的批准率高达 93%，逐条审批早已是橡皮图章；升级率超过两成会压垮审查者，开始不看就批。闸门数量本身是安全参数，要监控、要校准。

**遏制 agent 靠三层，每层挡不同的东西。** agent 的安全风险分三类：用户误用（恶意或疏忽的指令）、模型失当（没人要求却做了有害动作——更强的模型更会绕开没人写下的限制）、外部攻击者（注入与常规运行时攻击）。对应三层防御：环境层（进程沙箱、虚拟机、文件系统边界、出站控制——目标是对 agent 能到达的范围设硬边界，凭据不进沙箱就永远偷不走）、模型层（系统提示词、分类器、训练加固——只影响倾向，挡不住理论上的能力）、外部内容层（限制 agent 能到达的内容源，收紧工具权限缩小波及面）。三层互为冗余：环境防御缺位时模型层补位，模型层永远不可能是 100%，单独依赖必被穿透。数字参照：提示词注入对抗测试里单次攻击成功率约 0.1%、百次自适应攻击约 5-6%，自动模式在动作执行前拦住约 83% 的过激行为——防御有实测强度，同时有非零漏过率，这是分层冗余的理由。

**凭据不进 agent 的运行环境。** agent 持有长生命周期 API 密钥等于把全部下游系统的权限装进同一个口袋，被注入攻击接手后横向移动畅通。凭据代理模式：密钥放在沙箱外的代理进程，agent 发请求时代理注入凭据，agent 全程看不到密钥本身；密钥泄漏的最坏情况被限制在「这次会话用过的那部分」。配套三条：每个 agent 用独立身份（继承启动者的全部权限等于事后无法归因）；按任务发放短时效令牌（绑定任务标识，跨任务复用直接拒绝）；挂载文件系统时把 .env、云凭据目录、私钥全部排除在 agent 可读范围之外——只读挂载同样算可读。

**运行态一致性，有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 源码看一眼 | 源文件已是新版 | 进程加载的可能是旧二进制 |
| 重启了事 | 重启即新版 | 忘重启时误判已生效 |
| 三态判定 | 源码基线、构建产物、运行进程分别验证 | 需要访问 /proc |

**推荐：三态分离判定。** 「源码在基线」不等于「二进制重编完」，不等于「运行中进程已加载新版」——三个状态各自验证：源码对照基线（含子模块与依赖），构建产物做新鲜度检查（dry-run 看会不会重新编译），运行进程用 /proc/<pid>/exe 的 inode 与磁盘文件比对（路径带 (deleted) 标记直接判旧）。修改运行中服务后验证「已加载新版本」，这条纪律机制化之后才可靠。

**放行之后还有一站：长驻 agent 的自我升级。** 长期运行的 agent 运维与短任务不同：新版本到了要能自己换上。一套可用做法的骨架：空闲时才下载，版本比较确认真的更新才动手；换文件的执行者必须是独立进程——旧进程退出的锁要靠它解开，它还得脱离父进程的作业组，否则父进程一退出把它一起带走；配置与运行数据在升级时保持不动，只换程序文件；应用后写「已应用版本」标记，安装包已换而进程版本没跟上时停止重试，否则会陷进「下载、失败、再下载」的无限循环；版本号解析不出时视为不更新，宁可不升，不误升。这条按结语的入包标准暂不成模块：目前只有一个工程付过这笔学费，出现第二个独立判例再收编。

**文档也是运行时依赖：文档漂移要进门禁。** skill 与说明文档是静态文字，代码改名、删文件、换路由时，文档里的指针悬空不会报任何错——拿着过期文档干活的 AI 会静默产出错误结果。把「文档引用的代码事实」全部变成可校验断言接进统一门禁：文档里写的文件路径必须存在（按固定顺序在几处候选根解析），文档依赖的代码内标识符（词表、常量、路由）必须还在。文档断言与代码测试跑同一道门禁，漂移在合入时就被抓，避免拖到被执行时才发现。

**双副本要对账，晋升要走闸。** 同一份能力存两处副本（跟站点走的内嵌副本、平台加载的主副本）是常态，两边都改靠人脑记谁新谁旧必然失同步。做一对账工具：逐文件对比列出谁新谁旧（按修改时间），提供晋升方向（内嵌改完晋升到主副本、主副本改完同步回内嵌），晋升前跑门禁验证。能报差异不能处理差异的检测器只做了半个工具。

**触发入口匹配。** 「代码还有没有这个缺陷」与「触发后后果是什么」之外，还有第三层常被漏掉的事实：**用户能不能走到触发入口**。代码层受影响但入口藏在租户配置了开关的功能里，实际暴露面就是零；补丁排期、灰度范围、通知强度都该按这三层事实分开定。判定依据来自项目自报的暴露面矩阵，框架只做解析校验与触发前提匹配，不猜。

**豁免要收窄到文件形态，不放宽到目录。** 边界检查（工作区不许出现计划外的改动）需要豁免时，豁免条件必须描述文件形态而非所在目录——构建工具中断会在生成产物目录里留下半截下载文件（`.part`、`.partial`），这类残留不算源码改动，豁免判据是「生成根目录下的未完成归档形态」，源码区里同名后缀的文件照常拦截。按目录豁免的代价：那个目录从此整个退出监管，任何人往里放什么都查不到。豁免越窄，边界越硬；图省事的宽豁免，是在边界上开门。

**影响面分析：调用点先辨真伪。** 改了一个函数，全仓搜调用点数出的数字里混着宏展开的痕迹、注释里的调用痕迹、永不可达的路径——全算「受影响」会把评估做粗，全不算会漏真风险。逐个调用点判真假，受影响与不受影响分开计数，结论按「共多少真调用点、几个受影响、受影响的在哪」给出，附「合入前 review 受影响调用点」级别可执行建议。假调用点混进受影响清单，评估报告就失去被信任的资格。

**报告是唯一事实源，结构化字段是投影。** 验证类 agent 的结论天然有两种形态：人读的报告与机读的结构化字段（结果、轮次、状态）。让队列和下游只信报告正文，结构化字段按报告重新推导，两处不一致时以报告为准——把结构化字段当事实源，队列缓存一旦失真，后续全部判定建立在错误地基上。

**任务载荷最小化。** 下发给执行方的任务描述只带判定必需的字段（代码路径、标题关键词、判据），巨型现场材料（2.1G 的路径、完整日志包）不进载荷，执行方需要时按引用回取。载荷膨胀的直接代价是传输与解析时间，间接代价更贵：执行方把大材料当上下文塞进模型，噪声挤掉真正要判定的信号。

**入口处的文件验真用魔数，不用扩展名。** 接收上传包或外部文件时，验真只看内容字节头：扩展名与声明的内容类型全可伪造，指针文件就是典型的冒名顶替——名义上是内容包，实际是几行指向外部存储的引用文本，被当成真材料执行时产出的是空转与错误定位。真实学费：仓库没拉大文件存储时，收到的「压缩包」是 LFS 指针，校验用 PK 头加指针特征双重判定，报错信息直接给出修复动作（去执行 git lfs pull）。同样的字节级验真适用于一切「看起来是什么」的输入：图片看签名头，压缩包看魔数，文本看编码。

**敏感值在产出侧统一抹除，不靠下游自觉。** 产出给下游或人的摘要、日志、报告里，用户目录名、邮箱、令牌之类的敏感值在生成时就地替换，不由接收方各自处理——各处分散的「记得脱敏」提醒必然有遗漏，写入侧的统一清洗才可审计。

→ 模块：`risk_gate`（发布闸门）、`environment_guard`（三态一致性）

## 15. 知道自己做得好不好：感知与评估

**坑长什么样。** 前十四章保证「不出错」，但不出错不等于做对了：改了一版提示词，是变好还是变差全凭感觉；循环跑了一夜，不知道哪一轮的产出才值得保留；经验库里混着运行环境失败（配额、鉴权）当经验教训。评估缺位的 agent 是盲跑。

**指标口径，有哪几种做法。**

| 做法 | 描述 | 盲区 |
|---|---|---|
| 各处自写比较逻辑 | 每个调用点自己写「新值优于旧值吗」 | 同一指标出现两套口径，两处结论打架 |
| 统一归一比较 | 指标名带方向（最大化/最小化），比较统一走一个判定 | 需要一次口径登记的纪律 |

**推荐：统一归一比较。** 指标定义带方向，比较统一判定：方向不一致就地报错，基线为零时退化为绝对差值，相对增益低于阈值的「提升」不算更好。一套口径从头用到尾，报告、循环、回归各处共用。

**改进环，有哪几种做法。**

| 做法 | 描述 | 盲区 |
|---|---|---|
| 人工盯每轮产出 | 人肉判断接纳哪轮 | 慢，且夜里没人盯 |
| 无验证自动接纳 | 每轮产出直接生效 | 回退一步 |
| 提案→验证→接纳环 | 每轮候选先评测、达标才接纳、拒绝触发回滚钩子 | 需要一个能跑的验证器 |

**推荐：提案→验证→接纳环。** 循环只管节奏与终止（提案源耗尽、达标接纳、轮数耗尽三种停法），不管提案是什么、用什么验证；被拒候选触发回滚钩子回到轮前状态——接纳的那轮永远站在验证过的地基上。回滚钩子与第 12 章的字节级快照配对使用。

**预过滤，有哪几种做法。**

| 做法 | 描述 | 盲区 |
|---|---|---|
| 全量送昂贵评审 | 语义判断当第一道工序 | 大量条目本可免费判定，评审费用白烧 |
| 廉价判定前移 | 纯文档、纯配置类免费判定先行，源码变更才送评审 | 误滤会静默丢案例 |

**推荐：廉价判定前移，但未知不裁决。** 只靠文件清单就能做的判定（不含源码、目标分支不存在该文件、依赖清单升级自带修复）前移；每个判定带机器可读理由，被滤条目保留记录可复审。两条底线：证据不足时放行（读取失败一律放行），静默丢行计为缺陷。

**静态预检门禁。** 预过滤的近亲：跑昂贵验证之前，先在成品产物里查证据，拦截「代码不可达」与「缺陷已修复」两类条目。三条学费值得抄：产物 0 命中不裁决——产物旧、未打包、已移除三种可能分不清，判「不可达」会误杀「源码已合入、产物待重打包」，记证据后中性放行；扫描面必须覆盖完整产物——主包之外还有解包目录，原生模块与打包产物在那里，漏扫就是漏判；门禁自身永不阻断主流程——产物不存在、判定抛错一律放行，门禁拦住的应该是条目，不能是流程本身。信号分档投票：修复动作已命中强于旁路标志、强于产物命中，多信号达标才下高置信结论。

**各审计必须合成一个裁决。** 每套审计只看得见自己的失败形态：对比度审计、测试套件加上仔细的 diff 阅读，谁也没拦住 263 处指向已删除 token 的引用。单跑一套「没问题」极易变成「我查过的没问题」的错觉，汇总阶段的漏洞才是真正的漏洞。成熟形态是一个总入口把全部审计跑完、输出单一裁决（带 fast 档跳过浏览器类慢检查），任何一项红整体即红，人只看一个结论。

**评估材料必须是一手来源。** 凭摘要写出的「深度解读」每一句都可能是错的，而读者分辨不出来——摘要里没有的公式、超参、消融表、数据集指标，要么读到正文再写，要么明确留空。这条对 agent 的自我评估同样成立：评估器读到的材料降了一级，评估结论就整体降一级，看不出问题与没问题在报告上长得一模一样。

**评估集怎么起步，有哪几种做法。**

| 做法 | 描述 | 后果 |
|---|---|---|
| 想象场景 | 造一些「应该会发生」的用例 | 测的是幻想，真实失败形态全漏 |
| 只收 happy path | 全部用例都跑得通 | 永远全绿，一遇真实失败就哑火 |
| 真实失败任务起步 | 收集 20 到 50 个真实失败任务建评估集 | 起步通过率低，暴露真实短板 |

**推荐：真实失败起步的金标准集。** 评估集的骨架是真实失败的任务：生产里真实发生的失败案例转成可执行的评估用例，覆盖各类失败形态而不只顺利路径。每个用例保存完整轨迹（输入、检索到的上下文、全部工具调用、输出），不是只存输入输出对——没有轨迹，失败用例只告诉你「错了」，不告诉你「在哪一步开始错」。评估集是有 owner 的活资产：有人负责、有版本、随系统演化增删，无人认领的评估集会退化成一份没人敢信的过时快照。

**能力评估与回归评估分开放。** 两类评估的目的相反：能力评估测「能做多难」，起步通过率低才有提升空间；回归评估测「别把好的弄坏」，接近全部通过，专防退步。混在一份评估里，通过率的变化说不清是能力变差还是加进了难题——噪音信号淹没真实变化。分开维护，各自看各自的曲线。

**多轮跑分：pass@k 与 pass^k 是两件事。** k 次尝试里至少一次成功（pass@k）测的是「最好情况」；k 次全部成功（pass^k）测的是「每次都行」。客户按一致可用付费时，pass@k 的乐观数字会掩盖十次里九次翻车的真相。按业务承诺选口径：演示与探索场景看 pass@k，交付与生产场景看 pass^k。

**评分器三类，写法各有讲究。** 代码型评分器（单元测试、精确匹配、JSON 结构校验、产物存在性）最可信，能写代码判定的绝不交给模型；模型型评分器把评分标准写成可核查的断言（「修复方案必须提到文件名」），不写「按 1 到 5 打分」这种模糊口径——打分式 rubric 的输出无法复核，断言式的可以逐条对回去；人工评分只用于校准前两者，不进日常循环。被测模型永远不当自己的裁判：同一个模型既产出又给自己的产出打分，测不出它自己看不见的盲区。

**评分器自身要测噪声。** 评分器不稳定时，优化循环等于对着老虎机调参：同一份输出跑两遍，结论翻转的比率就是评分器噪声。改动前先测噪声，噪声大的评分器先修再优化。结果解读配置信区间：两版对比的差异区间包含零时，报「无明确变化」，不报「提升了」。

**优化循环：训练分与保留分分离。** 用评估集反复调优提示词与配置时，把用例分成训练分（允许反复看失败案例改配置）与保留分（只在验收时跑，过程不许看）。训练分通过率上升而保留分持平，是过拟合评估集的警报——改的东西只学会了应付这几道题，回退到上一个保留分也认的版本。每轮只改一处，改动与结果才能对应；一轮改三处，涨了不知道该谢谁，跌了不知道该怪谁。

**读轨迹，不只看分数。** 通过率之外的信息全在轨迹里：失败用例逐条读轨迹找最早开始走错的那一步；通过样本也要抽查——评分器奖励错的东西时（答案碰巧对、过程全错），通过的用例会掩盖评分器本身的缺陷。评估驱动的开发顺序是：先建评估集再写功能，功能写给评估集看，写完就有尺子量。

**引用校验与经验准入。** 两项支撑能力直接给结论：模型引文必须逐字出现在被引块中（防编造引文，配套修复提示可让模型自纠）；经验入库前先过准入判定——运行环境失败（鉴权、配额、基础设施）永远不是经验素材，正面教训需候选证据加可信评估，新教训与既有条目按结构化条件冲突优先于文本相似判定合并或新建。

**事故教训要机器强制化，防复发的账写在测试里。** 每次生产事故复盘后，把「怎么防止再犯」写成文档只是第一层——文档只防同一双眼睛。事故区的做法是把每条教训写成一个测试断言：计数恒等式（分组头与卡片必须同源，面板数字对不上就是事故重演）、时间戳时区约定（排序比较的前提，坏了所有排序静默失序）、解析对称性（写入的规则条数与解析回来的条数必须相等，解析器丢字段当场红）。三族断言值得抄：恒等式断言把「两个展示必须同源」变成数学；性质盲区补测锁住静态工具看不见的失败形态——linter 只报未用的 import 与局部变量，模块级的零引用函数对它完全不可见，一次改写留下约 90 个孤儿渲染函数没人发现，专门的孤儿代码检查补上这个洞；行为锁定测试把修复过的回归写成永久断言，尤其要锁快路径——指纹命中判定未变时跳过回收是最自然的短路优化，恰好把两次判定之间新生成的坏报告重新放进外发面，已修复的回归靠短路复活。判据：这条教训值得机器防，就值得一个测试名。

**失败先归因，再动手。** agent 失败时「模型不行」这个结论几乎总能往下再追一层，公开实战给的归因次序从高到低：环境给的信息对不对（最常见）——工具描述准不准（第二）——系统提示词清不清楚（第三）——模型在好输入下做坏决策（最少见）。把次序固化成固定清单是防逃逸设计：清单在，排查就逃不掉前面几层，换模型这个最省事也最贵的结论排最后。这有实测背书：LangChain 的编码 agent 只改 harness（提示词、工具、中间件 middleware），模型不变，Terminal Bench 2.0 从 52.8% 提到 66.5%。改 harness 的素材从哪来？从 trace：拉失败运行、并行分析、汇总成针对性改动，一轮改一处防止过拟合到单次失败。归因清单全部走完仍然失败，才轮到评估换模型。

**问模型自己。** 行为异常时，把失败案例放进干净的新会话，直接问模型「为什么做这个决定」「哪段上下文造成了误解」「改哪句话能防止」——失败的解释指向 harness 要修的位置：说系统提示词有歧义就去改那段，说没意识到验证是任务的一部分就把它写进任务模板。注意两条边界：模型的自我报告是事后叙述，当作假设而非结论，修完要验证失败形态真的消失；新模型到位后重读全部系统提示词，删掉为旧模型写的、新模型不再需要的脚手架——提示词只增不删，旧约束会变成新模型的干扰项。

**三大失败形态与各自药方。** 循环：同一工具同一参数反复调用无进展，病根多数在停止条件，药方是步数预算加进展检查（连续几步无变化即强制换路）；选错工具：意图对但调用的工具错，常因两个工具的描述重叠，药方是改描述划清边界；编造参数：调用真工具但参数是编的，药方是严格 schema 加必填校验，在执行前拦下大半。

**agent 是随机系统。** 同一提示词、同一环境，周一跑得干净、周二陷入循环是正常现象。单次通过不构成「修好了」的证据，单次失败也不构成「改坏了」的证据；要看多次运行的分布变化，单例异常先读轨迹再下结论。这与评估环的「每轮只改一处」配套：改动效果本来就被随机波动淹没，多处同时改，归因就彻底失效。

**提示词版本化与删除纪律。** 系统提示词的两种管理形态拉开差距：一份写完之后只增不删的提示词，几个月后装满为历史失败模式补的小节，每段都有人记得为什么加、没人敢删，模型在互相冲突的指令间静默仲裁，行为跨会话不稳定；版本化管理的提示词反而越改越短——每个小节都有存档与出处，删除有自然检查点「这行还必要吗」，成熟团队 8000 token 的提示词压回 2000 token 后在同一评估集上跑分反升，因为删掉过时指令去掉的噪音多过新增复杂度带来的收益。准入门槛照抄经验沉淀的重复门槛：一条指令要进系统提示词，需要至少两次同类失败支撑，单次失败只记日志；一个季度没有发挥作用的指令删除。配套三件：提示词按语义版本管理（大版本破坏输入输出约定、小版本加能力、修订版本改措辞），每次改动走与代码相同的评审；提示词版本号写进 trace（与第 12 章「模型与提示词版本随 trace 记录」同一条）；评审四问——回归评估是否仍全绿、是否与当前工具清单与 schema 对照过 diff、改动针对单一失败形态还是一次堆五句、指令是否写在了正确的层级（安全规则写进用户层是常见错误）。回归与漂移是两种失败：回归是自己的改动弄坏了东西，漂移是外部变了（模型供应商静默更新、用户行为迁移）而提示词没动行为却变了；金标准集每日跑，分数在无提示词变更时下降即为漂移信号，处置是重新校准评分标准与示例，复制成新用例保存。

**金标准集是活资产。** 50-100 例起步足够抓住生产里真实要害的失败：正常路径、边界情形、历史回归三类。历史回归类最重要也最常缺席：每次生产失败的第一反应应当是把「什么测试用例本可以抓住它」补进金标准集，生产 trace 直接晋升成永久回归用例。生产事故的直接转化路径值得抄：一次单提示词改动让任务完成率掉 23% 的事故之后，团队把回归用例积累到 3400+ 例，每次提示词改动必须全绿或有书面说明的行为变化记录，曾拦下一次复杂查询提升 12% 但简单事实题掉 15% 的隐形回归。

**跨提示词依赖链要当图管理。** 多段提示词系统（规划器、执行器、验证器、路由器各一份）里，每个文件被各自版本化与评审，没人管的恰恰是它们之间的边：规划器的输出是执行器的输入，执行器的输出是验证器的输入，验证器的评分标准是按旧执行器的输出形态校准的。实测事故形态：规划器提示词加一句「不确定就先问」，自己的评估集分数上涨、合并上线，两周后验证器的通过率掉三个点且无人能复现——规划器问的澄清问题变多，执行器第二轮收到的任务描述变短，评分标准校准的输出形态已不存在。药方：提示词目录之外维护一份依赖边清单（谁的输出喂谁的输入、交接形态是什么、哪条评估守这条边），改任何一份提示词之前先查它牵动的下游；这与「每轮只改一处」同族，对象从单系统内的一处改动扩展到提示词之间的传播链。

**scaffold 版本随 trace 记录。** 编码 agent 的质量下降时默认归因是模型，纵向对照实验给出相反证据：固定一个模型（自托管排除静默更新），跑 35 个连续的 scaffold 版本对 50 个分层任务，解题率无统计显著提升（23-39% 区间波动、早期版本有时反超），token 消耗单调上涨 70%（391K 到 668K）——每个版本都通过了既有 CI，退化是 scaffold 与模型交互的涌现效应，正确性测试抓不到，非功能性回归测试（每次任务的 token 数、工具调用数、成本）才能抓到。两条纪律：scaffold 版本号与模型版本号一起写进 trace，质量事故时它是可二分定位的变量；回归测试覆盖非功能性指标，正确性之外还要量每次运行的成本与调用数。

→ 模块：`metrics`、`iteration_loop`、`prefilter`、`evidence`、`admission`（评估集与评分器纪律无独立模块，骨架先记在此）

## 16. 自主循环的骨架：什么时候停

第 21 章骨架回答批量任务的断线续跑；自主循环（观察-行动-决策，原型 B）的骨架多一个最难的部分：**任务完成判定**——不是预算耗尽那种停，是「真的做完了」。骨架套两层：内层是第 19 章的批量骨架（每轮是一个被监督的任务），外层加一个改进环：

```python
from agent_foundation import IterationLoop, NormalizedMetric, MetricDirection, SpendGovernor

BUDGET = SpendGovernor(resource="rounds", max_units=20)


def propose() -> dict:
    BUDGET.spend(1)
    return next_candidate()          # 你的候选生成：改提示词、换参数、换方案


def evaluate(proposal: dict) -> dict[str, float]:
    result = run_eval_suite(proposal)  # 你的验证器：跑评测集，返回指标值
    return result


def accept(metrics: dict[str, float]) -> bool:
    score = NormalizedMetric(
        "task_score", metrics["task_score"], MetricDirection.MAXIMIZE
    )
    baseline = NormalizedMetric(
        "task_score", baseline_value, MetricDirection.MAXIMIZE
    )
    return score.is_better_than(baseline, min_relative_gain=0.05)


def on_reject(attempt) -> None:
    restore_snapshot()               # 回滚到轮前状态：快照见第 12 章


loop = IterationLoop(
    propose=propose,
    evaluate=evaluate,
    accept=accept,
    max_rounds=20,
    on_reject=on_reject,
)
result = loop.run()
print(result.stop_reason, len(result.attempts))
```

`propose` 抛 `StopIteration` 表示候选源耗尽；`evaluate`、`accept` 里的异常直接向外传播，不在环内吞掉。每轮的指标留在 `result.attempts` 里，事后可复查每轮为什么被接纳或拒绝。

**人从哪里进入循环。** 约四十万真实会话的遥测给出一个稳定模式：人做规划决策，agent 做执行决策。人的参与分三段：输入（任务描述、约束、示例——多数团队在这里投入不足，之后花两倍时间纠正从第一条提示词就跑歪的产出）、引导（监控方向、审查计划、出事时干预——逐动作批准在这里没有位置）、输出审查。监督策略随信任演化：新用户逐动作批准，老用户的会话全自动比例从约两成升到四成以上，中断率反而从 5% 升到 9%——从「事前把关」迁移到「放手跑、出事才出手」，两种形态各自成立，混着用（既逐条批准又不盯全局）最差。升级只认四类信号：显式要求人工（立即转，不反问「确定吗」）、策略门槛触发、解决路径耗尽、安全合规信号；情绪永不构成升级理由——按情绪路由的系统会训练用户表演不满换快速服务，按表面平静路由的系统会把「关闭我的账户」这类不可逆请求当例行任务执行。

**任务完成判定，有哪几种做法。**

| 做法 | 描述 | 盲区 |
|---|---|---|
| 模型自报完成 | 提示词里让模型说「我完成了」 | 自报完成率虚高，复杂任务几乎不可信 |
| 外部验证器 | 完成条件写成可执行的判定（测试通过、文件存在、指标达标） | 验证器本身要维护 |
| 双确认 | 模型自报加外部验证同时满足 | 实现成本最高 |

**推荐：外部验证器，自报只当信号。** 自报完成的 agent 在难任务上的完成宣称几乎不可信；把「什么算做完」写成可执行判定（能跑测试就跑测试，不能跑就验证产物存在与内容），模型自报只用来触发验证、不直接采信。这与第 14 章运行态一致性的立场同源：验证过的才算数。

→ 模块：`iteration_loop`、`metrics`、`budget`

## 17. 评估器本身也要被评估：自改进系统的防护链

**坑长什么样。** 自改进系统（自己找问题、自己修、自己验证）有个自举漏洞：它用来判定「改好了」的每件工具——探测器、修复器、验证门禁——自己也是代码，也会错。只有误报率、没有召回率测量时，系统的最优策略是**什么都不报**：不报就没有误报，报表全绿，而被管的东西一直在坏。某知识站的治理法庭用一套防护链把「谁来验证验证器」变成日常工序，每层回答一个不同的怀疑。

**金丝雀：测召回。** 往真实条目里注入已知缺陷，数抓到了几个。误报率衡量精度，金丝雀衡量召回，两者缺一报表就可以自欺。注意金丝雀与第 14 章「植入必红」的关系：植入必红证明闸门会拦已知的那类违规，金丝雀把注入变成持续工序、按周期数召回率。

**变异测试：测金丝雀的盲区。** 注入已知缺陷只能证明「改了这几处会被抓到」，证明不了「改了别处也会被抓到」——一条用例都没有的盲区，报表照样全绿。变异反着来：故意把被保护对象改坏，要求金丝雀必须报警；无声变异（改坏后金丝雀照常全绿）暴露的是探测规则的覆盖缺口，逐个补规则直到注入必红。

**混沌演练：测整车。** 零件级验证全绿，链路仍可能断：探测器发现了缺陷但修复协商拿不到锁，修复成功但验证环节确认不了。往一个真实条目注入已知缺陷走全链路，测三件事：多久发现（MTTD）、多久修好（MTTR）、最后文件是否毫发无损地还原。

**回滚自检：测安全网。** 修复链的安全网（快照→改→门禁→回滚）用一条端到端用例看住：走完整个「改了再退回去」的流程，文件必须逐字节回到原样。任何一环失效——快照没记下、回滚没还原、门禁没拦住——这条用例就红。它测的正是第 12 章快照机制的「会红」本身。

**自审：用对外同款闸门审自己。** 系统存在的理由是「模型会虚构问题」，这套自审不能豁免自己：模型报的每一条必须附上被审文件里真实存在的代码原文，逐条核对引用是否属实，对不上的一律丢弃——和它对外治理内容用的同一道闸门。

**配套三件。**
1. **对等协商定改法。** 「A 提方案、B 审核、A 照着改」的上下级流程把其中一个模型的局限固化成结论；两个对等智能体协商直到共识，谁都可能被说服，改法是谈出来的。
2. **记账流水与视图分离。** 流水只增不删（审计证据，三个月后要能回答「这个问题第一次什么时候出现、复发过几次」，越来越大是正常且有益的），当前视图随时从流水重算。
3. **防重复审。** 每次调模型要几分钟，条目没变结论不会变：审过什么、什么时候审的记下来，轮转回到刚审过且未改动的对象直接跳过。
4. **被测与裁判必须是两个模型。** 同一个模型既产出改写又给自己的改写打分，测不出袒护——它给不出自己看不见的盲区。评审的最低结构：被测模型读改前改后出报告，裁判模型拿同样的原始输入独立复核并补漏，裁判从原始材料出发，不从被测的结论出发。

**任务发现。** 修一条是一条的模式永远追不上反复出现的同类问题：同一模式在几十个条目里各自独立地被撞见，每次只修撞见的那个，没人知道总共波及多少。把反复出现的同类问题自动聚类成可持续推进的任务（带范围计数、跨会话接着做），治理整个模式，避免只修单次撞见。

**能力矩阵评测集：把声称变成可断言。** 金丝雀与混沌演练测的是单点与整车，能力矩阵测的是「系统的自我描述」：每个域声称能发现什么、误报率多少、修复链能修多难的修复，全部写成可断言的评测场景，跑在固定评测集上。治理系统升级探测器之后跑一遍矩阵，升级有没有伤到别的能力当场见分晓——系统的自我描述与真实能力之间的差距，只能在评测集上暴露。

**知识会过时，到期复查要闭环。** 经验、文档、评估基线都随真实系统演化：当时的「正确做法」半年后可能就是错法。给每条持久化知识带复查日期，到期自动收集成任务清单；只报 WARN 不生成任务等于没有闭环——告警之后没有动作，过期知识照样被当现状引用。复查后的更新或确认要销账，让下一轮巡检从干净状态开始。

**兜底路径也要走查，静默丢弃是最贵的失效。** 主路径与备路径并存的管线里，备路径常年不跑，坏了对报表不可见——真实学费：AI 泛化产不出卡片时本应由兜底直写接手，但兜底的写入函数只认规范化的类目名，收到的却总是原始域标签，映射规则从未写过，于是备路径 100% 静默丢弃，坏了两个半月无人知晓，期间丢的全是数据。备路径失效的特殊危险在「无报错」：主路径失败有告警，备路径失败只是什么都不发生。防线两条：备路径至少配一条金丝雀（造一条走备路径的输入，断言产出写入库中）；枚举管线全部写入路径，每条路径的失败都要么报错要么记账，不存在第三种结局。

**饱和与负结果：评估集的两条读法。** 通过率见顶之后进步看起来变小，这时候该换尺子：单轮编码评估通过率到顶的 agent，长任务评估可能还有大段提升空间——尺子量不到的能力不等于不存在，先怀疑尺子再怀疑系统。「什么没用」的清单与成功清单同样值钱：连续三轮净负的改动记下来，防止半年后换个名字再试一遍；最有用的消融常常是负结果——给 agent 加了全量访问权限，准确率一动不动，一次实验证明瓶颈在结构不在权限，重定向了数月的路线图。PR 粒度的消融进日常流程：每次改动前后跑相关评估切片，涨跌数字写进提交说明，善意的改动反而变差的常见情形靠这个当场抓住。

**为什么值得专门一章。** 前面的能力章回答「怎么把 agent 做对」，这一章回答「怎么证明它一直是对的」：没有金丝雀的自改进系统迟早学会什么都不报，没有变异的金丝雀不知道自己的盲区，没有混沌演练的零件不知道整车能不能跑，没有逐字节回滚自检的修复链总有一次改坏文件还不自知。

→ 模块：目前集中在知识检索站的治理法庭（canary、mutation、chaos、verify_apply、self_review、negotiate、ledger、dedupe、discover、missions），按结语三标准暂不抽象为独立模块，骨架先记在此；首次采用可直接参照该实现。

## 20. 向公开榜样学习：编排模式与系统设计

本指南的能力清单来自自己交过的学费；公开领域有两份材料值得反复读：Anthropic 的《Building Effective Agents》回答「agent 长什么样、什么时候不该上 agent」，OpenAI 的 GPT-5 系统卡示范「一个大规模 agent 系统的公开设计记录怎么写、怎么想」。两者与本包互补：它们讲编排与系统形态，本包讲让形态可靠运行的底层机制。

**架构抉择：工作流与 agent 的分界线。** Anthropic 把全部智能体系统分成两类：工作流的控制流预定义在代码里；agent 的控制流由模型现场支配。分界线只有一条：路径能否预测。任务能干净分成固定步骤，就用工作流，用可预测性换灵活性；开放式问题无法预知步数，才用 agent 循环，并接受更高的成本与误差累积。它的核心建议与本指南第 0 章同源：从最简单的方案起步，多数应用单次调用加检索已经够用，实测证明复杂度有收益才升级。

五种工作流模式，各记条件与代价：

| 模式 | 做什么 | 适用 | 代价 |
|---|---|---|---|
| 提示链 | 固定步骤顺序执行，中间可加程序化检查 | 任务能干净分段 | 每步延迟叠加 |
| 路由 | 先分类输入，再导向专门处理 | 不同输入需要不同处理与成本档 | 每请求多一次分类 |
| 并行化 | 分段（子任务分发）与投票（同任务多答取信） | 子任务独立，或需要多视角提置信 | 成本随份数线性上涨 |
| 编排者-工作者 | 中央模型现场分解任务、派发、汇总 | 子任务无法预先确定 | 最贵；规划者可能过度分解 |
| 评估器-优化器 | 生成与评估循环直到达标 | 有明确评估标准且迭代有收益 | 成本由迭代次数决定 |

与第二到六章直接对应：编排者-工作者必须配 worker 上限与任务账本（`budget`、`campaign`），否则过度分解烧穿预算；并行化的两种形态对应 `convoy` 的分段并行与多视角投票派发；评估器-优化器就是 `metrics` 加 `iteration_loop` 提案-验证-接纳环的编排视角。模式决定故障面：选哪种模式，决定要装哪些护栏。

**把榜样读透：GPT-5 系统卡的三个系统设计动作。** 系统卡是公开发布的运行设计记录，其中三个动作对自建 agent 直接可搬：

1. **统一系统 + 实时路由。** GPT-5 由快模型（答多数问题）、深思模型（答难题）与实时路由器组成；路由器按对话类型、复杂度、工具需求与显式意图（用户说「仔细想想」）实时分流，并用真实信号持续训练：用户切换模型的行为、回答采纳倾向、实测正确率。翻译成自建 agent 的话：贵模型只花在难问题上；路由信号自己手里就有，任务分类器加调用方显式标记就是第一版路由器；额度耗尽由小档模型兜底——与 `resource_pool` 的「忙碌与熔断分开」同源，降级是保可用，熔断是保额度。
2. **能力分档与防护联动。** 系统卡按 Preparedness Framework 把模型在各领域的能力分档，高档自动触发更强防护，无确凿证据也按预防性原则处理。对应 agent 工程的纪律：能力升级必须同步升级预算与闸门——更自主的模型配更紧的花费闸，新能力先在沙箱验证再放行。
3. **安全完成优于直接拦截。** 系统卡描述的安全训练目标是产出安全的完成内容，避开有害部分继续把任务做完。迁移到 agent 闸门设计：闸门的理想行为是把违规内容改写成合规输出再放行，拦截只是改写不可行时的兜底。这与第 14 章「闸门必须被证明会红」互补：红之前，先想有没有更聪明的处置。

**多 agent 的加减法与任务分解。** Anthropic 把自己的多 agent 研究系统公开成一份操作记录，加减两侧的判据都值得抄。加一个 agent 之前先回答一句话：第二个 agent 做了什么第一个做不到的事？这句话说不清就别加。加的顺序也有讲究：先加负责复核的 verifier 换可靠性，再加负责分流的 router 省成本，最后加并行 workers 提速度——顺序错了，花掉的钱换来的可能还是不可靠的结果。派发时只传 sub-agent 需要的上下文切片，回传只要简短摘要：上下文隔离就是子任务的边界，共享全部历史等于没有边界。任务分解的原则：每步要小、可检查、有预期输出；产出变差时能定位到具体哪一步引入的问题，这样的分解才值得，定位不了的分解合并回去。转交链的长度也有实测上限：代理到代理的转交超过四次，任务失败率不成比例地上升——每次转交都是有损压缩，长链要么减少边界，要么压扁编排。

**长任务的分层规划与战略监督。** 数小时量级的任务里，单层规划撑不住：规划定得太细，执行中的小误差让全部后续步骤作废；定得太粗，执行器自由度过大走歪。公开研究的收敛形态是两层：高层规划器只定「要做什么」（子目标序列，不规定怎么做的细节），底层执行器完成单个子目标（几十步以内的短任务，细节自己决定），子目标失败的信号向上反馈触发重新规划。战略层再配一个独立监督：执行 agent 战术推进，另一个异步角色盯战略方向，检测到原地打转或策略漂移（同一种尝试反复失败还在继续）时强制转向——「盲目坚持」是长任务 agent 最典型的失败形态，埋头执行的 agent 自己看不见。任务级还有两件配套：开工前把任务写成带验收条件的合同（什么算做完、边界在哪），执行中按里程碑同步进度（防数小时的漂移无人察觉），与第 16 章的任务完成判定衔接。

**要跨组织协作才用网络协议，不跨组织用进程内 sub-agent。** 多 agent 的经典价值场景——扫五万行日志回传两百字摘要、贵模型配便宜模型、并行检索——全部由进程内 sub-agent 解决（Claude Code、Codex、OpenCode 都这样跑），零网络开销；网络级协议的不可替代价值在跨组织远程协作：不同团队、不同厂商、不同框架的 agent 互相委派工作，这是 A2A 的地盘——它是 agent 之间横向协作的通信标准，MCP 是 agent 纵向连工具的调用标准，两层并存。A2A 设计过程里最值得抄的公开教训：agent 聊天室形态被彻底放弃。让几个 agent 在自然语言里自由讨论任务，放上生产的结果是单任务多轮澄清让 token 消耗膨胀五倍、延迟拖过九十秒、任何一个 agent 的小幻觉级联成整任务失败；收敛形态是严格控制流：中央编排者持有全局意图，远程 agent 只当专职执行单元。协作单位是 Task：带唯一 ID 与完整生命周期（submitted、working、input-required、completed、failed、canceled、rejected），能跑数小时数天，中途可暂停等人补输入；rejected 与 failed 的分别值得抄——rejected 是提交时刻的拒绝（能力不匹配、授权不通过、策略阻挡），failed 是接了、开工了、没能做完，重试逻辑对 failed 重试、对 rejected 永不重试，混用两者会把拒绝变成重复执行。两件配套：Agent Card 发布在 /.well-known/agent-card.json（能力目录：技能、端点、认证方式、流式支持），v1.0 起带签名防篡改，能力声明是 agent 自己说的，委托敏感工作仍要可信注册表与允许列表当凭据；身份传递用令牌交换（RFC 8693 的 On-Behalf-Of）：发起方 agent 把用户的令牌换成携带双方身份的新令牌去调远程 agent，审计链能回答「这个动作是哪个用户经哪个 agent 请求的」。

**错误内容会自我强化。** agent 的轮次越长，窗口里的正文就越是自己写的东西：第三轮写下的幻觉步骤，第四轮成为被模型当作证据的上下文，模型把自己的早期错误当成事实继续推理。实测数字：同一任务以欠约束的多轮对话形态到达时，模型平均掉 39% 性能（Laban 等 2025 对 15 个模型的测试）；注意力机制的解释也直白——softmax 注意力把固定预算的权重摊到窗口里每个位置，每多一条工具输出、一次重试、一条走不通的路径，都在从信号那边抢概率质量，窗口越满注意力越平。三条药方：中间产物先验证再进窗口（压缩与摘要的输出过校验，错误不进上下文）；轮次间重申目标与不可协商的约束（与压缩保留六样东西同族）；对第三轮上下的早期产出保持怀疑，幻觉痕迹已进窗口时，主动重申正确事实，指望模型自己纠正靠不住。

**怎么用这两个榜样。** 选编排形态，先回答 Anthropic 的问题：这条路径的控制流，写在代码里还是交给模型现场决定？设计模型调用策略，先回答 GPT-5 的问题：这个请求值多少算力，谁来判断？两个问题都有答案之后，本包的 29 个模块负责让答案可靠地跑起来。

**公开榜样的教训也是教训。** 榜样章节容易读成「照着大厂做就对了」，另一半信息同样值钱：GPT-5 系统卡写了路由误判时用户重试的体验代价，Anthropic 文章强调多步 agent 的误差累积随步数放大、部分任务里多 agent 并行反而不如单线程好调试。把这些反面项也搬进设计评审清单，与正面模式并列权衡，榜样才读完整。

```python
    ProcessSupervisor, RetryPolicy, SpendGovernor, Termination, retry,
)

ITEMS = ["alpha", "beta", "gamma", "delta", "epsilon"]    # 换成你的任务清单
STORE = FileCheckpointStore("ledger")                     # 账本：断线的断点
BUDGET = SpendGovernor(resource="rounds", max_units=8)    # 支出闸：越界即停
SUPERVISOR = ProcessSupervisor()                          # 监督：双闸加进程组回收
POLICY = RetryPolicy(max_attempts=2, initial_delay_seconds=0.1)


class TransientFailure(RuntimeError):
    pass


def run_item(item: str) -> str:
    spec = ProcessSpec(
        ["your-cli", "--do", item],
        hard_timeout_seconds=1800,   # 业务判断：这件事该不该跑这么久
        idle_timeout_seconds=300,    # 生理判断：它还活着吗
    )
    result = SUPERVISOR.run(spec)
    if result.termination is not Termination.EXITED or result.returncode != 0:
        raise TransientFailure(f"{item}: {result.termination}")
    return result.stdout.strip()


def process(item: str, index: int) -> None:
    BUDGET.spend(1)                  # 硬边界：越界抛 BudgetExhausted
    key = f"item-{index}-{item}"
    checkpoint = STORE.load(key) or Checkpoint(key=key)
    try:
        output = retry(
            lambda: run_item(item),
            policy=POLICY,
            is_retryable=lambda exc: isinstance(exc, TransientFailure),
        )
    except TransientFailure:
        STORE.save(checkpoint.next_attempt(status="failed", data={"error": "transient"}))
        raise
    STORE.save(Checkpoint(key=key, continuation=output, status="done"))


def main() -> int:
    for index, item in enumerate(ITEMS):
        existing = STORE.load(f"item-{index}-{item}")
        if existing is not None and existing.status == "done":
            continue                 # 断线重启：做过的直接跳过
        try:
            process(item, index)
        except BudgetExhausted:
            return 2                 # 账本就是断点，下次接着跑
        except TransientFailure:
            return 1
    return 0
```

骨架里每个部件回答一种「断」：

- **进程监督**回答子进程挂起：空闲超时与总超时分开设置，超时按进程组回收不留孤儿进程。
- **支出闸**回答循环失控：支出是硬边界，越界就地抛异常拒绝本次支出，退出码 2 表示「可续跑」。
- **检查点账本**回答进程终止：每项完成后以原子写入保存到账本，重启时 `status == "done"` 的直接跳过。
- **有界重试**回答瞬时抖动：退避封顶，可重试边界由调用方的 `is_retryable` 定义，重试层不管「该不该」。

两个值得注意的行为：预算只在实际支出时记账，跳过的任务不花预算，所以断线续跑的二轮仍有满额可用；失败任务的检查点保留尝试计数，排查时能看出一项试了几次。

任务不经过子进程时，把 `SUPERVISOR.run` 换成直接调用即可；但只要还执行外部命令，双闸监督就不要省。

→ 模块：`cli_session`、`budget`、`recovery`

## 22. 开源基因：把痕迹挡在发布之前

本包自身零司内痕迹。这道纪律本身就是从真实学费里抽象出的通用能力——任何人将来开源自己的 agent 基建，都会撞上同一批泄漏路径。

**泄漏的三个入口。**

1. 硬编码的项目名、内网域名、平台链接——最容易漏的位置是 docstring 与注释。
2. 编译产物：`__pycache__` 里的字节码会把本机绝对路径嵌进去，源码干净不等于包干净。
3. 绝对路径：日志语句、默认参数里的家目录路径直接暴露身份与环境。

**挡法，有哪几种做法。**

| 做法 | 描述 | 缺陷 |
|---|---|---|
| 发布前人工检查 | 靠记性 | 迟早漏一次 |
| 机器闸门扫描进发布流程 | 命中即红，禁止发布 | 需要维护禁词与规则 |
| 闸门加植入必红元测试 | 闸门自身被验证有效 | 元测试要跟闸门同步演化 |

**推荐第三种，且元测试与闸门始终配套。** 第 14 章的结论在这里同样成立：没被证明会红的闸门不可信。做法是往样本里塞一个假项目名，闸门必须红，这个「必红测试」跟着闸门进版本库。本包的 `risk_gate` 与隐私测试三道检查（禁词扫描、编译产物入库检查、源码绝对路径扫描）是参考实现，任何一道红即禁止发布，不依赖任何人的记性。

**上报身份只活在一处。** 上报 ID、采集地址、筛选名这类身份常量只存在随包脚本里，禁止写进入口文档、禁止从目录名或元数据推断——身份常量分散多处（文档一处、代码一处、目录名一处），任何一处变动都产生失配；身份从目录名推断，目录改名即断链。

**为什么值得专门一章。** 发布是单向门，包一旦公开，泄漏不可撤回。agent 基建天然带着运行痕迹（路径、命令、平台名），比普通开源项目多一层泄漏面。把「干净」从个人美德变成机器强制，是这件事唯一可靠的做法。

## 结语：什么能力值得进包

判断标准三条，按序：
1. **跨 agent 复现**：至少两个独立工程为同一问题各自付过学费。
2. **机制而非口径**：抽出来的是「怎么做」，业务口径（schema 字段、排序规则、评估标准）留给各自项目。
3. **框架中立**：不绑定任何 CLI、模型、存储；参数由调用方注入。

骨架价值验证脚本：`.work/skeleton_demo.py` 已实际运行验证——首次运行 `done 5/5, rounds remaining 3`，再次运行全部跳过（检查点续跑生效），指南里的代码是真实可运行的。规模数字只此一套：本包 37 个源文件（36 个功能模块加 adapters 子包的 base 基类），指南速查表 33 行覆盖全部模块的通用能力，README 矩阵 37 行与之逐名对应。

收编动作本身有纪律：先读源工程全文理解原始设计意图，抽象时改名去业务化，配独立测试，过隐私闸门（禁词扫描 + 植入必红检出），在 README 矩阵登记出处。新项目出现新的通用机制时，按同一条流水线入册。

发布前的最后一道流程见第 22 章「开源基因」；把能力装进自己代码的动手起点见第 21 章「开箱骨架」。
