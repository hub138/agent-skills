# 模型负责判断，运行时负责执行语义

Agent 运行时的价值不是“替模型思考”，而是把模型提出的动作放进一个具有状态、并发、失败和副作用的真实世界。模型可以决定尝试什么；只有运行时知道动作是否真正执行、执行在哪个环境、产生了什么结果，以及失败后能否安全重试。

## 两种权力必须分开

| 模型适合决定 | 运行时必须强制保证 |
| --- | --- |
| 如何理解目标和当前观察 | 当前任务绑定哪个用户、项目和版本 |
| 下一步最值得尝试什么 | 命令是否实际启动以及退出码是什么 |
| 选择哪个工具和候选参数 | 参数是否合法、权限是否满足 |
| 如何解释错误并调整方案 | 超时、取消、子进程和日志如何收束 |
| 何时认为证据足够 | 成功条件是否被独立验证 |

如果模型能够直接写入“已执行”“已成功”或“环境阻断”等事实字段，语言结论就会冒充系统事实。相反，如果运行时替模型硬编码每种项目和问题的处理逻辑，系统又失去模型处理未知环境的价值。

## Agent 是事件驱动的状态机

一次运行不应只保存聊天记录。最小状态至少包含：

```yaml
run_id: run_...
subject:
  user_id: ...
  tenant_id: ...
target:
  resource_id: ...
  revision: ...
workflow_version: ...
status: running
goal: ...
checkpoint: cp_...
observations: []
proposed_actions: []
executions: []
evidence: []
budget:
  deadline: ...
  max_steps: 12
  max_tokens: 30000
  max_cost: 0.30
```

状态变化应由事件驱动：模型提出动作、策略允许动作、执行器开始、执行器结束、证据验证、人工批准、超时、取消。最终状态是这些事件的投影，不是模型最后一段文字。

```mermaid
flowchart TB
    E1[事件: 模型提出动作] --> E2[事件: 策略允许]
    E2 --> E3[事件: 执行器开始]
    E3 --> E4[事件: 执行器结束, 记录退出码]
    E4 --> E5[事件: 证据验证]
    E5 --> E6[事件: 人工批准或超时取消]
    E6 --> S[状态投影: status 与 executions 与 evidence 只由事件写入]
    M[模型最后一段文字] -.不构成事实, 只是候选信号.-> S
```

事件逐个写入状态，模型的自述只能作为候选信号进入事件流；`status`、`executions`、`evidence` 三个字段的每次变化都能对应到一条事件。

## 检查点不是业务事务

检查点解决“运行过程从哪里恢复”，业务事务解决“外部状态如何保持一致”。如果工具已完成扣款，但检查点尚未保存，恢复后可能再次扣款；如果检查点记录成功，但外部写入回滚，系统又会产生幽灵成功。

```mermaid
sequenceDiagram
    participant R as 运行时
    participant C as 检查点
    participant E as 外部系统
    Note over R,E: 先扣款后存检查点：恢复后再次扣款
    R->>E: 扣款成功
    R--xC: 崩溃, 检查点未存
    Note over R,E: 恢复后重发 → 重复副作用
    R->>E: 扣款成功
    R->>C: 检查点已存成功
    E--xR: 外部写入回滚
    Note over R,E: 幽灵成功: 记录与外部事实相反
```

两类事故共同的原因是扣款与检查点属于两个无法原子提交的存储，所以靠幂等键、结果引用与恢复时重建状态来兜住，而不是追求单一事务。常见控制方法包括：

- 每个有副作用动作携带稳定的幂等键；
- 执行前保存意图，执行后保存不可伪造的结果引用；
- 对支持查询状态的外部系统，重试前先读取现状；
- 无法原子提交时使用 outbox、saga 或显式补偿；
- 恢复时按事件与外部事实重建状态，不重复相信旧的自然语言总结。

## 重试是语义，不是循环语句

只有临时故障适合自动重试。参数非法、权限不足、业务拒绝和目标版本不匹配不会因为重试变好。错误必须先分类：

| 错误 | 例子 | 默认动作 |
| --- | --- | --- |
| transient | 限流、网络抖动、服务暂时不可用 | 指数退避、抖动、次数上限 |
| invalid | schema 错误、参数越界 | 让模型修正一次或直接失败 |
| forbidden | 权限不足、策略拒绝 | 不重试，返回明确边界 |
| conflict | revision 已变化、资源被占用 | 重新读取状态，再决定合并或终止 |
| ambiguous | 请求可能已成功但响应丢失 | 用幂等键或状态查询消歧 |
| blocked | 必需依赖、凭据或环境不可用 | 保存证据，等待外部条件变化 |

后一次失败不能覆盖之前已经确认的成功事实。运行状态应支持“步骤 A 已完成、步骤 B 环境阻断”，而不是只保留一个全局字符串。

## 并发与资源所有权

多个 Agent 或多个重试代际可能同时操作同一资源。仅有文件锁并不足以防止旧任务继续写入：锁可以过期，进程可能暂停，网络可能分区。对长任务使用租约和 fencing token，外部写入拒绝旧代际；对 worktree、临时目录、端口和子进程建立明确所有者，清理动作只能回收本任务确认不再使用的资源。

## 停止条件必须可计算

Agent 循环至少在以下任一条件成立时停止：

- 可执行验收证明目标完成；
- 权限或策略明确拒绝；
- 缺少不可替代的外部条件；
- 连续步骤没有产生新证据；
- 步数、时间、token、工具调用或费用预算耗尽；
- 风险达到人工审批阈值；
- 用户取消或目标版本已失效。

“模型说完成了”不是停止条件，只能是触发验收的候选信号。

## 恢复测试

对每个关键节点做崩溃注入：工具执行前、执行中、执行成功但结果未保存、检查点保存后、人工审批等待中。重启后验证不会重复副作用，不会丢失已确认事实，不会把旧 revision 的结果绑定到新任务。无法通过这些测试的系统，不具备长任务自治能力。

验证的锚点：执行结果要与运行时记录对账——预写结论不依赖模型的陈述，若只能靠自述支撑，与预期对不上，说明运行时没有记下真实退出码。

## 验证

1. 职责分离：核对一次任务里模型只提出动作、运行时记录动作是否真正启动与退出码，确认执行结果不依赖模型的陈述。
2. 绑定核对：确认当前任务绑定的用户、项目与版本由运行时维护，模型上下文中被篡改的绑定值不会改变实际执行身份。
3. 重试安全：构造一次副作用动作失败重试，确认幂等键与输出锚点让重试不产生重复副作用。

## 效果与代价

把判断与执行分开带来的收益是完成状态有独立证据支持：动作是否启动、退出码是多少、结果引用是什么，都由运行时记录，模型的语言结论不再直接充当系统事实。代价是状态机、幂等键、恢复流程与并发所有权都需要显式实现，长任务的取消、重启与错误分类也要逐条覆盖。

## 机制与本质

运行时的机制层：模型只能依据当前上下文提出候选动作，动作是否真正执行、在哪个环境执行、外部状态是否已改变，只有运行时能观察。状态由事件驱动并由事件投影得出，模型自述的结论不构成事实；把这两者混在一起，恢复与重试就失去可判定的依据。

## 要解决的问题

模型提出一个动作之后，没人能回答它是否真的执行、在哪个环境执行、产生了什么结果，失败重试时是否会重复写入。本篇回答：运行时的职责边界在哪里、状态与并发与失败与副作用分别由谁处理、模型判断与执行事实不一致时以哪一侧为准。
