# 技能维护的方法与纪律

本文件是**本包技能共用的方法层**，只此一份。执行细节各技能自己承载：

- `design-craft/scripts/`（`skill_check.py`、`review_skill.py`、`quality_gate.py`、`cli_runner.py`）：确定性实现
- `article-illustration/scripts/concurrent_guard.py`：并发锁与内容指纹，各技能下同名脚本是同一份实现的分发副本

**各技能只写自己的执行入口，不复制本文的判据。** 需要判据时回到本文；发现本文缺失就改本文，不在技能里另写一份。分发包内同名脚本是同一份实现的副本，改行为时所有副本一起改，不得只改一处。

## 零、检索优先、来源纪律与技能自身的效力（全技能共用）

**需要外部事实、素材、成熟做法时先联网检索**，不要在技能自带的清单里挑——清单的价值是"已验证过"，不是"全集"，而且会过期（实测：Sentinel 文档图整目录 404、Wikimedia 对脚本限流）。

- **中文源优先**：中文关键词泛搜 → 中文源定向（官方中文文档、国内厂商技术文档），两轮无果才用英文兜底；同名概念取中文。
- **先判许可再判相关性**：许可不明或禁转载即不采用，不因"图很贴"破例。
- **留检索记录**：查询词、命中、取舍写进工作记录。无检索能力时记"未检索"，**不得据此声称"没有这类资源"**。
- **各技能只写执行入口**，不复制上述判据。

**技能正文是上次实践凝结的假设。** 写得越像操作步骤的条款，越可能只是那一轮的局部最优。判据与红线照办；参数、阈值、步骤、示例按当时语境理解，与实际冲突时以实际为准并回头改正文——照抄不适用的条文比没有条文更坏。

## 一、先分清是哪种失败

拿到一次产物缺陷，先定位已有规则，再判断属于哪一类。分错了就会用错动作：

| 类型 | 表现 | 动作 |
|---|---|---|
| 规则遗漏 | 搜不到相关条款 | 走归属判定，改写最近的既有条款 |
| 表达问题 | 写明了但没执行 | 就地改写措辞，**行数不增** |
| 路由问题 | 写在深处没加载 | 在入口加载表加一行指向，不加条款 |
| 工具失败 | 规则对但脚本报错 | 改脚本，不动规则 |

**审计脚本报出问题，先怀疑脚本。** 口径错一步就带偏全量结论，实测连踩两次：查"代码块有没有复制按钮"只找 `pre` 内部（按钮其实在外层容器）→ 全篇误报；统计"文章有没有图"只认 `![...]()`（漏掉 Mermaid）→ 把 100% 覆盖率报成 47%。采信前用已知样本验：**正例报"有"、反例报"没有"**，两头都对才算口径对。

**先喂一个已有规则完全覆盖的简单任务**。简单任务都失败，是表达或路由问题，不是遗漏；简单任务通过、复杂任务才失败，才是真漏。跳过这一步会把表达问题误判成遗漏，然后不停加条款。

允许零修改——已有规则覆盖时，本轮不改是正常的，不是没干活。

## 二、抽象要过两道测试

一条规则写"学习页四个按钮太多"只能管一个页面；写成"同形即同权重，同权重即没有主操作"能管所有按钮组。但抽象必须两道都过：

1. **去专名测试（能不能推广）**：抹掉页面名、项目名、工具名，句子仍成立才算抽象到位。不成立就还在个案层，继续抽象或降级进 references。
2. **复现基数测试（该不该推广）**：该现象实际出现过几次？只见过 1 次就写成通用条款，是把一次观察当规律。去专名测试拦不住它——去掉专名后照样成立。

**N=1 且抽象过的条款比带专名的更危险**：带专名的至少知道只管一处，N=1 却抽象过的会伪装成普遍规律，让后续所有同类判断套用一个孤例。

- N=1 无法自查 → 写进工作区 JSON，标注"单例观察，待复现"，不进规则正文
- N=1 可自查 → 先 grep 或加检查脚本确认是不是孤例，查完仍是单例按上条处理
- N≥2 且形态不同 → 可以进正文

一条条款覆盖 N 个场景才算收敛；一个场景一条条款，增长没有上限。

## 三、预算与快照

预算同时限制 `SKILL.md` 与全部 `references` 的**总行数和总字符数**，不得超过长期基线；入口另外单独限 500 行 / 24000 字符。

**基线是上限，不是"每次相对上一版"**：在上限内可以恢复被误删的可执行判据，只要总量不超基线。禁止靠更换基线掩盖累计增长。

代码与测试不计入规则预算，但改动必须留下相应测试证据——用"不计入预算"换来的空间，要用可验证性还回去。

新增内容优先合并同义条款、改写最近条款。每次任务最多一个候选、两次修订；达到次数仍不通过就保留可用版本与失败原因。单候选与修订次数是**维护者纪律**，脚本强制的是预算、引用、版本绑定与评审独立性——纪律与强制各管一层，不能互相冒充。

## 四、独立评审与多模型对抗

脚本能判预算与格式，判不了审美与语义——后者交给模型，且**被测与裁判必须是不同模型**：自己改的产物自己评，会顺着改动找理由。

命令行优先派具备视觉与工具能力的 subagent，不可用才用双模型命令（公开 CLI 如 `claude -p`、`codex exec`、`codebuddy chat -p` 均可）。两条路径产出结构相同的 `review.json`：

```json
{"digest": "<当前版本摘要>", "baseline_digest": "<基线摘要>", "reviews": [
  {"reviewer": "subagent-<标识>", "approved": true, "blocking": [],
   "evidence": [{"file": "相对路径", "quote": "改后文本中连续的原文"}],
   "generalization": "适用与不适用的边界", "coverage": "已有规则能否覆盖新增要求"}]}
```

摘要取自 `skill_check.py snapshot`，引用必须逐字存在，否则校验失败。

- 两位裁判各读同一份原文、改后文本、diff、检查结果与触发场景，**不互看结论**；与作者模型不同，限流回退后仍要保持互异，同模型换会话不算独立。
- 评审回答：能力是否丢失、已有规则是否覆盖、适用范围与反例。每条结论要有可定位引文。
- 评审集里放未经改动的正常内容：在干净内容上捏造缺陷，与在坏内容上漏报，是同一种失败。
- 记录摘要必须与当前文件一致；期间文件被改，结果只对附件版本成立，不能声称当前版本通过。
- 只有静态检查通过时 `publishable=false`：静态检查只证明格式、预算与引用，不证明语义。
- **评审必须先挑毛病**：裁判的任务是"先证明产物是错的"，证明不了才算通过；这个顺序要写进派给裁判的指令。产出 `approved: true` 却没指出任何具体问题，视为未通过——只比措辞、不落具体输入的评审不算评审。
- **换模型时一并换身份**，三种可并行：
  - **下游使用者**：拿这份产物去真用，走它没写明的路径，指出哪一步卡住、哪个字段有歧义。
  - **挑剔审计员**：指定一个思维模型（MECE、SWOT、五问等）按框架扫一遍，回答有没有缺漏、有没有互斥、边界在哪。
  - **反向追问**：让模型就难点对自己连环提问，人来回答；答不上的那处就是没想透的地方。
  每个身份只报能让产物出错的具体输入，且给得出输入、指得出产物里哪一句扛不住，不报措辞意见。
- **追问的底气来自自己掌握的事实**：手里只有 1 就让模型推 2、3、4，它只会发散出不知所云的 5、6。派评审前把已验证事实随任务给出，裁判没有事实就只能比措辞。
- **能跑不等于对**：判断力是核心，结果跑通只证明它没崩，不证明它该这样。改完先问"为什么非得这么实现"，答不上说明这一轮没有理解，只是搬运。
- **再进一步**：做完不等于做完，把个案抽象成可复用判据、把跑通的闭环推成通用方案，才算这一轮结束。觉得"够用"往往只是缺想象力——60 分到 95 分那段才是分水岭。
- **卡住就换主体，不在同一会话里硬磨**：同一段文本读第三遍仍走不通，就派 subagent 或换模型重做这一步。新主体只拿任务原文与已验证事实，不继承上一轮的判断过程。仍失败则问题在规则本身，回到第一节。


## 五、并发、验证与版本

- 改前用唯一身份和 token 认领：`python3 <技能目录>/scripts/concurrent_guard.py lock <文件> --agent <标识>`（返回 token），`unlock`/`renew` 必须带同一标识与 token，`fp --whole` 取全文指纹、`check --fp` 校验。各技能下的同名脚本是同一份实现的副本，改行为时全部副本一起改。发现外部变化就重新读取，不覆盖他人成果。界面侧另可用 `design-craft/scripts/quality_gate.py`（转发到同目录的确定性实现）。
- 采用前做前后对照，包含已正确的内容，确认没有把好的改坏。保存测试命令、结果、实际模型、修订次数与净变化。
- 自动审查只产出判断与报告，**不改写文件、不提交、不部署**。失败时用编辑工具恢复本次改动。
- 多份部署副本分别维护，仅按内容差异显式同步；**禁止按文件时间戳自动覆盖**——那会让旧副本反向吞掉新改动。
- 不得关闭安全保护、删除失败记录或改退出码来换取通过结果。

## 本文自身怎么被管

本文不是免检的。改 `skill-craft/SKILL.md` 同样走上面的流程：基线存在固定工作区（`.work/craft-before.json`，长期保留、不重建），用 `design-craft/scripts/skill_check.py` 与 `review_skill.py` 以 `--root skill-craft` 跑 check 与 review。**判据改动的评审，至少要有两位不同于作者的独立评审者**——改的是评审规则本身，自评必然判好。

## 红线

- 同一套方法不写进第二个技能；共用就加指向，实现副本保持一致。
- 不为单个场景新增正文条款；N=1 进工作区，不进规则。
- 不把"去专名后成立"当成抽象合格的充分条件。
- 每次任务追加一行不算自改进。
- 未经独立评审不得声称完成。
