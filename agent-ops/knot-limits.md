# 速率治理：从官方口径到自适应并发

> 本文只讲机制与方法，不内置任何平台的具体配额数字。你所用平台的速率与天级上限，以它的官方说明为准；下面每一步都说明「官方数字该填进哪个变量」。

## 一、官方口径怎么读

平台限流通常分三层，读文档时先拆清它们：

| 层级 | 典型形态 | 落到代码 |
|---|---|---|
| 单个智能体 | 每分钟请求数上限 + 天级总量上限 | `AGENT_RPM`、`AGENT_DAILY` |
| 人 + 模型粒度 | 某个人对某个模型的每分钟上限 | `MODEL_RPM` |
| 单模型全局 | 该模型全平台共享的速率 / 并发 | `PLATFORM_MODEL_RPM` |

三条容易读错的：

1. **限的是速率，不是并发数。** 并发必须由速率和单次耗时反推（见第三节）。
2. **各模型限频相互独立。** 撞限流切模型有效；看起来「切模型没用」，往往是所有模型被同一批请求同时打满、又没分桶。
3. **天级配额是总量闸门，不摊成每分钟速率。** 批量任务本来就集中跑，把天级摊成每分钟会把并发错误地压到 1 路。天级单独查。

> 天级是否按自然日还是滚动 24h，按官方文档为准——多数平台是滚动窗口，这一点直接影响「第二天什么时候能放开」。

## 二、两类 429，别用一套恢复逻辑

| 类型 | 形态 | 处理 |
|---|---|---|
| **带重置时刻** | 文案里有「将在 <时刻> 重置」 | 解析时刻 → 整模型冷却到那一刻 → 持久化（进程重启不丢）→ 到期自动回归；其余模型继续跑 |
| **不带恢复时间** | JSON body 里的 429 / too many requests | 无时刻可解析 → 降并发到 1 + 指数静默（60 / 120 / 240 / 480s 封顶）→ 连续成功再逐步回升 |

**不能混用**：对有时刻的做盲退避是浪费；对无时刻的做「冷却到某时刻」是无依据的猜测。

第三类常被误判：**模型调用 timeout**。这是通道被并发会话占用，不属于限流文档管辖，重试不如错峰或换通道。

## 三、正确并发怎么算

```
启动速率(次/分) = 在途并发 ÷ 平均单次耗时(秒) × 60
=> 并发上限   = 允许的启动速率(次/分) × 平均单次耗时(秒) ÷ 60
```

允许的启动速率取三者最小，再乘「本项目份额」和安全系数：

```
agent_rpm   = AGENT_RPM   × share
model_rpm   = MODEL_RPM   ÷ 每次智能体触发的模型调用数 × share
allowed_rpm = min(agent_rpm, model_rpm) × safety
```

- `share`：多项目共用同一池子时本项目占的份额，默认 0.25。
- `safety`：给其它项目和瞬时抖动留余量，默认 0.7。
- 算出来的单模型并发再 **clamp 到一个经验上限**（本项目用 1~2 路起步），因为公式只给理论上限，实际抖动与调度开销会吃掉余量。

**一次智能体调用会触发多次模型调用**，并发会话把速率放大——这就是「单条正常、并发报错」的根因。

## 四、按模型分桶

全局信号量不够，必须按模型分桶：

- 每个模型一个 `Semaphore(per_model)`，避免所有请求挤在一个模型上把它打满、其它模型闲置。
- 批内按连续任务分给同一模型（`start_model = batch_no % len(models)`），保证轮转而不是只用第一个。
- 分桶 vs 不分桶的差距在多路并发下非常明显：不分桶时撞限流失败率飙升，分桶后显著下降。

## 五、AIMD + 指数静默

自适应并发状态机：

| 事件 | 动作 |
|---|---|
| 连续 N 次成功 | `slots += 1`（封顶到每模型上限） |
| 一次 429 | `slots = 1`，`fails += 1` |
| 连续 429 | 静默期 `60×2^(fails-1)`，封顶 480s；**静默期不发请求** |
| 一次成功 | `fails = 0` |
| timeout（通道占用） | 不降并发，只打断成功计数 |

从 1~2 路起步，连续成功才上探。模拟与故障注入下，这比固定 1 路的报错率更低、吞吐更高（因为固定 1 路放弃了并发收益，而一味加并发会持续撞墙）。

## 六、可观测性三坑

统计限流次数时，这三种误算很常见：

1. `grep 429` 会命中时间戳里的毫秒和文件名——只数带 `request_id` / `model` 的行。
2. `grep 限流` 会命中脚本文档正文——按结构化日志字段数，不按自然语言。
3. 调度器心跳日志不是请求——按请求日志数。

全局占用分析：数进程时要**排除看护子进程**（一个 chat 常伴随一个 watchdog，实际并发要除以 2）；`pgrep` 在 Python 子进程里会漏，用 `/proc` 扫。

## 七、排查顺序

队列突然零成功时，按这个顺序查，不要一上来归因「全局拥堵」：

1. `grep 429` / 额度文案 / 冷却文件 → 是不是限流？
2. 假绿灯：RC=0 但 stdout 是错误串 → 是不是失败被当成了结论？
3. 孤儿进程：ppid=1 且挂了很久的 chat 占额度不释放 → 只按自己的 PID 清。
4. 通道占用：timeout 而非 429 → 错峰或换通道。
5. 最后才看全局池是否被别人打满。

## 八、本地闸门的边界

本地速率预算只记**本项目**的调用，不是全平台账本。能严格保证的只有「自己 ≤N 并发、≤M 次/分、观测到拥堵时排队 / 静默」。想做全局协调需要共享存储（多机场景换 PostgreSQL），单机 SQLite 做不到跨项目协调。
