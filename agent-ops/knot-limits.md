# Knot 官方限流口径与速率治理（2026-11-12 查证）

> **适用边界：本文全部内容只讲 knot-cli / Knot 平台。** codebuddy CLI 是另一套机制：它的 429 会在文案里明确通知「将在 <时刻> 重置」，可以解析时间做整模型冷却；**knot 的 429 没有任何恢复时间通知**，只能靠降并发、切模型、短退避 + 探测式自动恢复。两者不要混为一谈（用户 2026-11-12 纠正）。codebuddy 的用法见 `codebuddy-cli-notes.md`。

> 权威来源：内部文档 （内部文档，公开版略） 《智能体使用限流与模型 token 限额说明》（平台官方文档）
> 工程实践参考：内部文档 （内部文档，公开版略） 《TME AI 后台自动化接入司内免费模型方案（Knot CLI）》（2026-09 调研，数字为旧口径，以官方文档为准）

## 一、官方限制（公开版略去具体数字）

平台对单个智能体、人+模型粒度、单模型调用均有速率与天级上限；具体配额以官方说明为准。并发策略与自动恢复状态机见下。

## 二、本 skill 之前写错的两条结论（已纠正）

1. ❌ 旧：「429 是全局排队，**换模型没用**，退避 45s 重试同一模型」
   ✅ 官方：各模型限频**相互独立**，撞限流**切模型有效**。之前实测看起来「换模型没用」，是因为那次所有模型被同一批 worker 同时打满、又没按模型分桶和降速，不是策略本身无效。
2. ❌ 旧：「**建议按 16 并发跑**」（把并发数当固定值）
   ✅ 官方限的是**速率**，不是并发数。并发必须由速率和单次耗时反推，见下节。16 路只在长任务下成立，短任务下必然撞墙。

另外一条实测仍然成立、但要归对类：
- `knot-cli chat` 被并发会话占用时出现 **模型调用 timeout**，这**不属于限流文档管辖**，是通道占用问题，重试不如**错峰或绕过**。我们后来的做法正是绕过到 codebuddy 独立通道。

## 三、正确并发怎么算（这是「全局多少」的答案）

**换算公式**

```
启动速率(次/分) = 在途并发 ÷ 平均单次耗时(秒) × 60
=> 并发上限 = 允许的启动速率(次/分) × 平均单次耗时(秒) / 60
```

允许的启动速率取三者最小，再乘「本项目份额」和安全系数：

```
agent_rpm   = 20 × share                       # 单个智能体
model_rpm   = 60 ÷ 每次智能体触发的模型调用数 × share
allowed_rpm = min(agent_rpm, model_rpm) × safety
```

- `share`：十几个项目共用同一免费池，本项目只取一份，默认 0.25。
- `safety`：留余量给其它项目和瞬时抖动，默认 0.7。
- **天级配额是总量闸门，不摊成每分钟速率**：批量任务本来就是短时间集中跑，摊成 官方速率上限会把并发错误地压成 1 路。用 `RateBudget.day_remaining()` 单独查。

按默认参数（share=0.25、safety=0.7、每次触发 2 次模型调用）实测输出：

| 平均单次耗时 | 公式值 | 本项目实际并发（硬上限 2） |
|---|---|---|
| 7s（短 prompt） | 1 | **1 路** |
| 25s | 1 | 1 路 |
| 45s（长代码对比） | 2 | **2 路** |
| 60s | 3 | **2 路** |
| 90s | 5 | **2 路** |

这正好解释本机两次实测：短 prompt ~6.7s 时 18 路并发 4 分钟 0 返回；长 prompt ~45s 时 4 路 codebuddy 并发稳定产出。

**结论**：速率公式给的是理论上限，但**用户给的实测口径优先**：**同模型最多 2 并发**；**多模型合计全局上限 10**（其它项目也在用，别打满）。公式算出的单模型并发 clamp 到 2；总并发 = min(10, 模型数×2)。旧版把这两个量混成「本项目总量 2」是错的，已修正。批量判定更该走独立通道（codebuddy），把 knot 全局池留给别人的长任务。

## 四、自动恢复状态机（按错误类型，别一律 45s×3）

| 匹配文案 | 分类 | 正确动作 |
|---|---|---|
| `429` / `too many requests` / `RateLimitError` | `personal_limit` | **按模型独立 → 切下一个模型并降并发**；不要原地退避 45s。fallback 链最多试 N 个模型 |
| `模型资源非常紧张` / `有限流情况` | `platform_load` | 平台负载，不是个人限流；短退避 8s/16s 最多 2 次，或换模型 |
| ~~`使用量已超出频率限制，将在 <时间> 重置`~~ | ~~`quota_exhausted`~~ | **不属于 knot**。这是 codebuddy 账号额度， knot 的 429 从不给重置时间；见 `codebuddy-cli-notes.md` |
| `hard_timeout` / `timed out` / 超时 | `channel_timeout` | 通道占用，**不重试**；错峰或绕过到独立通道，失败留到下轮断点续跑 |
| 偶发格式错 / 单次网络抖动 | `transient` | 失败不写库，下轮断点续跑自动重判 |

判据仍是：**失败是否集中在限流且随并发数变化**。随并发数变化 = 容量问题，降并发/切模型；固定并发下偶发 1~2 条 = 抖动，短退避有用。

### knot 没有恢复时间通知 → 自动恢复必须靠探测

codebuddy 的 429 带「将在 … 重置」，可以精确冷却到那一刻；**knot 只回 `too many requests`，不告诉你什么时候能恢复**。所以 knot 侧的正确做法是反馈式：

```
撞 429  → 立即把本项目并发降到 1，短冷却 60s（不是等某个通知的时刻）
连续 5 条成功 → 并发 +1（上限 = 本项目硬上限 2）
timeout  → 属于通道占用，不降并发、只打断连续成功计数，错峰/绕过
```

`knot_rate_budget.AdaptiveConcurrency` 已实现并持久化到文件，跨重启保留：

```python
a = AdaptiveConcurrency()
workers = a.current()
a.on_rate_limited()   # 撞 429
a.on_success()        # 成功后调用，自动逐步回升
```

## 六、与本机其它通道的关系

- **knot-cli**：走上面这套速率预算；按模型分桶、每模型 `Semaphore(2)`、滚动 24h 总量闸门。
- **codebuddy CLI**（另一套、不是本文口径）：独立账号额度通道，429 文案**明确通知重置时刻**，走 `quota_exhausted` 整模型冷却到那一刻、到期自动回归。它不走 knot 凭证池，批量判定优先走它。knot 没有这个通知，不能照抄这套冷却逻辑。
- **timeout**：两条通道都可能出现，属于通道占用，官方限流文档不管；处理方式是错峰/绕过，不是重试。

批量封装见 `knot_batch.py`；会话产出定位见 `ai-session-forensics.md`；codebuddy 接入坑见 `codebuddy-cli-notes.md`。

## 七、持续恢复 + 最大限度试探边界但小报错数：AIMD + 指数静默

### 为什么必须是这套，而不是「固定并发」或「撞了就重试」

三个来自官方机制的约束叠加：

1. **限的是速率（次/分），不是并发数**。一次智能体调用还会触发多次模型调用，所以并发只是速率的代理量；短任务 7s 时 2 路就是 官方速率上限，长任务 90s 时 5 路才 官方速率上限。固定数字必然在某种耗时下撞墙、在另一种下浪费。
2. **knot 的 429 没有恢复时间通知**（codebuddy 才有「将在 … 重置」）。不能等一个已知时刻，只能靠请求的成功/失败反馈来推断当前可用容量。
3. **十几个项目共用同一池**，别人占多少随时间波动。本项目的「可用容量」是条起伏的曲线，不是常数。

于是固定并发只有两个结局：定高了持续撞墙，定低了长期浪费。而**撞墙后原地重试是最差的**——模拟 59.8% 报错率，因为重试在容量没恢复时只是重复制造 429。

### 策略本体（TCP 拥塞控制的 AIMD 思路）

| 层 | 动作 | 作用 |
|---|---|---|
| **加性增（AI）** | 连续 5 次成功才把并发 +1，上限硬顶 2 | 慢速逼近边界，一次只多探 1 路，试过头也只多几个错 |
| **乘性减（MD）** | 一次 429 立刻把并发从 2 砍到 1 | 快速脱离拥塞，不让同一批里后续请求一起撞墙 |
| **指数静默** | 连续 429 静默 60/120/240/480s 封顶，静默期**不发请求** | 容量被别人占满（cap=0）时，连「1 路探测」都会每轮报错；整段静默把它变成每 60~480s 才探一次 |
| **成功后清零** | 一次成功把 `fails` 归零 | 容量一恢复就退回原来的收敛速度，不会因历史失败被长期压在 1 路 |
| **timeout 区别对待** | 不降并发，只打断连续成功计数 | 通道占用不属于限流，砍并发是误判；错峰/绕过才对 |
| **三重硬约束** | 速率闸（本项目约 官方速率上限）+ 并发硬上限 2 + 滚动 24h 天级总量 | 分别管秒级速率、瞬时在途、天级预算，缺一层就会从另一维度撞墙 |

**为什么这样「报错数小」**：增是加性的（5 次成功才 +1），减是乘性的（一次撞墙直接砍到 1），系统大部分时间停在容量下沿而不是上沿；再叠加容量归零时的整段静默，避免了「明知发不通还每轮探一次」的无谓报错。代价是吞吐比无脑打满低约 19%，换来报错率降 3~4 倍——这正是「最大限度试探边界但小报错数」的取舍点。

### 定量验证（离散事件模拟，容量随时间波动：宽松 2 / 半拥塞 1 / 被占满 0）

| 策略 | 成功 | 429 报错 | 平均并发 | 报错率 |
|---|---|---|---|---|
| 固定 2 路 | 175 | 65 | 2.00 | 27.1% |
| 固定 1 路（保守） | 95 | 25 | 1.00 | 20.8% |
| 撞了原地重试 3 次 | 175 | **260** | 2.00 | **59.8%** |
| AIMD（加性增/乘性减） | 160 | 27 | 1.56 | 14.4% |
| **AIMD + 指数静默（采用）** | 142 | **9** | 1.57 | **6.0%** |

对比「固定 1 路」：报错少 64%（9 vs 25），吞吐高 49%（142 vs 95）——说明它既更保守地报错、又更充分地试探了边界，不是靠一味降并发换来的。对比「固定 2 路」：报错少 86%，吞吐只掉 19%。

状态机单测（两侧实现各自验证）：`2 → 撞429=1 → 冷却过期+5次成功=2 → 再10次仍=2`；连续 429 静默 `60/120/240/480/480s` 封顶；成功一次 `fails` 归零。

### 验证边界（必须如实说）

- ✅ 策略逻辑：模拟 + 状态机单测通过。
- ✅ 代码落地：`业务项目` 的 `knot_slot.py`（`note_knot_rate_limited` / `note_knot_success` / `note_knot_timeout` / `wait_if_cooling`，跨进程文件状态）与 `LLMClient` 的 429 / 成功 / 超时三处反馈；skill 的 `AdaptiveConcurrency` 是同一套逻辑。
- ❌ **真实生产限流场景未触发**：2026-11-12 14:25 查日志，三份队列日志 `429 = 0`、`降并发 = 0`，自适应状态是 `{workers:2, cool_until:0, fails:0}`。原因是批量静态判定已绕到 codebuddy 独立通道（`knot-cli 调用 = 0`、`codebuddy 成功 548`），knot 侧只剩动态复现单路串行，从没撞到 429。所以**AIMD 在真实 knot 限流下的收敛行为只有模拟证据，没有生产证据**；要拿到生产证据需要一次真实 429（或故障注入），不能声称已线上验证。
- 真实系统当前报错集中在 **codebuddy 的 timeout**（`free-model` 46 次、`free-model-preview` 37 次超时，62 次「连续 2 次超时冷却」），那是另一套机制（通道占用降权 + 额度通知冷却），不属于 knot 的 429 策略，别混为一谈。

## 八、实战反例与排查顺序（原 playbook 压缩，别再踩）

### 三个反例

| 反例 | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 用「单任务封装」做批量 | 18 路并发、4 分钟 0 条返回，单条探活却 6.7s 正常 | 封装 `retries=3 / timeout=180 / 限流后 sleep 45s`：前一批撞 429 全进退避，worker 被占满，后续任务发不出去 | 批量必须用**单次调用**：`timeout=25`、不重试、失败返回 None。实测 24 条 / 46 秒 |
| 不分模型堆全局并发 | 全局 10 路 48 条 → 16 成功 / **32 失败**（全 429） | 限的是**每模型在途/速率**，不是整机总并发 | 按模型分桶、每模型 `Semaphore(2)`；实测 9 模型×2=18 路 → 48 条成功 35 |
| 只看 `returncode == 0` | 把 429 错误串当成 AI 回答写库 | 429 时 knot **RC=0、stderr 空、错误串在 stdout** | 检测 `429 / too many requests / 创建异步请求失败 / RateLimitError / "type":"error"`，命中即失败不写库；另有 `[任务规划中]` 前缀、`requestID` 后缀干扰，`json.loads(stdout)` 会全量误杀，要用括号配对提取 |

### 判据表

| 现象 | 判据 | 正确动作 |
|---|---|---|
| 偶发单条格式错/抖动 | 一批失败 <20%，且不是集中 429 | 短退避 8s/16s 最多 2 次，或留到下轮 |
| 并发超阈值 | 连续两轮 429 占比 >30%，或同一模型 `/proc` 里已有 ≥3 个 chat | 降并发 + 切下一个模型；**不要 45s 退避重试同一模型**（所有 worker 一起等） |
| 探活就失败 | 单次调用 `rate_limit` | 通道被别人占满，整轮跳过，不要逐条重试 |
| 单条 timeout | 偶发 | 记失败不写库，下轮断点续跑；**timeout 是通道占用，不属于限流** |
| `模型资源非常紧张` | 平台负载文案 | 不是个人限流；短退避 8s/16s 最多 2 次或换模型 |
| `使用量已超出…将在…重置` | **codebuddy 账号额度，不属于 knot** | 整模型冷却到通知时刻并持久化；**knot 的 429 没有恢复通知，不能照抄** |

**重试有用/无用的分界线**：看失败是否**集中在 429 且随并发数变化**。并发 10→4、失败 32/48→6/24 就是容量问题，重试无用；固定并发下偶发 1~2 条格式错就是抖动，短退避有用。

### 排查顺序

1. `python3 knot_batch.py` 看全局 chat 数与按项目/模型分布，先确认是「自己并发高」还是「别人占满」。
2. 看错误串是 `429`（限流）还是 `timeout`（通道占用）——两者处理不同，别混。
3. 数 `/proc` 里同模型 chat 数；`pgrep` 在 Python 子进程里会漏报，要用 `/proc/*/cmdline`。
4. 确认是不是孤儿（`ppid=1` 且挂很久）占着槽，按本项目特征精确清。
5. 最后才调超时/换模型；先降并发和让路通常更快恢复。

### 探活频率

探活本身也占额度：**进程启动时一次 + 每 10 批一次**，失败整轮跳过。不要每条判前都探（`knot_batch.PROBE_EVERY = 10`）。

### 三个必踩的统计坑（否则会得出「全局 640 次限流」的荒唐结论）

1. **`grep 429` 会把时间戳毫秒 `.429`、文件名 `...4294cf...`、进程号全算进去**。本机误计 640 行，精确模式是 0。
2. **`限流` 二字会命中 `write response` 里 Python 脚本文档正文**（知识站脚本注释含「限流」），不是限流事件。误计 45 行，精确模式是 0。
3. 主日志里 `[IsolateScheduler] wake` 每分钟一条是**心跳**，不是模型请求。按「全部带时间戳的行」统计会得到每小时 ~370 的稳定假象，必须只数带 `"request_id"` / `"model"` 的行。

严格模式：`"code"\s*:\s*429|too many requests|RateLimitError|api request failed with status 429`，并且排除 `write response` 行。

可复用片段：

```python
import re, collections, urllib.parse
ts = re.compile(r'^(\d{4}-\d{2}-\d{2}) (\d{2}):')
req = re.compile(r'"request_id"|"model"\s*:')
strict = re.compile(r'"code"\s*:\s*429|too many requests|RateLimitError')
h = collections.Counter(); e = collections.Counter()
for line in open('<knot 主日志路径> errors='ignore'):
    m = ts.match(line[:25])
    if not m: continue
    hk = m.group(1)+' '+m.group(2)
    if req.search(line): h[hk] += 1
    if strict.search(line) and 'write response' not in line: e[hk] += 1
```

`.gz` 历史用 `zgrep -cE '"code"...|too many requests|RateLimitError'`。

### 本项目闸门的真实作用域（别高估）

- `knot_slot.py` 的 `<项目私有状态文件>`、`<项目私有状态文件>`、`<项目私有状态文件>` 都是 **业务项目 私有文件**；其它十几个项目不认这些锁，**本项目无法全局协调并发**，只能靠 `global_knot_chats()` 读 `/proc` 观测别人占用后主动让路。
- `RateBudget.day_remaining()` 只在**本项目调用时**记一次，统计的是本项目自己的滚动 24h 用量，**不是官方「个人 LLM 总量 ≤2000/天」的全局账本**（那个包含所有项目、按人聚合）。所以 `PROJECT_SHARE=0.25 / GLOBAL_PER_MODEL_CAP=3` 是**用户给的经验值**，不是实测出来的全局容量。
- 结论要写准：本项目能严格保证的只有「自己 ≤2 并发 + 自己 ≤官方速率上限」，以及「观测到全局拥堵时排队/静默」；全局额度是否触顶，只能从主日志/官方后台确认，本地策略无法直接读取。

### 对策略结论的影响

AIMD + 指数静默依然成立（它本来就是「不知道全局容量、只能靠成功/失败反馈推断」的拥塞控制），但验证等级要标清：模拟 + 单测 + 故障注入通过；**生产未触发 429**（因为批量静态判定已绕到 codebuddy 独立通道，knot 侧只剩动态复现单路串行）；**全局视角是事后补的观测，不是策略设计时的输入**。
