# 任务书：文章级深读（radar/analyze-article）

> 目标：从一篇技术文章里提取**机制**，并严格区分「作者声称」与「可验证事实」。
> 文章的默认上限是 `adapt`；只有给出可复核代码/数据的文章才可能 `adopt`。

## 0. 输入与产出

- 输入：文章正文（雷达仓库已抓取的 `data/articles/*.md` 优先，避免重复抓取；否则用原文 URL）。
- 产出：`radar/analyses/<简报日期>/<序号>-<slug>.md`，并 record 入账。
- 时间盒：单篇 20 分钟。正文被导航/评论污染时，只读连续正文段落，跳过页头页脚。

## 1. 三遍读法

1. **第一遍（2 分钟）**：标题、导语、小标题、结论段。写一句话：作者想让读者相信什么。
2. **第二遍（10 分钟）**：找机制——数据怎么流、状态放哪、失败怎么处理、谁写谁读。
   每找到一个机制，摘 1–3 句原文（≤120 字），标注小节标题。
3. **第三遍（5 分钟）**：找证据——有没有代码、配置、数据、线上指标、失败案例。
   没有证据的机制，标 `声称`；有证据的标 `可验证`。

## 2. 必答问题

1. 文章描述的**真实失败场景**是什么？（没有失败场景的架构文，价值有限）
2. 机制的最小形态是什么？去掉产品名和内部术语后，剩下哪几条规则？
3. 关键数据结构/协议长什么样？（字段、消息、状态机）
4. 哪些是**约束**（必须满足才能成立），哪些是**选择**（可以换）？
5. 有没有反例/失败复盘？作者怎么发现问题的？
6. 这些机制在 agent-ops 里是**已具备 / 更弱 / 缺失 / 不适用**？
7. 如果要抄，最小改动是什么？如果不抄，最硬的理由是什么？

## 3. 证据分级（决定 verdict）

| 级别 | 特征 | 最高 verdict |
|---|---|---|
| A 可复核实现 | 给出仓库/文件/代码片段/配置，能定位 | `adopt` |
| B 可复核数据 | 给出线上指标、压测、故障数据，但无代码 | `adapt` |
| C 机制描述 | 只有架构图和术语，无实现细节 | `adapt`（且必须给最小实现方案） |
| D 观点/通稿 | 产品介绍、未来展望、无失败场景 | `skip` |

**文章里的「我们做了 X」不等于 X 的机制成立**。没有失败分支描述的机制，默认按 C 级处理。

## 4. 常见话术的识别

- 「一次装配，按角色投影」→ 追问：投影规则写在哪？新增角色要改几处？缓存失效怎么办？
- 「单一结果信封」→ 追问：字段版本怎么兼容？大对象怎么引用？失败结果长什么样？
- 「单写者 + 租约」→ 追问：租约过期与任务仍在跑怎么区分？时钟漂移怎么办？
- 「三重标识防过期验证」→ 追问：哪个标识变化会使验证失效？谁来更新？
- 「毫秒级快照/回滚」→ 追问：快照包含进程内存吗？外部副作用怎么回滚？

把追问的答案写进报告；答不上来就是「文章未说明」，不是你补全。

```markdown
- 类型：article

- 结论：adopt | adapt | skip

- 原文摘录：「……」（小节：<小标题>）
- 机制形态：（去掉术语后的规则）
- 数据结构/协议：
- 失败分支：文章说明了 / 未说明
- 证据级别：

## 3. 与 agent-ops 的对照
| 维度 | 文章 | 本 skill 现状 | 差距 |
|---|---|---|---|

## 4. 可验证性
（哪些能本地复现；哪些只能等真实故障）

## 5. 最小落地方案（若 adapt/adopt）
（改哪里、加什么字段、怎么测；≤150 行）

## 6. 判定与理由

## 7. 未说明的部分
（追问后仍无答案的问题，列出来，供下次遇到同作者/同团队时优先核验）
```

## 6. 完成判据

- [ ] 每条机制都有原文摘录或「文章未说明」的明确标注；
- [ ] 证据级别与 verdict 一致（C/D 级不许给 `adopt`）；
- [ ] 至少回答了第 1、2、6、7 个必答问题；
- [ ] 若给 `adapt`，有最小落地方案与验证方式；
- [ ] 若给 `skip`，写清是「不适用」还是「证据不足」，两者后续处理不同。
