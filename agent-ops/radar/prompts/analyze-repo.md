# 任务书：仓库级深读（radar/analyze-repo）

> 目标：从一个上游仓库里，提炼出**能脱离原框架、在单机 Python 标准库环境验证**的机制，
> 并给出 adopt / adapt / skip 的判定与证据。不是写项目介绍，不是夸架构。

## 0. 输入与产出

- 输入：`python3 scripts/radar_cli.py workspace --candidate <id>` 输出的本地路径与 `commit_sha`。
- 产出：`radar/analyses/<简报日期>/<序号>-<slug>.md`，并 record 入账。
- 时间盒：小仓库（<5k 文件）一轮 40 分钟内；大仓库先读 docs/架构与入口，再定点读，
  **不要 `cat` 全仓库**。读不完的部分在报告里写「未覆盖」，不许假装读过。

## 1. 先定位（10 分钟）

按顺序读，每读完一层写 3 行笔记：

1. `README` / `README.zh` / `docs/architecture*`：它自称解决什么问题，怎么分层。
2. 入口：`cmd/`、`main.*`、`server/`、`app.py`、`pyproject.toml`、`go.mod`、`package.json`。
3. 数据模型：`migrations/`、`schema*`、`models/`、`internal/domain/`。
4. 测试与文档中「失败/恢复/重试/lease/lock/checkpoint」关键词的命中位置。

写下一句话：**这个仓库的核心循环是什么（输入→状态→执行→产物→回收）**。
写不出来就继续读入口，不要开始逐文件摘抄。

## 2. 结构测绘（只记与借鉴有关的）

- 语言与运行时、构建方式、外部依赖（DB/消息队列/容器/云服务）。
- 模块边界：哪些是「引擎」，哪些是「适配器」，哪些是「业务样例」。
- 状态存放：内存 / 文件 / SQLite / Postgres / Redis；单写还是多写。
- 进程模型：单进程、多进程、容器、K8s；有没有租约/心跳/选举。

> 这一节只回答「它的机制依赖了什么假设」。依赖越重，可移植性越差。

## 3. 机制清单（按 agent-ops 的问题清单逐项找）

对每一项，找到就给证据；找不到就写「未实现/未找到」，**不要用文章里的说法替代代码**。

| # | 机制 | 在 agent-ops 里对应什么 | 要找的证据 |
|---|---|---|---|
| 1 | 任务状态机与不可变性 | `taskctl` 的 status/attempts | 状态枚举、迁移函数、非法迁移的处理 |
| 2 | 领取与租约 | `lease_until` + `BEGIN IMMEDIATE` | 抢占 SQL/事务、过期回收、双写保护 |
| 3 | 断点续跑 | `progress.md` + resume | 检查点写在哪、恢复时读什么、幂等怎么保证 |
| 4 | 失败重试与退避 | attempts/backoff | 重试上限、退避曲线、不可重试错误的分类 |
| 5 | 从中间节点重跑 | 目前较弱 | 节点级 checkpoint、产物引用、回滚到某节点 |
| 6 | 人工门禁 / 审批 | `manager` 的 escalate | 等待态怎么持久化、超时、恢复、审计 |
| 7 | 上下文装配与投影 | 模板 + progress/result | 全局事实包、按角色裁剪、大对象引用 |
| 8 | 结果信封 | `result.json` 五字段 | 统一 schema、校验、版本兼容 |
| 9 | 子任务编排（DAG/SOP） | `plan` 拆解 | 依赖表达、并发度、失败传播 |
| 10 | 观测与审计 | `task_events`、日志 | 事件模型、trace 关联、成本统计 |
| 11 | 资源隔离与清理 | 租约回收、缓存清理 | 工作区生命周期、TTL、容量上限、孤儿回收 |
| 12 | 配置与密钥 | `jobs.json`、env | 单一配置源、密钥不落盘、校验 |

**只深挖命中 1–2 个的机制**：找到最有价值的 2–3 项读透，其余标记「已扫描，未见实现」。
把 12 项平均用力等于什么都没读透。

## 4. 每个机制要回答的六个问题

1. **它解决什么失败**？（没有失败场景的机制是装饰）
2. **最小实现是什么**？去掉框架、DB、容器后，剩下哪几行逻辑？
3. **数据放在哪**？字段、唯一约束、索引；并发下谁写谁读。
4. **失败分支**：崩溃在写入前/后、重复执行、部分成功，分别怎么处理？
5. **边界**：单机成立吗？标准库能实现吗？需要新依赖吗？
6. **反例**：什么情况下这套机制会害了我们（过度设计、与现有租约冲突、维护成本）？

## 5. 可移植性判定

给每个候选机制打三个标签：

- **依赖**：`纯逻辑` / `需要 SQL` / `需要容器` / `需要外部服务` / `需要特定语言运行时`
- **切片大小**：`<50 行` / `50–200 行` / `>200 行` / `不可切`
- **验证方式**：单测 / 集成测试 / 只能人工观察

只有「纯逻辑或需要 SQL」+「<200 行」+「可单测」的组合才值得 `adopt`。
其余最多 `adapt`，并写清改造后的形态。
