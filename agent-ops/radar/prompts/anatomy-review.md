# 任务书：ANATOMY 全文审阅（不是追加）

> 触发：任何 P1 及以上变更完成后；或 `anatomy_check.py` 报错时。
> 目标：**通读 ANATOMY 全文，判断哪些说明已经与代码事实不符，然后把相关章节重写到自洽。**
> 禁止在文末追加一段「2026-xx-xx 更新：新增了 xxx」——那不是解剖，是流水账。

## 0. 为什么不能只追加

ANATOMY 的价值在于「读一节就能知道现在的真实结构」。追加式更新会留下三种毒：

1. 同一事实出现两处，一处新一处旧，读者不知道该信哪一处；
2. 旧章节的因果（为什么这样分层、为什么这个脚本不能直接读 /proc）被新内容淹没；
3. 半年后没人敢删任何段落，文档越来越长、越来越不敢信。

所以每次审阅的产出是「**修订后的章节**」，不是「**更新日志**」。

## 1. 输入

- `ANATOMY.md` 全文（必须逐节读完，不许跳读）。
- 当前代码树：`scripts/`、`templates/`、`tests/`、`radar/`。
- 本次变更：`git diff`（若在提交前）或最近 1–3 个提交。
- 机器初筛：`python3 scripts/anatomy_check.py`（它只抓结构漂移，不判断文字）。

## 2. 逐节提取「声称」并对照事实

对第 1–10 节，每节列出它**断言的事实**，逐条验证：

| 章节 | 断言类型 | 怎么验证 |
|---|---|---|
| 1 一句话架构 | 谁是入口、谁执行、谁监督、数据放哪 | 读 `SKILL.md`、`taskctl.py`/`manager.py` 的 docstring |
| 2 分层 | 依赖方向 | `grep -n "^from\|^import"` 看是否向上依赖 |
| 3 目录树/脚本表 | 每个文件存在、职责准确 | `ls`、`--help`、docstring 首段 |
| 4 数据流 | 状态怎么流动、谁写谁读 | 跟一遍函数调用与 SQL |
| 5 数据位置 | 路径、是否进 git | `.gitignore`、代码里的默认路径 |
| 6 影响矩阵 | 改 A 要同步 B、验证 C | 反向查：谁 import A、cron 调谁 |
| 7 外部引用 | cron/安装副本/公开版契约 | `crontab -l`、`ls -la ~/.codebuddy/skills` |
| 8 雷达 | 数据流、判定口径、磁盘边界 | `radar/README.md`、`radar_*.py` |
| 9 扩展清单 | 新增子功能的步骤是否仍然成立 | 用最近一次新增（雷达）反推 |
| 10 边界 | 「不做的事」是否还成立 | 看是否已经偷偷做了 |

## 3. 五类判定（每一条声称必须落一类）

| 判定 | 含义 | 处置 |
|---|---|---|
| **成立** | 与代码一致 | 保留；若表述含糊，补一句可验证的判据 |
| **过时** | 代码已变，文档还写旧的 | 改写该段，不是加「现已改为」 |
| **不完整** | 只写了「有」，没写「谁依赖/失败怎么办」 | 补因果与边界，不堆字段名 |
| **矛盾** | 同一事实两处不一致 | 找到权威源（代码/门禁），另一处改成指针 |
| **多余** | 描述的模块已不存在 | 删除，不留「历史参考」占位 |

## 4. 六个必查维度（每次都不能少）

1. **依赖方向**：有没有 L1 反向依赖 L2/L3？有没有脚本绕过 `model_policy`/`platform_util`？
2. **数据所有权**：每个状态只有一个写者吗？谁读、谁写、什么事务边界？
3. **外部契约**：cron 的命令名与参数、安装副本路径、公开版生成规则，有没有变？
4. **失败路径**：文档是否只写了 happy path？租约过期、审计失败、clone 超限分别怎么处理？
5. **新鲜度**：哪些数字/条数/版本是写死的？是否已交给 `doccheck`/`anatomy_check`？
6. **边界自洽**：第 10 节说「不做」的事，代码里有没有偷偷做？第 9 节说「必须做」的步骤，最近一次新增是否真做了？

## 5. 执行顺序

```bash
python3 scripts/anatomy_check.py        # 先拿机器清单
# 通读 ANATOMY 全文，产出「修订计划」表
# 按计划重写相关章节（不是追加）
python3 scripts/anatomy_check.py
python3 scripts/doccheck.py
python3 -m pytest tests/ -q
```

修订计划表格式（写在提交说明或 `radar/applied/` 里，不必留在 ANATOMY 正文）：

```
| 章节 | 现状声称 | 代码事实 | 处置 |
|---|---|---|---|
| 3 脚本表 | radar_store 只做解析/入账 | 还负责事务与 claim 事件 | 改写 |
| 6 影响矩阵 | 缺 radar_store | 改事务要跑 test_radar | 新增行 |
| 7 外部引用 | 安装副本 mtime 对齐 | 实际用 rsync 全量同步 | 改写 |
```

## 6. 反模式

- 在文末加「## 更新记录」，正文不动。
- 保留过时段落，在旁边写「（已废弃）」——读者仍会读错。
- 把「计划做」写成「已实现」（`running_not_ready`、验证门禁这类未落地项必须标清楚）。
- 只改数字（测试数、脚本数），不改它背后的因果。
- 为了让 `anatomy_check` 通过而删掉检查项，而不是修文档。

- [ ] 所有「过时/矛盾」已改写或删除，不是旁注；
- [ ] 第 6 节影响矩阵覆盖本次改动涉及的文件；
- [ ] 第 7 节外部引用与真实 cron / 安装副本一致；
- [ ] 未落地的东西（计划/未采纳）明确标注，不与已实现混写；
- [ ] `doccheck.py` 与 `pytest` 通过。
