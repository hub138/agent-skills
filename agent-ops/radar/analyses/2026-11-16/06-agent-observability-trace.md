# 面向生产流量的 Agent 可观测：Trace 分层与先筛后评

- 来源：2026-11-16 15:00 #2 / https://www.cnblogs.com/OceanBase/p/23612511
- 类型：article（证据级别 B：有线上规模数据与埋点规范，无开源代码）
- 相关性：3
- 结论：**adapt（本期不落地）**

## 1. 核心机制

- **以 Trace 为中心**做端到端实时评估，而不是离线抽样看日志。
- **先筛选再评估**：先用便宜规则筛出异常 trace，再交给贵的评估器，控制成本。
- **埋点分层**：通用层 / 场景层 / 业务层，三层各自定义字段与责任人。
- **声明式表达式**把「提取」与「评估器」分开：提取规则可配置，评估器可复用。
- 规模：一天 10TB Trace、一年 3–6PB；数据沙箱 Fork 毫秒级，便于回放。

## 2. 与 agent-ops 的对照

| 维度 | 文章 | 本 skill 现状 | 差距 |
|---|---|---|---|
| 事件模型 | 分层埋点 | `task_events(task_id, kind, payload)` 平铺 | 无层级，但字段可扩展 |
| 先筛后评 | 规则筛 → 评估器 | `manager.should_ask()` 先判断是否值得调模型，再 `ask_model` | **已具备同类思想** |
| 成本控制 | 采样/筛选 | 快照只读 progress 头尾，超长要求重写 | 已具备 |
| 回放 | 数据沙箱 Fork | 无；靠任务目录 + 会话 jsonl | 不适用（单机无 trace 库） |

`manager.py:250 should_ask()` 已经是「先筛后评」：不是每轮都调模型，而是按快照与
状态决定是否值得问；`ask_model` 只在需要时触发。这与文章的核心成本策略同构。

## 3. 可移植性

- 埋点分层：可以给 `task_events.payload` 约定 `layer` 字段（generic/scenario/business），
  但当前消费者只有 manager 与审计脚本，分层没有第二个使用方，属于提前抽象。
- 声明式表达式提取：需要一套表达式语言与评估器框架，成本远高于收益。
- Trace 存储：本 skill 的规模是「几十万任务行、几条事件」，不需要 10TB 级设施。

## 4. 判定与理由

`adapt`，本期不落地。可借鉴的是「先筛后评」的成本纪律，而它已经存在于
`manager.should_ask`。剩余机制（分层埋点、表达式评估器、Trace 存储）在单机规模下
没有使用场景。若未来 `task_events` 的消费者超过 3 个，再评估加 `layer` 字段。

## 5. 没抄什么及原因

- 10TB/天级 Trace 设施：规模不匹配。
- 数据沙箱 Fork：需要专门的存储引擎，本 skill 不引入。
- 声明式表达式评估器：为一个消费者建 DSL，维护成本高于收益。

## 6. 第二轮深读补充

- 埋点三层：通用层（OTel GenAI 语义约定）、场景层（轮次/工具调用）、
  业务层（业务域字段）。
- 筛选链：Trace 标量字段走 DB 过滤 → 正则/关键词 → 小模型 → 大模型，先筛后评控成本。
- 声明式表达式把「提取」与「评估器」分开：字段路径变化只改表达式，评估器复用。
- 规模：最大应用 10TB/天、年 3–6PB；97% 以上是文本；单条 Trace 3–20MB；
  数据沙箱千张表 Fork 毫秒/秒级。

结论不变：`manager.should_ask` 已是先筛后评；本 skill 没有第二个评估器消费者，
分层埋点与表达式 DSL 属于提前抽象。
