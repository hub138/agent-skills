# 长任务续跑的工程学：检查点四问与副作用前落盘

- 来源：2026-11-16 15:00 #1 / https://cloud.tencent.com/developer/article/2784829
- 类型：article（证据级别 B：有 AWS 官方口径与工程清单，无开源代码）
- 相关性：5
- 结论：**adopt（本期落地：写进任务收工契约）**

## 1. 作者的核心主张

长任务不是「把超时调大」，而是把「断了之后还敢不敢接着跑」变成可检查的工程事实：
检查点、确定性重放、幂等三件套；**有外部副作用时，重跑可能是一次新事故**。

## 2. 机制提取

### 2.1 检查点最小快照四问

原文（02 节）：一个可用的检查点最少要能回答四个问题：

1. 现在执行的是哪一版目标？（用户中途改过需求吗）
2. 已经确定完成了什么？（哪些有可验证结果，可直接跳过）
3. 下一步做什么？
4. 有没有结果未知的副作用？（哪个请求可能已发出但没收到回执）

并给出硬约束：**任何产生外部副作用的步骤，必须在执行之前落盘**。
副作用发生了却没记录，系统就进入「既不能安全重做、也不能安全跳过」的死角。

### 2.2 幂等与三阶段

- 稳定幂等键由 `run_id + 步骤名` 派生；
- `PREPARED → EXECUTED → CONFIRMED` 三阶段，请求可能已发出但无响应时停在「结果未知」，
  进入对账而不是盲目重试。

### 2.3 八项清单（09 节）

列副作用工具并标注可重放/需补偿/不可撤销；稳定幂等键；副作用前的 PREPARED + outbox +
检查点同事务；编排代码确定性；检查点记四问；恢复前用稳定 ID 查权威回执；
长等待用可唤醒持久化状态；把恢复正确性写成可回放评测用例。

## 3. 与 agent-ops 的对照

| 维度 | 文章 | 本 skill 现状 | 差距 |
|---|---|---|---|
| 检查点四问 | 显式四问 | `progress.md` 由模板引导，未强制四问 | **可补** |
| 副作用前落盘 | 硬约束 | 无显式约束（模板只说写进度） | **可补** |
| 幂等键/三阶段 | 推荐 | 任务级 `attempts`，无外部副作用协议 | 不适用（本 skill 不直接调外部写接口） |
| 恢复前对账 | 三路分支 | `resume` 读 progress 继续 | 部分（靠人/manager 判断） |

## 4. 为什么只落「四问」

- 本 skill 的子任务通常改文件、跑命令，**外部副作用较少**，幂等键/outbox 属于过度设计。
- 但「哪版目标 / 已完成 / 下一步 / 未知副作用」这四问直接对应三次真实事故：
  目标被改后 worker 仍按旧目标跑、重复执行已完成步骤、崩溃窗口里的半成品。
- 落点是 `templates/tasks/_done-contract.md` 的「从断点继续」段：加一节「五、断点快照四问」，
  要求每轮写 progress 时补齐四问，尤其「未知副作用」。

## 5. 判定与理由

`adopt`，改文档不改运行时：成本低、可验证（渲染后的提示词包含四问）、
不引入新状态。这是本期最确定的一条。

## 6. 落地与验证

- 改动：`templates/tasks/_done-contract.md` 增加「断点快照四问」与「副作用前落盘」；
- 验证：`taskctl render_prompt` 真实渲染一次 generic 任务，确认四问出现在提示词中；
- 回滚：revert 该文件即可，无数据迁移。

## 7. 没抄什么

- 幂等键、outbox、PREPARED/EXECUTED/CONFIRMED 三阶段：本 skill 不直接调外部写接口，
  真正的外部副作用在子 agent 的代码里，应由子任务自己负责；在编排层再造一套是重复。
- 确定性重放：依赖「编排代码 + 事件历史」，本 skill 的编排是 Python 脚本 + 文件，
  不属于同一模型；`resume` 的语义是「接着做」而不是「重放」。
